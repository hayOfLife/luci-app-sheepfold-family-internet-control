## B144: ответ относится к запросу, а не ко всему текущему черновику

Общие поля Settings продолжают изменяться, пока Save-кнопки отключены. Старый
flow после save очищал весь текущий объект, а не только отправленные опции.

| Точка | До ответа | Старый результат | Новый результат |
| --- | --- | --- | --- |
| save ожидается | Отправлено `note=submitted`, добавлено `extra=later` | draft пуст | `extra=later` остаётся |
| runtime отказал после записи | Пользователь изменил `note` и добавил `extra` | Повторная очистка удаляет оба | Оба поздних значения остаются |
| Только special-saver сохранялся | Во время его ожидания введена общая опция | Его persisted-ошибка очищает общую опцию | Общая опция остаётся, общий save не вызывался |

`acceptOptions(snapshot)` проверяет собственные ключи снимка и текущее строковое
значение. Если оно уже отличается, опция не принимается как сохранённая. Повторно
введённое в точности сохранённое значение может быть снято с dirty: новый запрос
для него не нужен. Если пользователь вернулся к прежнему значению, отличному от
переданного, оно остаётся для новой записи.

Сохраняется различие стадий: подтверждённые общие опции принимаются до runtime,
а runtime-failure не отменяет их запись и не принимает новый ввод. Для ошибки
общего saver с признаком persisted предусмотрено однократное принятие его снимка.
Специальный saver не получает права очищать общие поля, которые ему не передавались.
Полный `clearOptions()` оставлен для намеренного сброса, но из этого save-flow удалён.

Воспроизведение не использует реальную конфигурацию: настоящий JS передаёт пакеты
в записывающую модель persistence, а Promise-барьер позволяет добавить draft точно
до ответа. Сравниваются пакет, оставшаяся память и ручной повтор. Контрольные поздние
post-save случаи, которые уже проходили на старом коде, не выданы за новые дефекты.

## B145: общая обработка должна существовать до первого callback

Старая последовательность: установить saving, обновить кнопки, вызвать save и
только к возвращённому Promise подключить catch/finally. Синхронный throw оставлял
внутренний saving=true, хотя внешний currentSave уже освобождался. Тот же пробел
затрагивал исключение callback при включении busy.

Теперь busy-entry и вызов save выполняются из `Promise.resolve().then(...)`.
Синхронное исключение становится отклонением уже подготовленной цепочки. После
охваченного отказа оба guard освобождаются. Ручной повтор после исправления причины
проходит, а повторное нажатие во время текущей операции возвращает тот же Promise.
Автоматического повтора или скрытого подавления ошибки нет.

Тесты различают исключение save, отказ buttons и onChange, неуспешную валидацию,
отмену подтверждения и нормальный путь. Они проверяют модель управления кнопками,
не настоящий DOM. Одновременный отказ всех финальных UI-callback или физической
отрисовки не объявлен устранённым.

## B146: фиксированное действие для фиксированного подтверждения

Прежний save читал время для диалога, но executeSave повторно читал весь draft
после согласия. На тесте `confirm=23:00`; пока диалог ожидал, введены `20:00` и
новое поле. Старый пакет содержал позднее время и поле, затем всё очищалось.

В новом flow общий snapshot захватывается перед диалогом. Он же передаётся в
executeSave, validation, persistence, runtime и post-save. В тесте saver получает
23:00, а `20:00` и дополнительная опция остаются для отдельного Save. Диалог не
подтверждает эти новые значения молча. Если пользователь отменяет действие,
запись не начинается.

Копирование всего состояния UI не добавлено: список специальных savers фиксируется,
но их внутренние поля не замораживаются этим snapshot. Изменение fallback-значения
на роутере в другой сессии также требует отдельной проверки общей согласованности.

## Ограничения и дальнейшие границы

- Общий draft Settings не равен очереди UCI. Native rpcd, batching, reload кэша,
  другие вкладки/CLI, окно после последней проверки и общий rollback остаются R03.
- Специальные savers имеют собственные draft/save/accept. Этот проход не гарантирует
  сохранность их позднего ввода или неизменность внутренних параметров подтверждения.
- Полный render/reset и автоматический page reload, включая смену языка, всё ещё
  могут потерять поздний ввод. Исправление B144 сохраняет его в памяти, а не на диске.
- Сообщение успеха относится к исходному снимку. Остаток dirty требует нового явного
  Save; автоматического сохранения или повтора изменяющих команд нет.
- Ошибка уведомителя или конечной отрисовки может препятствовать показу сообщения.
  Снятие флага в модели не доказывает исправность всего браузера.
- Прежние сырые копии не удаляются и не шифруются задним числом. Безопасный фоновый
  экспорт и согласованное облачное восстановление ещё не реализованы.

Ни эти проверки, ни сохранённая история r323 не делают кандидат принятой стабильной
версией. Правило «Без ограничений» выше чёрного списка для обычного интернета,
отдельные запреты управления и карантин не менялись.

## Применение без commit и без установки

Два патча альтернативны:

1. `sheepfold-r323-review-settings.patch` применяется к чистому `1e9c43b` **вместо**
   всех прежних review-патчей.
2. `sheepfold-r323-review-settings-delta.patch` применяется **после** ранее выданного
   `sheepfold-r323-review-persistence.patch`.

Не применяйте их последовательно друг к другу или прямо к принятому `bdb3a92`.
Сначала сохраните существующую рабочую копию; используйте новую папку:

```sh
git clone --branch main sheepfold-r323-main.bundle sheepfold-review-settings
cd sheepfold-review-settings
git rev-parse HEAD
git apply --check ../sheepfold-r323-review-settings.patch
git apply ../sheepfold-r323-review-settings.patch
```

содержит правки. Команды ничего не отправляют в GitHub и не создают новый коммит.
Новый bundle не выдаётся, потому что он не включил бы незакоммиченные изменения.
Полный ZIP содержит исходники без `.git`, тестовых временных каталогов и зависимостей.
