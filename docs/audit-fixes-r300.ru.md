# Аудит и исправления Sheepfold r300

Дата: **10 сентября 2026 года**. База — `17e4f90` (r299), потомок принятой
`bdb3a92` с сохранёнными доработками тестирования и CI. Пакет: **0.1.0-300**,
ветка `main`. Точный итоговый commit, дерево и SHA-256 файлов зафиксированы в
`delivery-verification.json` поставляемого архива проверок. Push и установка
на роутер/телефон не выполнялись.

## Результат

Исправлены четыре группы B68–B71 в **общей постоянной административной очереди**.
Она отличается от RAM-просьб ребёнка прошлых r298/r299: путь по умолчанию
`/etc/sheepfold/admin-notifications`, срок 30 дней, максимум 100 событий.
[Накопительный реестр](bug-register.ru.md) содержит 71 карточку с подробными
причинами, решениями, альтернативами, проверками и ограничениями.

| Карточка | Прежнее поведение r299 | Изменение |
|---|---|---|
| B68 | Ошибка reader удаляет уведомление; ошибки часов/перечисления скрыты | Целостное чтение записи, проверяемый план удаления и сохранение проблемного файла |
| B69 | `/notifications` заранее выдаёт 200; control-байты повреждают JSON | Буферизация успешного результата, 503 при отказе, корректное escaping |
| B70 | Два одинаковых enqueue оба новые; 101-я запись остаётся; медленный Telegram удерживает канал | Общий lock, повторная квота после вставки, освобождение lock/каналов до handoff |
| B71 | Игнорируются права; failed mv оставляет tmp; ID collision перезаписывает файл | Проверяемая закрытая подготовка, уникальный tmp, очистка своего пути, отказ от замены |

## Что именно изменено

Два производственных файла:

- `package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-admin-notification`;
- `package/luci-app-sheepfold-family-internet-control/root/www/cgi-bin/sheepfold-api` —
  только блок `/notifications`, без изменения авторизации, лимитов и других маршрутов.

В Makefile изменён только `PKG_RELEASE`. Зависимости не добавлены: общий lock-helper
и flock уже поставляются обеими редакциями. Android, LuCI, firewall, токены,
workflow и runner-скрипты не изменены. D01 остаётся действующим: «Без ограничений»
выше чёрного списка устройств для обычного интернета; отдельные запреты управления
роутером и карантин сохранены. Уведомление не выдаёт ребёнку интернет.

Добавлены `tests/adminNotificationRuntime.test.mjs` и
`tests/helpers/adminNotificationFixture.mjs`. В карте categories тест относится к
backend/messaging. В changeImpactRules добавлены прямой consumer нового fixture и
новый consumer существующего parser `routerRuntimeFixture`; механизм выбора не
переписан. Тест карты теперь проверяет и новую связь. Уточнены профильные документы.

## Воспроизведение и доказательства

`baseline-probes.json` фиксирует три прямых наблюдения на старом helper: удаление
правильной записи после фактического reader failure; stdout с невалидным JSON при
`0x08`; 101 файл после успешного добавления к 100. Это изолированный каталог, не
производственное хранилище. Похожий класс старого дефекта в другом helper не
используется как замена воспроизведению этого файла.

Runtime-тесты запускают настоящие скрипты, перемещая только системные пути.
Авторизация/адрес/часы синтетические, Telegram заменён локальным trace-получателем.
Любая подставленная sed/awk/ls/date/chmod/mktemp/mv/rm/flock должна отметиться в
trace. Применяется системный POSIX sh, а не BusyBox ash, способный обойти PATH
встроенным applet. Windows не получает ложного подтверждения Unix-прав и flock:
нативные сценарии явно ограничены Linux.

В гонке первый процесс удерживается перед публикацией, второй должен явно достичь
либо прежней публикации, либо нового lock. Только после этого снимается барьер.
На r299 два `duplicate:false`, на исправлении один false и один true, один файл и
один Telegram-handoff. Ещё два теста внешним flock удерживают тот же inode для list
и cleanup. Синтетический медленный Telegram остаётся остановленным, когда основной
helper уже завершил ответ, а queue-lock свободен.

Проверены и частичные результаты: после успешной публикации ошибка quota-rm
оставляет 101 файл и возвращает nonzero, а не обещает откат. Повтор после снятия
отказа подчищает квоту и возвращает прежнее событие. Это зафиксированная граница,
не удалённый ради зелёного результата assertion.

## Как повторить профильные проверки

Рабочий каталог — корень клона. Требуются Node.js 22, системный sh, awk/sed и
обычные файловые утилиты; Linux и flock для native-сценариев. Python 3 нужен только
для тестовых IPK. Все fixtures создаются в `.build/test-fixtures`, затем удаляются.
Секретов, доступа к GitHub, роутеру, Telegram или телефону эти команды не требуют.

```sh
node --test tests/adminNotificationRuntime.test.mjs
node scripts/run-test-category.mjs --file adminNotificationRuntime.test.mjs --file siteListResilience.test.mjs --file simChangeMonitoring.test.mjs --file childWifiNetworkMonitoring.test.mjs --file lockCommon.test.mjs --file apiRateLimitRuntime.test.mjs --file homeNetworkAccess.test.mjs --file packageHardeningRuntime.test.mjs --file changeImpact.test.mjs --file testCategories.test.mjs
```

Ожидается exit 0, **41/41** в новом файле, **152/152 в 10 файлах** профильного контура,
без fail/skip/cancel в Linux. Полный runner не запускался. Соседи выбраны по фактическим
потребителям/границам, не по одному только увеличению версии пакета. Повторные
прогоны и два варианта IPK не увеличивают число уникальных сценариев.

Сравнение с неизменённой базой, создавая новый локальный worktree:

```sh
git worktree add --detach .build/notification-r299 17e4f90
SHEEPFOLD_NOTIFICATION_TEST_SOURCE="$PWD/.build/notification-r299" node --test tests/adminNotificationRuntime.test.mjs
```

У второго запуска ожидается exit 1: **38 fail / 3 pass**. В этом сравнении есть
проверки новых codes/инвариантов; 38 отказов не являются 38 отдельными найденными
уязвимостями. Не запускать production helper прямо от root вместо fixture: штатный
путь расположен в `/etc`, а не в тестовой папке.

### Упаковка, синтаксис, документация

```sh
python3 scripts/build-test-ipk.py --variant all
SHEEPFOLD_TEST_IPK="$PWD/.build/ipk-output/luci-app-sheepfold-family-internet-control_0.1.0-300_all.ipk" node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
SHEEPFOLD_TEST_IPK="$PWD/.build/ipk-output/luci-app-sheepfold-ai-support_0.1.0-300_all.ipk" node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
busybox ash -n package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-admin-notification
busybox ash -n package/luci-app-sheepfold-family-internet-control/root/www/cgi-bin/sheepfold-api
node scripts/checkDocumentation.mjs --git 17e4f90
node scripts/runQualityChecks.mjs --git 17e4f90 --plan
git diff --check
```

Обе тестовые IPK собраны; по 24 архивные проверки прошли. Это быстрый локальный
сборщик, не канонический SDK и не установочный успех. Дополнительный протокол
поставки сравнивает исправленные файлы в обоих архивах с преобразованием исходников
соответствующей редакции и запускает hardening на распакованном root.

Дополнительно четыре обычных вызова enqueue/list/duplicate/cleanup прошли под
локальным BusyBox ash с настоящими часами и файловыми утилитами, без инъекций через
PATH. Они не заменяют проверку конкретной сборки OpenWrt и не прибавлены к 41
уникальному регрессионному сценарию. Обе распакованные редакции прошли hardening;
три проверенных файла (helper, CGI, lock-common) соответствуют варианту исходников.
Проверены восемь изменённых Markdown-файлов, без ошибок.

`quality:plan` сохранён: общий CGI/Makefile и документы заставляют советник
предложить широкий прогон. По фактическому diff изменён только `/notifications`,
новая зависимость тестового fixture и версия; auth/flow/Android не переписаны.
Выбран прямой профиль и ближайшие потребители по принятому правилу §testcat.
Ни сквозного refactor механизма отбора, ни безусловного обхода CI не добавлено.

Для пяти изменённых/новых JavaScript-файлов выполняется `node --check`. ESLint
попытались запустить адресно через `npm exec --offline -- eslint ...`: получен
ENOTCACHED, нужных зависимостей нет. Это не успех lint; lockfile и политика CI не
менялись ради обхода отсутствующего пакета. Shell syntax не заменяет выполнение на
целевом BusyBox/прошивке. Точные команды и stdout находятся в архиве проверок.

## Неуспешные промежуточные проверки

Первый расширенный прогон остановился на test changeImpact: новый файл использовал
`parseCgi` из общего fixture, но не был добавлен к его direct consumers. Исправлена
карта зависимостей, а не ослаблен assertion; следующий прогон прошёл все 10 файлов.
Первоначальные и финальные журналы сохранены отдельно. Попытка интерактивного
container-session отвергнута средой до запуска тестов; использован обычный
синхронный runner. Это не дефекты кода роутера.

## Совместимость и существенные ограничения

Нормальный envelope, ID, типы уведомлений, opt-in/режимы источников и модель
многих родительских телефонов сохранены. HTTP 503 `notifications_unavailable`
сообщает о недоступности данных, не об отзыве токена. Повреждённые записи не
исчезают автоматически: вся очередь будет сообщать ошибку до диагностики.
Старый key=value формат сохраняется, новая схема не вводится.

Telegram — best effort. Сохранение файла и вызов локального отправителя не доказывают
доставку или показ на телефоне. Не добавлены durable outbox/ack/exactly-once,
автоматический повтор изменяющих запросов или глобальная транзакция с UCI.

Открыт R12: предел байтов и время обхода повреждённых файлов, безопасный ремонт,
усечение многобайтного текста прежним clean_value, монотонное время, уборка после
SIGKILL, износ flash, старые writers при обновлении и измерение ожидания flock.
Новое событие сохраняется при ошибке последующей quota-очистки; формальная квота
действует после успешной операции, не при неисправном удалении. Root-writers вне
lock не согласованы, inode не является защитой от привилегированного противника.

Настоящий UCI/flash/uhttpd, physical Android, внешняя Telegram-доставка, live-router,
нагрузка и отключение питания не проверены. Новые Android/SDK/Actions-сборки не
запускались. Исторические успехи принятой базы не переписаны и не присвоены r300.
Это локально проверенный интеграционный снимок, не подтверждённый stable-релиз.

Внешние веб-источники в этом проходе не использовались: выводы основаны на присланном
репозитории, сравнении исполняемых версий и приложенных локальных проверках.
