## Что сделано и что не завершено

Подтверждённый путь отправки сырой полной конфигурации закрыт. Генератор больше
не создаёт tar с `/etc/config/sheepfold`, а `archive-push` обоих облачных backend
явно возвращает `config_backup_unavailable` до отправки очереди и удаления
локальных архивов. Прямая отправка снимка журнала `push-events` сохранена.

**Это временная блокировка всего архивного прохода, включая пакетную отправку
старых журналов. Это не реализация безопасного автоматического экспорта.**
Принятые читаемый JSON и полный AES-GCM экспорт остаются в LuCI. Пароль не переносится
на роутер и не хранится рядом с копией, второго формата не добавлено. Подключение
этого контракта к фоновому заданию и безопасному импорту остаётся следующим этапом.

Также исправлены обнаруженные в ревью пути и подготовка тестовых fixture:
проверка flock, Windows-only последовательная модель при отсутствии утилиты,
согласованный cwd Yandex context, платформенные лимиты дочернего процесса и
диагностика первичного `ETIMEDOUT`/spawn error до разбора HTTP/JSON.
Рабочие блокировки и тайм-ауты роутера/Android не менялись.

В начало обоих облачных документов вынесено действующее состояние. Старые разделы
помечены как исторические, а не удалены. Реестр дополнен **B132–B135**, всего 135
карточек: это не 135 подтверждённых уязвимостей и не 135 новых исправлений.

## Почему выбрана блокировка, а не поспешный новый экспорт

Существующий безопасный сериализатор находится в браузерном модуле
`features/settings/backup.js`. Он формирует `sheepfold-settings-export-v2`,
маскирует секреты, исключает одноразовый QR-код; зашифрованный экспорт использует
`sheepfold-settings-encrypted-v1` и пароль пользователя. Импорт выполняет свои
проверки переноса между роутерами. Текущие shell-экспортёры этот путь не вызывают.

Фильтрация нескольких строк сырого UCI не заменяет эту схему. Самостоятельное
шифрование tar породило бы другой формат, хранение ключа и неопределённый restore.
Продолжение отправки старой непроверенной очереди оставило бы обход через ранее
созданный сырой архив. Поэтому этот кандидат закрывает риск без объявления
нереализованной функциональности готовой.

Блокировка не удаляет локальные или облачные исторические копии, не шифрует их
задним числом и не подтверждает факт реальной утечки. Авторизация и выбор другого
backend сохраняют прежний контракт: при подтверждённой RAM отправитель пропускается.
У Яндекса ошибку фиксирует существующий завершающий обработчик. Старый кэш результата
Google может остаться историческим; новый ответ команды является явным отказом.

## Подробности исправлений

### B132 — конфиденциальность автоматической копии

Из обоих `create_config_backup` удалено сырое копирование/архивирование. Прямой
вызов возвращает exit 78 без файла. `cmd_archive_push` отвечает exit 1 и
`{"ok":false,"error":"config_backup_unavailable"}`. Ни обход через старую очередь,
ни переключатель окружения для разрешения сырых копий не добавлены.

Новый тест создаёт конфиг с синтетическими password/refresh-token/pairing-code и
настоящий старый tar с этими данными. Вызовы curl/cp/tar внутри исполняемого
экспортёра оставили бы trace; после защитного отказа trace пуст, архив и исходник
совпадают с исходными байтами. Повторный вызов также сохраняет копии.

### B133 — flock и границы платформенных доказательств

В двух standalone fixture ротации и Google Drive добавлена проверка утилиты.
Linux/POSIX без неё получает явный инфраструктурный отказ. Только Windows без
flock получает помеченную последовательную модель. Нативные проверки конкуренции,
прав и ссылок сохраняют Linux-gate, их Windows-пропуск не считается успехом.
Новая модель живёт в `tests/helpers`, не включается в пакет.

### B134 — рабочий каталог Yandex context

Все относительные shell-пути уже строились от repo. Теперь из repo запускается
и сам shell. Передача entry, UCI/HTTP-модели и переменных окружения согласована.
Unit использует настоящий `shellTestPath` с Windows-параметрами: новый путь
совпадает с файлом, старый cwd дублирует `.build/...`. Настоящий Windows не запускался.

### B135 — время и диагностика shell-стендов

В затронутых fixture POSIX сохраняет 15/20 секунд; Windows получает минимум 120
секунд. Override `SHEEPFOLD_TEST_PROCESS_TIMEOUT_MS` ограничен 1..600000 мс.
Per-file runner и production timeouts не менялись. При timeout/spawn/signal
выводится первичная причина до assertions HTTP/JSON. Обычный отрицательный exit
продукта остаётся доступным для проверки и не скрывается исключением стенда.

**Два отказа не скрыты и не помечены skip.** Старый тест ожидал `quota_unavailable`
после начала архивного прохода, теперь получает ранний `config_backup_unavailable`.
Другой ожидал успешный archive-push при отсутствующей квоте, но операция теперь
запрещена. Это ожидаемое следствие смены разрешённого поведения, однако пакет
нельзя называть «весь зелёный». Остальные старые archive-push/config-backup tests
также требуют пересмотра при подключении безопасного экспорта. Их не удаляли и
не переписывали так, чтобы представить новую блокировку доказательством старой
успешной загрузки. Непроверенные тесты не считаются прошедшими.

Первый unit-прогон имел одну ошибку проверки пробела в записи `skip:!native`;
исправлено регулярное выражение теста, gate продукта не ослаблялся. Исходный лог
сохранён вместе с окончательными результатами.

## Команды повторения

Запускать только в изолированном checkout, не выполнять production shell напрямую
на рабочем роутере.

```sh
node --test tests/runtimeProcess.test.mjs tests/cloudArchiveSafety.test.mjs tests/testCategories.test.mjs tests/changeImpact.test.mjs
node scripts/run-test-category.mjs --file maintenanceRotationRuntime.test.mjs --file adminNotificationRuntime.test.mjs --file legacyLogRuntime.test.mjs --file settingsBackup.test.mjs
node --test --test-name-pattern=push-events tests/googleDriveUploadRuntime.test.mjs
node --test --test-name-pattern=push-events tests/yandexEventsRuntime.test.mjs
```

Эти команды прошли с exit 0 в Linux. Сохранённый диагностический запуск ниже
возвращает exit 1 из-за двух старых ожиданий архивной команды:

```sh
node --test --test-name-pattern='Yandex quota setting boundary' tests/yandexContextRuntime.test.mjs
```

Обновлённая карта влияния сохраняет прямых и косвенных потребителей нового helper.
Это не отменяет необходимость их остальных проверок перед принятием кандидата.

Подключить безопасный автоматический экспорт к принятому формату и проверить
передаваемые bytes и импорт, затем осознанно обновить архивные сценарии. Повторить
Windows/Git Bash проверки, включая достижение искусственных отказов и фактическое
время процессов. После этого отдельно решать принятие в main и выпуск.

Синтаксис 11 изменённых JavaScript-модулей и двух shell-файлов (sh и BusyBox ash)
проверен без ошибок; документационный checker проверил 8 Markdown-файлов.
`git diff --check`, `git bundle verify` и `git fsck --full` прошли.
ESLint не запустился: offline npm вернул ENOTCACHED; сетевые зависимости не
устанавливались. Синтаксическая проверка не заменяет ESLint.

Настоящие облачные аккаунты, нативный UCI/libubox, физический OpenWrt, Android,
установка, SDK и Windows не проверялись. Новых облачных запросов и внешних
публикаций нет. Полный suite не выполнялся. Наличие новых unit-проверок не является
доказательством полного Windows-прогона. Безопасное восстановление из облака не

## Поставка без нового коммита

ZIP содержит полную рабочую копию кандидата r323 с этими правками, без `.git`
и без `.build`. Patch применяется **только поверх `1e9c43b`**, не поверх принятого
`bdb3a92`. Новый bundle не создаётся: без нового коммита он потерял бы изменения.
Для сохранения истории используйте исходный r323 bundle и отдельный patch.

```sh
git clone --branch main sheepfold-r323-main.bundle sheepfold-review-fixes
cd sheepfold-review-fixes
git rev-parse HEAD
# Должен быть 1e9c43bfea54aba15d7020fbdbe84ad5dc23b7c0.
git switch -c review/r323-privacy-fixtures
git apply --check ../sheepfold-r323-review-fixes.patch
git apply ../sheepfold-r323-review-fixes.patch
```

Команды не выполняют commit/push, merge или установку. Проверка применения patch
и побайтовое сравнение восстановленной рабочей копии с ZIP выполняются отдельно
в сопровождающем протоколе поставки. История исходного bundle не переписывается.
