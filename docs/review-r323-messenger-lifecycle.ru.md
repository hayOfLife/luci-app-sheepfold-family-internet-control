## Подтверждённые сценарии

| Карточка | До | После |
| --- | --- | --- |
| B147 | Реальная панель вызывает отсутствующий deps.command, до команд не доходит | Controller передаёт общий actions.execute и ensureOk |
| B148 | При отдельно предоставленном callback тест сначала сохраняет несохранённый chat ID и restart | Тест разрешён для сохранённого Telegram и не вызывает config-save/restart |
| B149 | Отправлен chat ID 123, введён 456, ответ отмечает 456 чистым | Backend остаётся 123, 456 остаётся несохранённым |
| B150 | Restart exit 1 или rejection подавляется, выводится общий успех | Сохранение и применение разделены; поздняя ошибка имеет persisted=true |

### Нельзя объединять ранний отказ с последующим побочным действием

B147 воспроизведён настоящим controller.renderBot и настоящей панелью: исключение
`deps.command is not a function`, пустая трасса команд. Для B148 прежняя панель
проверялась отдельно с предусмотренным callback. Её исходник не исправлялся, но
недостающая интеграционная зависимость была восполнена, чтобы исследовать следующий
слой. Поэтому нет утверждения, что полностью неизменённая старая страница успевала
сохранить chat ID: она останавливалась раньше.

В этом изолированном сценарии старый chat ID `100` и введённый `999` давали trace:
`messenger-save-telegram` → restart → status → check → send-test. Исправленный
код при несохранённых полях выдаёт предупреждение, не передавая ни одного из этих
действий. После явного Save обычная тестовая кнопка вызывает только send-test.

### Снимок специального saver не равен живым полям

Прежний baseline после ответа строился из collectOptions() текущего DOM, а accept
повторял чтение. Он включал и поздний ввод, и скрытые поля другого провайдера,
которых не было в аргументах backend-команды. Теперь подтверждение содержит только
active_messenger и реквизиты действительно выбранного Telegram/VK. При отключении
подтверждается только active_messenger. Слияние baseline не меняет DOM; поздние поля
остаются dirty и требуют нового явного сохранения.

Это касается и успешного ответа, и ошибки службы после записи. Поздний connected
не накладывается на изменённые реквизиты. Модель Save → late chat ID → response
показывает прежние saved=123/UI=456/dirty=false и новые saved=123/UI=456/dirty=true.
Явное второе Save сохраняет 456. Скрытая VK-правка остаётся до выбора VK и Save либо
осознанной отмены. Автоматического сохранения всех провайдеров нет.

### Успешный запуск RPC не гарантирует успешный restart

Проверяется числовой FileExecResult.code, а не только разрешение Promise. При
охваченной поздней ошибке уже успешная конфигурационная команда не объявляется
невыполненной; общий UI получает persisted/runtimeApplied и предупреждает об
обновлении службы. Синхронная и асинхронная ошибки проходят одной цепочкой.
Автоповтора нет. Неуспешный внешний messenger-check остаётся предупреждением
отдельно от записи; его частичный stdout не становится признаком connected.

Первичный источник проверен: https://openwrt.github.io/luci/jsapi/fs.js.html
(FileExecResult.code). Это сверка интерфейса, не запуск нативного rpcd.

## Как повторить

Рабочий каталог — корень распакованного кандидата. Нужны Node.js и Git; новых
npm-зависимостей, ключей, роутера и доступа к облаку этим тестам не требуется.
Успешная команда заканчивается exit 0. При отказе runner останавливается на файле;
перечисленные, но не запущенные файлы не считать прошедшими.

```sh
node scripts/run-test-category.mjs --file messengerSettingsLifecycle.test.mjs --file settingsSaveLifecycle.test.mjs --file luciCommandActions.test.mjs --file overviewFinalDecomposition.test.mjs --file frontendModules.test.mjs --file overviewSettingsExtraction.test.mjs --file telegramCommandsSync.test.mjs --file overviewLocalization.test.mjs --file testCategories.test.mjs --file changeImpact.test.mjs
node scripts/run-test-category.mjs --file cloudArchiveSafety.test.mjs
```

Для повторного узкого контроля исправлений и сохранности облачного запрета:

```sh
node scripts/run-test-category.mjs --file messengerSettingsLifecycle.test.mjs --file cloudArchiveSafety.test.mjs
```

Ожидается **39 успехов**, без пропусков. Сравнение со старым кодом требует именно
двух предыдущих модулей из каталога before архива доказательств; их нельзя
подменять модулями чистого r323, поскольку предыдущие review-правки отличаются.
SHEEPFOLD_MESSENGER_SOURCE задаёт каталог этих модулей только тесту. Ненулевой exit
сравнительного прогона ожидаем: он доказывает наличие воспроизводимых сценариев,
а не является разрешением поставить старый код на роутер.

```sh
SHEEPFOLD_MESSENGER_SOURCE=/mnt/data/sheepfold-review-next-evidence/before node --test --test-skip-pattern='Russian translations' tests/messengerSettingsLifecycle.test.mjs
```

Путь в последней команде — фактический путь текущего Linux-стенда, при распаковке
доказательств в другом месте его нужно заменить на локальный before. На Windows
синтаксис переменной отличается; нативный Windows-прогон этой поставкой не удостоверен.

Переводы: пять строк добавлены в po/ru/sheepfold.po, JSON перегенерирован командой
`python scripts/po2json.py` из корня. Геометрия UI, CSS и новые значки не менялись.
Карта direct-тестов охватывает controller/panel, общий saver и actions; существующие
workflow и исполняющие runner-скрипты не редактировались.

## Применение без выпуска

Поставка содержит полный source ZIP, совокупный patch, дополнительный delta,
отчёт, реестр и checks ZIP. SHA256SUMS проверяет эти шесть файлов.

**Выберите один вариант**, не применяйте два патча последовательно:

1. Чистая локальная копия кандидата r323 (`1e9c43b`): применить
   `sheepfold-r323-review-messenger.patch`. Он включает предыдущие review-правки.
2. Копия, где уже применён `sheepfold-r323-review-settings.patch`: применить только
   `sheepfold-r323-review-messenger-delta.patch`.

```sh
git apply --check ../sheepfold-r323-review-messenger.patch
git apply ../sheepfold-r323-review-messenger.patch
```

Для второго пути команды такие же с именем delta; до применения сохранить свою
незакоммиченную работу. Эти патчи не предназначены для прямого наложения на принятую
историческую bdb3a92. Нет нового bundle: незакоммиченные изменения он не содержит.
Патч не выполняет commit/push/установку. Полный source ZIP удобен для отдельного ревью.

## Проверка поставки

Совокупный патч наложен на отдельный чистый клон исходного bundle r323.
В другом независимом клоне последовательно применены прежний settings-патч и
текущий delta. Обе рабочие копии дают одинаковое дерево: **1078 файлов**. Их
независимые Git-экспорты совпадают с source ZIP по всем байтам и режимам файлов,
с учётом настроенных окончаний строк из .gitattributes. Патчи прошли apply --check;
новый commit не создавался, HEAD всех копий остаётся исходным r323.

Из восстановленной копии повторены **39 тестов**: 31 messenger lifecycle и восемь
защитных cloudArchiveSafety. Все прошли без отказов, пропусков и отмен; это повтор,
не прибавка к 127 уникальным сценариям. Пройдены синтаксис двух LuCI-модулей в
правильной Function-обёртке и четырёх Node-модулей, git diff --check и проверка
шести Markdown-файлов текущего прохода. Это не аудит истинности всех исторических
отчётов и не успешный ESLint: offline-зависимость линтера отсутствует.

Манифесты, точные результаты и исходники предыдущей панели входят в checks ZIP.
SHA-256 для всех шести итоговых файлов проверен после упаковки. Индексы и деревья
Git, созданные только для сравнения и экспорта, не являются принятием изменений
в main или выпуском. Версия пакета не изменена.

## Незакрытые границы

Это не общая транзакция между Save, тестовым сообщением и настройками других
процессов. Успех конфигурационной команды принимается по её действующему контракту;
секреты независимо не перечитываются. Ошибка restart диагностируется, но её причина
этим кодом не устраняется. Readback active не доказывает сохранение всех реквизитов.
Сам send-test может менять служебные метки backend; запрет касается неявных
конфигурационных save/restart из UI. Поздний ввод хранится только в памяти панели:
полный render/reset/reload может его потерять. Снимок общего подтверждения всех
специальных savers и изменение настроек уже после последней проверки остаются
отдельными задачами. Принятие кандидата и выпуск требуют отдельного решения владельца.
