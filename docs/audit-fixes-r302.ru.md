# Sheepfold r302: аудит записи RAM-журнала и фоновых копий

Дата: 10 сентября 2026 года. База: `0238869` (r301), с сохранёнными доработками владельца из `bdb3a92`.
Версия обоих роутерных пакетов: `0.1.0-302`. Все изменения локальны, в `main`; push не выполнялся.
Точная вершина результата, дерево Git и контрольные суммы поставки записаны в `delivery-verification.json` внешнего архива проверок.

## Результат и область

Исправлены три группы проблем, B76–B78. Полные карточки с причинами, альтернативами и ограничениями находятся в [реестре](bug-register.ru.md), теперь содержащем 78 карточек. Это число карточек за всю историю, не число независимых уязвимостей текущего прохода.

Проверен обычный административный RAM-журнал `/tmp/sheepfold/events.log`, прежде всего его writer `sheepfold-log`. Исправление API-чтения и очистки r301 само по себе не распространялось на запись событий. Обнаруженное поведение проверено в изолированных временных каталогах; файлы реального роутера, облачные аккаунты и пользовательские данные не использовались.

Изменены четыре производственных shell-файла (один новый), Makefile, непосредственные тесты и карта их зависимостей. Код Android, алгоритм доступа, TLS/токены/HTTP-формы, workflow и runner-скрипты не менялись. Решение D01, разделение Standard/AI Support и отсутствие автоматической выдачи интернета по просьбе ребёнка сохранены.

## B76. Writer выходил за ожидаемый каталог журнала

**Воспроизведение.** Старый writer разрешал `/tmp/*`, включая компоненты `..` и символические ссылки. Временный файл за границей каталога Sheepfold получал строку события; при этом могли меняться его права или права родительского каталога. Ошибка чтения `log_cache_path` через UCI также могла направлять событие в журнал по умолчанию вместо сообщения об отказе.

**Причина.** Проверка строки на префикс не определяет фактическую границу файлового пути. Writer и API имели две разные реализации выбора и проверки пути.

**Решение.** Добавлена общая `sheepfold-log-common`: она разделяет отсутствие опции и отказ чтения; проверяет каталог `/tmp/sheepfold`, компоненты пути, ссылки и тип конечного объекта. Writer проверяет путь до блокировки и повторно под ней; создание отсутствующих обычных подкаталогов разрешено только writer. API использует ту же библиотеку, сохраняя прежние ответы ошибок. Настоящие вложенные пути и пробелы поддерживаются.

**Почему так.** Молчаливая нормализация, замена опасного пути на другой файл или ещё одна копия проверок сохраняли бы неоднозначность. При невозможности подтвердить назначение запись отказывает. Библиотека входит в обе редакции пакета с правами 0644; hardening проверяет присутствие и синтаксис, а не игнорирует новую зависимость.

**Граница.** Это проверка согласованного файлового поведения, не защита от намеренной подмены пути другим root-процессом между проверкой и открытием. Жёсткие ссылки, mount changes и атомарный openat/O_NOFOLLOW этим не решены. Другие потребители журналов требуют самостоятельного аудита.

## B77. Неуспешное добавление выдавалось за успешную запись

**Воспроизведение.** В реальном Linux-процессе тест установил `RLIMIT_FSIZE=0` и игнорирование SIGXFSZ: `printf` получил отказ записи, файл остался пустым, но старый writer вернул 0. В других сценариях он продолжал работу после отказа chmod или использовал частичный вывод неуспешных tr/cut/date. Шумный syslog-helper загрязнял стандартный вывод.

**Причина.** Функция добавления вызывалась внутри условия; полагаться на один `set -e` было недостаточно. Последующая успешная операция скрывала статус предыдущей. Подготовка текста, времени и прав не составляла проверяемую последовательность.

**Решение.** Отдельно проверяются подготовка сообщения, получение времени, настройка закрытого каталога, права существующего файла и добавление строки. Для новых файлов действует umask 077. При отказе RAM-записи команда завершается неуспешно и не планирует облачную копию. Вывод syslog изолирован. Отказ дополнительного USB-копирования диагностируется отдельно и не отменяет уже успешный RAM-результат.

**Почему так.** Сохранённая в RAM строка и дополнительная копия — разные результаты. Возвращать успех после отказа основного добавления неверно; удалять успешную RAM-запись из-за побочного отказа тоже неверно. Проверяется сама запись, а не только наличие файла.

**Граница.** Код возврата подтверждает проверенное добавление в RAM, не fsync и не сохранность после отключения питания. При иных отказах возможна частичная добавленная строка; транзакционный откат append не введён. Все пути USB, его mount-проверка и ротация не объявлены полностью проверенными.

## B78. Фоновая облачная копия удерживала ответ и родительскую блокировку

**Воспроизведение.** Подставленный транспорт действительно запускался и ожидал управляемого барьера. Основной writer уже завершался, но вывод вызывающего процесса не закрывался либо наследуемый FD 9 продолжал держать его файловую блокировку. Поведение воспроизведено для Yandex Disk и Google Drive без обращения в сеть. Отдельный отказ создания служебного флага мог прервать команду после успешного добавления в RAM.

**Решение.** Фоновые процессы получают закрытый stdin и перенаправленные stdout/stderr на уровне всей группы команд. Они закрывают собственную копию FD 9. Планирование выполняется в отдельном subshell: его фатальный отказ редиректа не отменяет RAM-результат. Диагностика планирования также изолирована.

**Почему так.** Перенаправление только исполняемого helper оставляло оболочку с открытыми дескрипторами. Промежуточный вариант с редиректом самой shell-функции тоже оставлял сохранённую внутреннюю копию pipe — барьерный тест выявил это, окончательный вариант использует subshell. Нельзя вызывать `flock -u` в потомке вместо закрытия копии FD: это может снять ещё нужную блокировку живого родителя. Тест отдельно подтверждает, что родительская блокировка остаётся действующей до выхода родителя.

Техническая семантика наследования и снятия flock подтверждается [Linux man-pages: flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html). Основное доказательство исправления — локальные процессы и реальные flock-барьеры, не только чтение документации.

**Граница.** Гарантированная доставка, подтверждение удалённой записи, повтор после отказа транспорта, очистка зависших scheduled-флагов и атомарное резервирование одного отправителя не реализованы этим проходом. Интервал 300 секунд и opt-in облачной настройки не менялись. Отсутствие удержания FD 9 не означает аудит всех дескрипторов любого стороннего вызывающего процесса.

### Почему выбрано 25 файлов

Изменение общего runtime-fixture — добавление копирования библиотеки — требует проверки всех его непосредственных потребителей, даже если отдельные production-модули не менялись. Дополнительно выбраны чтение/запись журнала, обслуживание, UI-контракт, hardening, разделение редакций, IPK и карта отбора. Отчёты advisor сохранены: их широкая классификация критичных legacy/fixture-путей не подменяет анализ фактически изменённых функций. HTTP-формы, авторизация, Android и CI-runner не переписывались. Выборочный runner запускает перечисленные файлы отдельными процессами по принятому владельцем порядку.

### Как выполнено сравнение со старым writer

Из Git `0238869` извлечён только оригинальный `sheepfold-log`. Остальные модели и общий reader остаются текущими, поскольку сравнивается конкретный дефект writer, а не полная сборка r301. Переменная `SHEEPFOLD_WRITER_TEST_SOURCE` выбирает каталог источника только в тесте, не в установленном продукте.

Стенд переносит как `/tmp/sheepfold`, так и прежний общий разрешённый префикс `/tmp/*` внутрь своего временного каталога. Иначе нахождение стенда в `/mnt` искусственно направляло бы старый код в default, маскируя реальную проверку. Пути с `..`/пустыми компонентами не нормализуются тестом до вызова. Результат 27 отказов означает регрессионные assertions по трём группам, не 27 самостоятельных уязвимостей.

Файловые fault-команды проверяют след вызова. Сбой добавления — настоящий отказ Linux записи с RLIMIT_FSIZE; конкурентные проверки используют настоящий flock, а не строковый поиск в коде. Платформенно-специфичные случаи явно ограничены Linux и в этом запуске не пропущены. Проверка синтаксиса BusyBox не выдаётся за прохождение fault-сценариев под BusyBox applets.

## Повторение из корня репозитория

Понадобятся Node с `node:test`, Python 3, POSIX sh и flock; Linux для ссылок, прав, RLIMIT и наследования блокировки. Прямой запуск:

```sh
node scripts/run-test-category.mjs --file logWriterRuntime.test.mjs --file legacyLogRuntime.test.mjs
```

Сравнение оригинального writer (ожидается неуспех регрессионных assertions):

```sh
mkdir -p .build/r302-baseline
base=0238869
git show "$base:package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-log" > .build/r302-baseline/sheepfold-log
SHEEPFOLD_WRITER_TEST_SOURCE="$PWD/.build/r302-baseline" node --test tests/logWriterRuntime.test.mjs
```

Полный список именно выбранных 25 файлов находится в `selected-tests.json` архива проверок; runner принимает каждый через `--file`. Он не заменяется wildcard-запуском всех тестов.

```sh
python scripts/build-test-ipk.py --variant all
node scripts/checkDocumentation.mjs --git 0238869
git diff --check 0238869
```

Тестовые пакеты размещаются в `.build/ipk-output`, не в установке роутера. Скрипт `verify-packages.py` во внешнем архиве показывает сверку распакованных вариантов и установочных проверок; для повторения на другой машине нужно заменить его явно указанный путь к рабочему клону. Это вспомогательное доказательство прохода, не новый канонический SDK-builder.

## Журналы, поставка и ограничения

Архив проверок содержит окончательные и неуспешные промежуточные запуски, 34-сценарное сравнение, список выбранных файлов, патч r301→r302, накопительный патч после принятого `bdb3a92`, тестовые IPK и проверку восстановления. Ранние журналы с меньшим числом сценариев сохраняются как история разработки и не являются окончательным итогом. Текущие итоги: `selected-summary.json`, `writer-final.log`, `writer-baseline.log`, `package-verification.json` и `delivery-verification.json`.

Настоящий OpenWrt UCI, uhttpd под нагрузкой, физический роутер/Android, внешние USB/облака и отключение питания не проверялись. SDK/Android-сборки и GitHub Actions не запускались. Исторические CI-успехи принятой r297 не приписываются r302.

R13 остаётся открытой: остальные потребители логов, полнота маскирования, объём ответа, root-races, облачные флаги/повторы, архивирование и безопасное обслуживание. r302 — локально проверенный интеграционный снимок, не подтверждённый стабильный релиз.
