## B154: подготовка не подтверждала исправность и принадлежность снимков

Предыдущий код создавал каталог `transaction.PID`. Если такой каталог уже существовал,
`mkdir` отказывал, но обработчик завершения удалял его, считая своим. Проверка
создаёт прежний каталог в launcher, затем выполняет `exec sh`: PID сохраняется.
Старый обработчик удаляет `old.before`; новый сохраняет его и использует другой
уникальный каталог. Это не модель удаления: состояние файлов проверяется реально.

Вторая часть той же стадии — результат `cp -p` не сравнивался с оригиналом, а ошибка
установки прав общего каталога подавлялась. При искусственном успешном копировании
неправильных байтов старый обработчик переходил к UCI set/commit. Исправленный код
проверяет копирование и `cmp -s`, подтверждает закрытый каталог, различает отсутствие
файла и существующий неправильный тип, отказывает на конфигурационной symlink.

Теперь `mktemp -d` создаёт отдельный каталог, и лишь **успешно завершённый** вызов
даёт обработчику право его удалить. Если неуспешный mktemp печатает чужой путь,
данные по этому пути остаются нетронутыми. До записи подтверждаются оба снимка и
их state-маркеры. Каталог имеет права 0700; `cp -p` сохраняет метаданные исходных
конфигов внутри закрытого каталога. Это не шифрование локальной страховочной копии.

При отказе подготовки возвращаются exit **4**, `status=error` и
`error=time_snapshot_failed`. Команда не вызывает изменение/commit UCI и не
перезапускает NTP. Ошибка копирования с частичным выходным файлом также очищает
только собственные временные данные.

**Почему так:** уникальный каталог решает принадлежность, а побайтовое сравнение —
целостность. Только более точное время имени, PID или проверка размера не решают
обе задачи. Предварительное удаление существующего каталога могло бы уничтожить
единственную оставшуюся аварийную копию.

## B155: неудачный откат повреждал файл и удалял исходную копию

Настоящий скрипт выполнялся с моделью UCI, записывающей те же реальные конфигурационные
файлы, из которых берутся снимки. В модели ошибка второго commit возникает после
его записи. При восстановлении system подставленный `cp` записывает частичный
результат и завершает работу с ошибкой. След подставленной команды обязателен в тесте.

| Наблюдение | Предыдущий кандидат | Исправленный кандидат |
| --- | --- | --- |
| Файл system после отказа восстановления | `BROKEN RECOVERY` | Новая записанная конфигурация, не испорченная частичным cp |
| Второй файл sheepfold | Удачно восстановлен | Удачно восстановлен |
| Исходные снимки | Удалены | Оба сохранены в закрытом каталоге |
| Сообщение | Заранее обещает восстановление прежней конфигурации | Явно сообщает о неполном восстановлении |
| Exit | 4 | 6 |

Это **не заявление, что при неудачном откате восстановлены старые настройки**.
В этом сценарии система остаётся в смешанном состоянии, но не теряет исходный
снимок и не получает дополнительного повреждения рабочего файла.

Для присутствовавшего конфига восстановление сначала создаёт соседний закрытый
временный каталог на файловой системе получателя. Проверяются `cp -p`, `cmp -s`
и тип получателя, затем выполняется `mv -fT`. Копировать прямо поверх действующего
файла больше не требуется. `-T` не разрешает превратить возникший каталог в новое
место назначения. При первоначальном отсутствии файла удаляется только допустимый
конечный файл; ошибка удаления также означает неуспешное восстановление.

Отказ первого файла не прекращает попытку восстановить второй, если его commit
уже начинался. Но снимки удаляются только после общего успеха всех необходимых
восстановлений. Прежнее сообщение «было восстановлено» до выполнения rollback
удалено. Вместо него до отката говорится о предстоящей попытке.

Отдельно сужена область отката: до начала commit выполняется лишь private staging,
поэтому полный исходный файл в этой фазе не восстанавливается. Если первая попытка
commit не удалась, а commit второй конфигурации не вызывался, второй файл также не
перезаписывается. Два теста вносят чужое новое значение на этих границах и проверяют,
что оно сохраняется. **Гонки после начала commit и с другими writers этим не закрыты.**

### Точный контракт результата

| Ситуация | Exit / поля | Значение |
| --- | --- | --- |
| Подготовка снимка отказала | 4 / `time_snapshot_failed` | Новая запись UCI не начиналась |
| Commit/readback отказал, необходимые файлы восстановлены | 4 / `time_save_failed`, `config_files_restored=1` | Восстановлены файлы, не весь runtime/общая pending-очередь |
| Хотя бы один необходимый файл не восстановлен | 6 / `time_rollback_failed`, `config_files_restored=0`, `recovery_required=1` | Снимки сохранены, нужно проверить фактическую конфигурацию |
| Обработанный TERM во время commit | 143, поля отражают результат отката | Код сигнала сохраняется |
| Настройки подтверждены, restart NTP отказал | 5 / прежний `ntp_restart_failed`, `persisted=1`, `runtime_applied=0` | Контракт B152 сохранён |

При неудачном восстановлении путь к сохранённым снимкам выдаётся в stderr, но их
содержимое не печатается. UI признаёт новый специальный результат только при
точном exit 6 и всех предусмотренных полях. Он **не устанавливает persisted=true**,
не принимает черновик как сохранённый и не повторяет запись автоматически.
Родитель получает предупреждение:

> Не удалось полностью восстановить настройки времени. Проверьте настройки роутера и сохранённые аварийные копии перед повторным сохранением.

Строка добавлена в RU `.po`, JSON перегенерирован штатным `scripts/po2json.py`.
Поддельные/частичные маркеры с exit 4, 5 или 124 не принимаются за этот контракт.
Связанный тест передаёт реальный отказ helper через `sheepfold-luci-action`,
`core/backend/actions` и обработчик ошибки time-модуля — не только через успешный
callback, подставленный напрямую.

**Почему так:** одной проверки `cp` недостаточно, пока запись идёт поверх оригинала.
Одного сообщения об ошибке недостаточно, пока cleanup удаляет снимки. Общая
транзакция system/sheepfold, автоматический повтор или общий `uci revert` не
добавлены: они могли бы затронуть посторонние изменения и требуют отдельного решения.

## B156: отказ уборки отменял ответ и пропускал restart после записи

В старом коде `TRANSACTION_ACTIVE` уже становился 0, затем выполнялся безусловный
`rm -rf`. Если удаление отказывало, `set -e` завершал команду прежде перезапуска NTP
и ответа. Тест подтвердил сохранённые новые значения, пустой stdout, exit 1 и
отсутствие вызова init. Это реальный путь с искусственно отказавшим удалением,
а не поиск текстовой конструкции.

Теперь удаление собственных временных данных вынесено в контролируемую уборку.
Неудача даёт предупреждение и оставляет закрытый каталог, но не прерывает дальнейший
restart и не меняет подтверждённую запись на неизвестный результат. При успешном
restart ответ остаётся `status=ok`; при его отказе сохраняется точный exit 5 B152.

**Почему так:** повторная запись UCI или восстановление старых настроек не исправят
отказ удаления каталога. Считать уборку несущественной и молчать тоже неправильно:
остаток может занимать RAM и содержать секреты. Предупреждение не является
автоматической безопасной очисткой или гарантией, что каталог переживёт reboot.

## Как повторить

Рабочий каталог — корень **отдельной копии кандидата**, не действующего роутера.
Нужны Node.js, sh (Git Bash для Windows), awk, cp, cmp, mv, mktemp; на Linux —
настоящий flock. В Windows запуск ещё не выполнен. Тесты создают только синтетические
файлы в `.build/time-recovery` и удаляют их после проверки. Не запускайте production
`time-control save` напрямую на рабочем роутере ради воспроизведения.

```sh
node scripts/run-test-category.mjs --file timeTransactionRecovery.test.mjs --file timeSettingsLifecycle.test.mjs --file timeAndDetectionSetup.test.mjs --file settingsSaveLifecycle.test.mjs --file luciCommandActions.test.mjs --file portableShellAndStatus.test.mjs --file overviewSettingsExtraction.test.mjs --file overviewFinalRuntime.test.mjs --file frontendModules.test.mjs --file overviewLocalization.test.mjs --file cloudArchiveSafety.test.mjs --file changeImpact.test.mjs --file testCategories.test.mjs --file runtimeProcess.test.mjs
```

Ожидается exit 0, 200 тестов. Runner останавливается при ошибке файла; ещё не
запущенные файлы нельзя считать прошедшими. Для быстрого повтора:

```sh
node scripts/run-test-category.mjs --file timeTransactionRecovery.test.mjs --file cloudArchiveSafety.test.mjs
```

Ожидается 41 успех, это повтор 33+8, не новые сценарии. Для отрицательного сравнения
в Linux распакуйте `before/` из checks рядом с копией и задайте фактический путь:

```sh
SHEEPFOLD_TIME_RECOVERY_SOURCE=../evidence/before node --test tests/timeTransactionRecovery.test.mjs
```

В `before/` должны быть прежние `sheepfold-time-control`, `time.js`, `ru.json`.
Ожидается exit 1 с 7 успехами и 26 отказами; это воспроизведение прежних проблем,
не тест готовности текущего кандидата. Синтаксис переменной в PowerShell другой.

## Существенные ограничения

- Не выполнены нативные UCI/OpenWrt, физический NTP/роутер, Windows/Git Bash,
  браузер LuCI, Android, облака, SDK и установка. Часы хоста не изменялись.
- Две конфигурации сохраняются/восстанавливаются последовательно. Сбой может
  оставить смешанное состояние. Сохранение снимков не означает успешного отката.
- Общая UCI pending-очередь и другие session savedirs не откатываются. `-t`/`-p`
  не считаются доказательством полной изоляции. Первичные исходники
  [uci/delta.c](https://lxr.openwrt.org/source/uci/delta.c) показывают отдельный
  поиск/сохранение delta; [uci/file.c](https://lxr.openwrt.org/source/uci/file.c)
  — запись конфигурационного файла. Их чтение не является запуском libuci.
- После начала commit другой writer ещё может изменить файлы; полный rollback
  способен затронуть такое изменение. Отложенная до commit активация и отдельные
  flags устраняют только проверенные более ранние случаи.
- SIGKILL, потеря питания и неисправность носителя не позволяют гарантировать
  cleanup или сохранность RAM-снимков. Обработанный TERM проверен отдельно.
- Автоматической уборки оставленных аварийных копий, квоты RAM, мастер-процедуры
  ручного восстановления и fsync/долговечности после reboot не добавлено.
- Getters времени всё ещё подавляют отдельные ошибки чтения, итоговый readback
  проверяет не все поля. Эти отдельные границы не объявлены исправленными.
- Успех restart не доказывает синхронизацию часов. Права и порядок действующего
  firewall не менялись. Безопасный облачный экспорт/restore по-прежнему не подключены.
- ESLint недоступен в локальном кэше. Проверка синтаксиса не заменяет линтер.
