# Доступ к Sheepfold из разных сегментов домашней сети

<!-- §homen01 -->
<!-- §pairux1 -->

Статус документа: реализованный ограниченный режим v1 и план последующих расширений.
v1 установлен на тестовый OpenWrt: проверены firewall reload, отключение допуска,
изолированный API и работа физического parent APK в LAN.
Полная живая проверка смены Wi-Fi остаётся отдельным обязательным шагом.
Наличие документа не разрешает автоматически включать вход с WAN.

**Приоритет текущей задачи, уточнённый владельцем 31.08.2026:** родительский APK должен
связываться со Sheepfold из основной домашней сети. Это задача доступа к приложению,
не изменения места ограничения интернета. Главный Huawei/Xiaomi остаётся главным:
не переводить его в мост, не переносить DHCP, не перестраивать маршруты семейного
трафика и не требовать OpenWrt на всех роутерах ради этого сценария. Разделы про AP,
детский APK и satellite ниже являются отдельными вариантами/будущим расширением,
не обязательными шагами текущего исправления.

## Что реализовано в коде v1

**Сверка main от 10.10.2026:** обсуждённое с владельцем объединение сетевых профилей
одного родительского телефона пока отсутствует в этой версии. `sheepfold-token-common`
сравнивает наблюдаемый MAC с MAC записи токена; это не готовое хранилище aliases.
Согласованное направление остаётся задачей: новое подтверждённое подключение с ранее
выданным credential должно дополнять одну логическую карточку, а не создавать вторую;
IP/last seen преимущественно хранятся в RAM. Перед реализацией нужны отдельные проверки
отзыва, подмены MAC, сетевого источника и карантина. Не удалять проверку источника
в текущем helper под видом исправления документации и не обещать работу при смене MAC.

Изменения 31.08.2026: router r286, parent APK 0.1.61 (62). Режим выключен по умолчанию,
только для parent APK и прямого IPv4-сегмента на логическом интерфейсе `wan` с протоколом
`dhcp` или `static`. Произвольные VLAN, NAT relay, VPN и child APK не добавлены.
`/pair` и `/ai-assistant` также не открываются на upstream в v1: выдача новой привязки
остаётся только в основной LAN, а AI-канал требует отдельного пересмотра ролевой границы.

| Участок | Текущее поведение | Последствие |
|---|---|---|
| `LocalRouterDiscovery.kt` | Первичный поиск всё ещё проверяет только шлюз | Первое сопряжение выполняют на Wi-Fi Sheepfold; обход подсети и multicast не нужны для v1 |
| `HomeRouterEndpoints.kt`, `RouterAdminClient.kt` | Из успешного pinned HTTPS-ответа сохраняют два адреса, предпочитают адрес текущей подсети | Переход на основной Wi-Fi не требует новой привязки при неизменном MAC телефона |
| `RouterEndpointRecovery.kt` | Резервное чтение discovery меняет порт на прежнем host; постоянное сохранение только после успешного административного запроса | Не сохраняет непроверенный адрес после одного discovery |
| Init-скрипт | uhttpd использует `/tmp/sheepfold/api-www`, directory listing отключён | В отдельном root только API CGI и well-known JSON, без LuCI и чужих CGI |
| `sheepfold-home-network`, общий firewall helper | Явно подтверждённый сетевой контекст разрешает только вход TCP API на конкретном WAN-устройстве, адресе и префиксе | Нет изменения default policy, forwarding, DHCP, Podkop или главного роутера |

Живые маршруты подтвердили `192.168.4.0/24` на `br-lan`, `192.168.2.0/24` на `wan`
с адресом `192.168.2.179` и шлюзом `192.168.2.1`. На момент проверки телефон уже был
в `192.168.4.0/24`; его Wi-Fi не переключали, прежнюю неудачную попытку не воспроизводили.
Не утверждать на этом основании, что проверен будущий multi-router сценарий.

Для повторной диагностики использовать SSH-профиль из
[живого runbook](live-router-automation.ru.md): read-only команды `ip -4 route`,
`nft list chain inet fw4 input`, `nft list chain inet fw4 input_wan` и
`nft list chain inet fw4 sheepfold_input_guard`; на выбранном телефоне
`adb -s PHONE_SERIAL shell ip -4 route`. Проверять фактический upstream-адрес заново:
DHCP может изменить его. Отсутствие default route в выводе Android само по себе не
означает отсутствие интернета: Android использует отдельные таблицы маршрутов.

### Включение v1

1. В LuCI открыть «Настройки → Интеграция → Родительское приложение в основной домашней сети».
2. Проверить показанные адреса Sheepfold и главного роутера. Выбрать разрешение только
   если WAN-кабель действительно подключён к своей домашней сети, затем нажать общую кнопку сохранения.
3. Открыть уже привязанный parent APK через Wi-Fi Sheepfold и обновить данные: успешный
   `/devices` или другой защищённый ответ сохранит адрес основной сети.
4. Перейти на основной Wi-Fi. На обеих сетях должен использоваться MAC устройства,
   не разные случайные MAC. Backend продолжает сверять реальный источник с привязкой токена.
5. Для отмены выбрать «Выключено» и сохранить. При смене upstream IP, префикса, интерфейса
   или шлюза повторить явное подтверждение. Желательно закрепить адрес Sheepfold в DHCP главного роутера вручную.

Нельзя исправлять неудачу HTTP fallback, сбросом токена при тайм-ауте, открытием LuCI/SSH
на WAN или автоматическим переносом админских прав между разными MAC.

### Данные и алгоритм v1

UCI: `config home_network 'home_network_global'`, `enabled=0` по умолчанию.
При сохранении `enabled=1` helper заново читает netifd и сравнивает `candidate` с тем,
который LuCI показал перед сохранением. `fingerprint` хранит SHA-256 от
`wan|l3_device|IPv4/prefix|gateway IPv4|gateway MAC`. Это контроль неизменности контекста,
не криптографическое доказательство доверия шлюзу. ARP/MAC можно подделать; основная
авторизация всё ещё Bearer + TLS/SPKI. Публичный адрес, CGNAT, пустой ARP шлюза и слишком
широкий префикс отвергаются. Пакетное обновление сохраняет выбор; импорт любой резервной
копии выключает дополнительный допуск и требует нового согласия.

`home-network-status` возвращает JSON: `state=available|trusted|changed|unavailable`,
`enabled`, `address`, `prefix`, `gateway`, `candidate`. `trusted` означает совпадение
подтверждённого контекста, не доказательство сетевой доступности с телефона.
Сохранение выполняет только `home-network-configure 0|1 candidate` через защищённый
LuCI command layer. Используются общий admin-config lock и отдельная очередь UCI.
Ошибка применения firewall переводит настройку в `enabled=0`.

При обычной синхронизации r289 отказ доступного `sheepfold-home-network rules` не
принимается за выключение функции: sync завершается ошибкой до нового nft batch.
Успешная выдача должна начинаться с `flush chain inet fw4 sheepfold_home_input`;
пустая/неполная выдача отклоняется. Явный успешный flush-only для отключённой функции
остаётся допустимым. Это не гарантирует сохранность старых правил при внешнем fw4
reload и не означает применение новых настроек. Подробности и fixture-проверки B26:
[реестр ошибок](bug-register.ru.md).

Вход API после rate limit проверяет маршрут источника: основной LAN разрешён по
`lan_firewall_zones`; для дополнительной сети требуется подтверждённый контекст,
источник в его префиксе и neighbour MAC именно на этом интерфейсе, отличный от MAC шлюза.
Адрес шлюза и собственный адрес роутера отвергаются. Детские `/client-status`,
`/access-request`, `/sim-report`, `/wifi-network-report` на дополнительном сегменте запрещены.
Используется явный allowlist parent API paths; новый endpoint не открывается автоматически.
Это не универсальный детектор NAT: неизвестный посредник может иметь собственный MAC.
Поэтому upstream не выдаёт новые токены, а для существующего токена дополнительно
обязателен ранее привязанный реальный MAC телефона.
Ошибка `403 home_network_not_allowed` не удаляет токен Android.
Parent `0.1.61` также сохраняет привязку при явном `device_source_mismatch`, даже если
статус ответа 401: это отказ источнику, не отзыв токена. Запрос остаётся запрещённым;
автопереноса прав на другой MAC нет. Остальные 401, отзыв и смена TLS обрабатываются
по прежней строгой политике.

После успешной аутентификации CGI выдаёт `X-Sheepfold-Home-Endpoints`, CSV из локальных
HTTPS API URL без секретов: первый IPv4 `lan` и текущий доверенный `wan`.
APK принимает только полные RFC1918 IPv4 URL с портом 1–65535 и точным API path,
без userinfo/query/fragment, не более 4 адресов и 1024 символов. Список хранится только
для совпадающих токена, device ID и TLS-идентичности; новое сопряжение и отзыв очищают его.
Текущая подсеть Android влияет на порядок попыток, но не отменяет SPKI-проверку.
Автоповтор разрешён лишь для GET при connect/no-route/timeout/404. POST/PUT/DELETE/PATCH
после ошибки не повторяются по другому адресу: неизвестно, успел ли роутер выполнить команду.

### Владение runtime и стоимость

| Файл/компонент | Зачем нужен именно здесь |
|---|---|
| `sheepfold-home-network` | Единственная проверка сетевого контекста, scoped rules и endpoint list; не устанавливает пакеты и не меняет маршруты |
| `sheepfold-firewall` | Применяет `sheepfold_home_input` атомарно вместе с management block sets, чтобы reload не создавал обход чёрного списка устройств |
| `sheepfold-home-firewall` | Штатный fw4 script include вызывает принудительное восстановление sets; пропускает вложенный reload уже выполняющегося firewall helper, чтобы не ждать собственный lock |
| `90-sheepfold-home-network` в `hotplug.d/iface` | На событиях `wan` обновляет только firewall; не перезапускает тяжёлую службу и не создаёт таймер |
| Init `start/stop` | Создаёт изолированный RAM-root и маркер работающего API, снимает допуск при остановке |
| `HomeRouterEndpoints.kt` | Чистые ограничения адресов, порядок по текущей подсети и политика безопасных повторов |

Дополнительных библиотек, сканера LAN, VPN, приложения на главном роутере и фонового
таймера нет. Обычный firewall sync также сверяет контекст; без изменений не пишет nft.
Все runtime-файлы находятся в RAM. Во flash пишутся только настройки при явном сохранении.
SDK Standard APK на этом проходе: r285 = 427794 байта, r286 = 439368 байт,
разница 11574 байта (около 11,3 КиБ сжатого пакета). Это не замер потребления RAM/CPU.
На OpenWrt `jshn.sh` использует unset-переменные, поэтому этот helper применяет `set -e`
и явную валидацию входов, а не несовместимый с библиотекой `set -u`.
Script include следует [штатному контракту fw4](https://openwrt.org/docs/guide-user/firewall/firewall_configuration#includes_2203_and_later_with_fw4).

Из корня репозитория, в PowerShell с Git Bash в PATH:

```powershell
node --test tests/homeNetworkAccess.test.mjs tests/settingsBackup.test.mjs tests/firewallDomainPolicyRuntime.test.mjs
```

Исполняемый CGI-тест подменяет только внешние helpers: отказ source gate не доходит до
авторизации/команды, токен остаётся обязательным, endpoint header появляется лишь после
успеха. Это не проверка реального HTTP listener. Карта `quality:plan` считает отдельные
правки home helper, hotplug и Android endpoint store критичными и требует профильных
`access`/`security`/`android` проверок плюс перечисленных ниже живых сценариев.

тестового роутера. В основной сети `homeExpectedHost` заменить на его WAN IPv4; при
возврате на Wi-Fi Sheepfold вернуть LAN IPv4. Домашний доступ должен быть явно включён,
а MAC телефона совпадать с привязкой. Ожидается `OK (1 test)`, без skips, за 120 секунд.
Gate читает router-info и устройства, проверяет сохранённый endpoint production-клиента,
прежние токен/SPKI, 401 без токена, отказ чужому TLS pin и отсутствие LuCI/чужого CGI.
На upstream дополнительно ожидает 403 для детского статуса, SIM-report и нового pairing.
POST в этих двух проверках не содержит данных и обязан быть отклонён до handler.
Тест не переключает Wi-Fi, не пишет UCI, не создаёт токены; endpoint cache может обновиться
штатным клиентом. При 401 с сохранённым токеном сначала проверить MAC телефона, а не стирать
привязку. Тест намеренно останавливается до production client при таком отказе.
Не запускать этот класс вместе с clean-install tests и не обходить отказ TLS/источника.

## Цель

Родительское и детское Android-приложения должны находить домашний Sheepfold и подключаться к нему, даже если телефон подключён не к тому роутеру или точке доступа, на которой установлен Sheepfold.

Под словами «из любого места домашней сети» понимаются только явно доверенные локальные сегменты владельца. Гостевая сеть, сеть провайдера, публичный WAN, CGNAT, VPN неизвестного происхождения и интернет домашней сетью автоматически не считаются.

Пример целевой схемы:

```text
Телефон родителя: 192.168.2.45
        |
        | Wi-Fi
        v
Основной роутер: 192.168.2.1
        |
        | LAN, адрес дочернего роутера 192.168.2.179
        v
Дочерний OpenWrt с Sheepfold
  upstream: 192.168.2.179
  internal: 192.168.4.1
  API: HTTPS 5201
```

Телефон обращается к `https://192.168.2.179:5201`, не к недоступному ему адресу `192.168.4.1`.

## Принятое решение по QR

Сопряжение остаётся одношаговым:

1. Владелец открывает настройки администратора в аутентифицированном LuCI.
2. Backend создаёт короткоживущий одноразовый код.
3. LuCI показывает QR и заметное предупреждение не показывать и не пересылать его.
4. Первый телефон, успешно предъявивший код по закреплённому HTTPS-соединению, получает административный credential.
5. Backend атомарно сжигает код и больше никогда его не принимает.

Второй проверочный код на телефоне и в LuCI намеренно не вводится. Он уменьшает риск кражи первого использования, но добавляет ещё один непонятный шаг в основной пользовательский сценарий. Для домашней доверенной сети принят другой баланс: короткий срок действия, одноразовость, rate limit, SPKI pinning, понятное предупреждение и быстрый отзыв устройства.

Остающийся риск описывается честно: человек, получивший фотографию действующего QR, может попытаться использовать его первым. Одноразовость защищает от повторного применения, но не от такой гонки. Поэтому QR нельзя показывать, пересылать или оставлять открытым без необходимости.

Это решение следует пересмотреть только при подтверждённых злоупотреблениях или появлении столь же простого для родителя способа проверки устройства.

## Варианты домашних топологий

### Sheepfold является шлюзом телефона

Телефон и Sheepfold находятся в одной LAN. Это основной существующий сценарий. IP и MAC телефона доступны через DHCP/neighbour, а QR содержит адрес текущего роутера.

### Sheepfold установлен на дочернем роутере, телефон находится выше него

Это схема `192.168.2.x -> 192.168.2.179`. Требуется разрешить строго ограниченный вход к Sheepfold API на upstream-интерфейсе дочернего роутера.

Если оба устройства находятся в одном L2-сегменте, Sheepfold может увидеть реальный per-network MAC телефона. Если вместо него виден MAC основного шлюза, сопряжение нельзя считать привязанным к физическому телефону.

### Телефон находится за дочерним роутером, Sheepfold установлен выше

Обычный исходящий HTTPS-запрос чаще всего уже проходит без проброса портов. Проблема появляется из-за NAT: Sheepfold видит IP и MAC дочернего роутера, а не телефона.

Простой TCP-проброс не исправляет идентификацию. Он также показывает backend адрес relay-устройства. Для полноценной поддержки этого сценария потребуется криптографическая идентичность Android-приложения либо ограниченный Sheepfold satellite-agent.

### Несколько точек доступа работают мостом или mesh

Если точки находятся в одной L2-сети и не выполняют NAT, отдельный relay не нужен. Приложение использует любой доступный адрес Sheepfold, а переход между точками не создаёт новое административное устройство.

### Маршрутизируемые VLAN и гостевые сети

Они запрещены по умолчанию. Владелец должен явно добавить доверенный сегмент. Гостевой VLAN не следует делать доверенным ради удобства обнаружения.

### Интернет и публичный WAN

Прямой доступ запрещён. Sheepfold не открывает API через UPnP, NAT-PMP, PCP, автоматический port forwarding или правило `WAN -> 5201`. Удалённые короткие команды и уведомления остаются задачей отдельно настроенного мессенджера либо будущего необязательного family message relay (§mrelay1).

Family message relay не делает домашний API публичным: роутер сам устанавливает исходящее HTTPS-соединение к отдельному relay endpoint на `443`, а локальный pinned-HTTPS обмен продолжает работать независимо от доступности сервера. Полный Android API, LuCI, SSH и домашняя подсеть через relay не маршрутизируются. Точные параметры: [`android-router-message-relay.ru.md`](android-router-message-relay.ru.md).

## Обязательные границы безопасности

### Отдельный web root

В v1 дополнительный uhttpd использует отдельный RAM-root с двумя разрешёнными путями:

```text
/.well-known/sheepfold.json
/cgi-bin/sheepfold-api
```

На этом listener не должны быть доступны:

- `/cgi-bin/luci`;
- SSH;
- CGI других LuCI-приложений;
- файлы конфигурации;
- журналы;
- резервные копии;
- технические helpers.

Проверка отсутствия LuCI на API-порту является блокирующим тестом релиза.

### Явно доверенные сети

RFC1918-адрес сам по себе не доказывает домашнюю сеть: такой адрес бывает в гостинице, офисе и чужой Wi-Fi-сети.

Для будущего реестра нескольких сетей планируются состояния (не путать с JSON v1 выше):

- `detected` - обнаружена, но не разрешена;
- `trusted` - явно подтверждена владельцем;
- `changed` - интерфейс, адрес или префикс неожиданно изменился;
- `disabled` - доступ закрыт.

Автоматически разрешается только основной LAN Sheepfold. Upstream и дополнительные VLAN требуют явного включения в LuCI.

Если адрес стал публичным, попал в CGNAT `100.64.0.0/10`, потерял ожидаемый префикс или интерфейс сменил роль, правило закрывается до решения владельца.

### Firewall

Целевая расширенная версия firewall manager должна (v1 использует одну именованную цепочку):

1. Создавать отдельный именованный nftables set доверенных интерфейсов и источников.
2. Разрешать только TCP на текущий Sheepfold API-порт.
3. Не менять default policy зоны, forwarding, DNS и правила Podkop/AdGuard Home.
4. Не открывать IPv6 без отдельной реализации и тестов.
5. Атомарно переносить правило при смене API-порта.
6. Удалять правило при выключении функции, удалении пакета или ошибке listener.
7. После сопряжения по возможности сужать разрешение до известных административных устройств.

MAC в firewall является дополнительным ограничением, а не основным паролем: MAC можно подменить. Постоянная авторизация всё равно требует Android credential и закреплённый SPKI.

### Проверка прямой L2-доступности

До MAC-bound сопряжения backend проверяет:

- source IP находится в префиксе разрешённого интерфейса;
- MAC найден в neighbour/ARP на том же интерфейсе;
- найденный MAC не совпадает с MAC default gateway;
- запрос не пришёл через NAT или неизвестный routed hop;
- устройство отсутствует в чёрном списке устройств.

Если реальный MAC телефона не виден, текущий MAC-bound режим отказывает безопасно. Нельзя незаметно привязать credential к MAC шлюза.

### HTTPS

- Родительский `SF2` QR содержит SHA-256 SPKI.
- Android проверяет SPKI до отправки логина и одноразового кода.
- HTTP fallback запрещён.
- Публичный IP, loopback и multicast запрещены.
- Смена SPKI требует нового сопряжения.
- Тайм-аут, временный offline и `5xx` не удаляют постоянный credential.
- Доступ через дополнительный домашний адрес не отменяет TLS pinning.

### Rate limit и защита ресурсов

Помимо лимита на один IP/MAC необходим общий лимит публичных запросов. Иначе клиент может менять адреса и создавать много временных файлов в `/tmp`.

Backend ограничивает:

- число pairing-попыток на устройство;
- общее число pairing-попыток за окно времени;
- число файлов rate-limit;
- срок хранения устаревших записей;
- частоту предупреждений в журнале.

Секреты, QR payload, одноразовый код и Bearer в журнал не попадают.

## Будущий публичный список адресов

Это план, не JSON работающего v1: сейчас список идёт только в заголовке защищённого
ответа. В будущем минимальный публичный discovery-документ можно расширить:

```json
{
  "service": "sheepfold",
  "routerId": "local-random-id",
  "appPort": 5201,
  "endpoints": [
    {
      "host": "192.168.4.1",
      "port": 5201,
      "scope": "lan",
      "priority": 100,
      "roles": ["parent", "child"],
      "spkiSha256": "64-hex"
    },
    {
      "host": "192.168.2.179",
      "port": 5201,
      "scope": "trusted-upstream",
      "priority": 80,
      "roles": ["parent"],
      "spkiSha256": "64-hex"
    }
  ]
}
```

Этот документ не содержит:

- токенов;
- временных паролей;
- имён администраторов;
- MAC и названий устройств;
- SSID и паролей Wi-Fi;
- полной таблицы маршрутов.

Список endpoint сам по себе не является разрешением. Родительское приложение принимает кандидат только после совпадения сохранённого SPKI. Детское приложение после первого доверенного соединения принимает новые адреса только от уже закреплённого Sheepfold.

Публичный ответ должен сообщать только адреса, предназначенные для текущего доверенного сегмента. Не нужно раскрывать клиенту гостиничной или гостевой сети всю домашнюю топологию.

## Обнаружение сервера

### Первый этап

1. QR содержит один адрес, который должен быть доступен сканирующему телефону, и SPKI.
2. LuCI показывает выбор адреса, если у Sheepfold несколько доверенных интерфейсов.
3. После первого защищённого соединения Android получает и сохраняет список дополнительных endpoint.
4. При недоступности основного адреса приложение перебирает только сохранённые кандидаты с тем же SPKI.

Полный список не следует помещать в QR: он увеличит матрицу и вернёт уже известную проблему переполнения QR.

### Второй этап

Для Sheepfold, который не является шлюзом телефона, добавить локальное обнаружение:

- mDNS/Android NSD как основной кандидат для одной L2-сети;
- необязательное локальное DNS-имя `sheepfold.home.arpa`, если Sheepfold управляет DNS;
- ограниченный UDP discovery только после отдельного security review.

Сканирование всех адресов `/24` не является штатным механизмом: оно медленнее, расходует батарею, создаёт лишний трафик и плохо работает в больших сетях.

Любое объявление считается подсказкой, а не доказательством. Решение принимает HTTPS-проверка закреплённого ключа.

## Нужен ли отдельный пробросчик портов

### Обычные роутеры без OpenWrt

Дополнение владельца 31.08.2026: небольшой вспомогательный пакет на других OpenWrt
допустим, если он действительно нужен. Это не делает satellite обязательным для
каждой точки доступа и не разрешает открывать управление в интернет. На штатную
прошивку Huawei/Xiaomi нельзя рассчитывать устанавливать OpenWrt-пакеты.

Для домашней сети предусмотрены три разных случая:

1. **Существующая схема владельца.** Главный роутер остаётся `192.168.2.1`, телефон
   и upstream Sheepfold `192.168.2.179` находятся в его LAN. Если нет гостевой/client
   isolation, изменение главного роутера для обычного HTTPS к этому соседу не требуется.
   Требуется реализовать изолированный API, доверенный сегмент и адреса в APK на стороне
   Sheepfold. Это не открытие входящего порта со стороны провайдера.
2. **Одна сеть через точки доступа.** Отдельный возможный вариант, не требование для
   работы родительского APK и не предложение перестраивать текущую сеть:
   `интернет -> OpenWrt с Sheepfold -> Huawei/Xiaomi в AP/bridge -> телефоны`.
   AP/bridge здесь означает Wi-Fi-точку доступа без отдельного NAT для клиентов, не
   проброс публичного IP провайдера. Роутер Sheepfold выдаёт клиентские адреса и видит
   их сетевую идентичность; отдельная программа на точках доступа обычно не нужна.
3. **Несколько сетей с NAT.** Роутер прячет клиентов за своим адресом. Открытие порта,
   статический маршрут или объявление адреса Sheepfold сами по себе не возвращают
   личность каждого телефона. Нужен описанный ниже device credential/satellite либо
   переход дополнительного роутера в AP. Не обещать поддержку только по факту успешного TCP.

По официальным материалам, проверенным 31.08.2026:

| Модель на штатной прошивке | Подтверждённая возможность | Ограничение проверки |
|---|---|---|
| Huawei WiFi BE3 Pro | Проводной мост, настройка «Интернет -> Мост», без обязательного Huawei Mesh на основном роутере: [инструкция Huawei](https://consumer.huawei.com/ru/support/content/ru-ru15806362/) | Модель указана в списке применимости; конкретная региональная прошивка и физический экземпляр не проверены |
| Xiaomi Mi Router 3C | `Wired Repeater Mode` и `Wireless repeater mode`: [официальное руководство Xiaomi, стр. 5–7](https://i01.appmifile.com/webfile/globalimg/in/router3c/APP3C.PDF) | Старое руководство именно 3C, не 3/3G/3A; наличие пункта и прозрачность MAC выбранного режима проверить на установленной прошивке |

Для Xiaomi предпочтителен проводной повторитель; общая документация производителя
описывает его как AP с выдачей адресов основным роутером
([описание режимов Xiaomi](https://cdn.cnbj1.fds.api.mi-img.com/ics-resources/articles/6050c98d5078534fd7625401.html)).
Беспроводной режим не считать автоматически прозрачным для MAC: конкретную реализацию
нужно проверять. Перед сменой режима сохранить конфигурацию, иметь проводной доступ,
проверить новый адрес управления и восстановление; не менять рабочую сеть автоматически.

**Доступ приложения к Sheepfold не равен контролю всего домашнего интернета.** Sheepfold
не может блокировать трафик, который проходит напрямую через главный Huawei/Xiaomi,
минуя OpenWrt с Sheepfold. В существующей схеме родитель сверху сможет управлять
устройствами за тестовым роутером после реализации multi-router доступа, но это не
распространит firewall тестового роутера на всех клиентов главного Wi-Fi.

### Ограниченный satellite вместо общего port forwarding

Простое приложение для port forwarding не берётся в основную реализацию.

Причины:

- клиент за дочерним роутером обычно уже может выполнить исходящий запрос к основному Sheepfold;
- port forwarding не возвращает backend реальный IP/MAC телефона;
- лишний listener увеличивает поверхность атаки;
- появляется отдельный жизненный цикл обновления, firewall и диагностики;
- перенос TLS termination на relay потребовал бы копировать приватный ключ, что запрещено.

Вместо него в будущем допустим отдельный пакет `sheepfold-satellite`, если реальные тесты покажут необходимость.

Satellite-agent должен:

- сопрягаться с основным Sheepfold отдельным одноразовым токеном;
- иметь собственный ограниченный ключ без прав администратора;
- объявлять адрес основного Sheepfold клиентам своего LAN;
- при необходимости сопоставлять локальные IP/MAC клиентов;
- отправлять только подписанные запросы разрешённых типов;
- никогда не хранить root-пароль, административный Bearer или приватный TLS-ключ основного роутера;
- не открывать доступ из интернета;
- удаляться и отзываться из LuCI основного Sheepfold.

TCP relay с прозрачным TLS допустим только как транспорт и не решает идентичность. Для детских правил satellite должен доказуемо сообщать локальную личность клиента, а основной backend обязан считать эти сведения доверенными только от конкретного сопряжённого satellite.

## Устройства за NAT

Текущая серверная сверка `IP -> MAC` полезна в одной L2-сети, но не может различить несколько телефонов за одним дочерним NAT.

Целевая долгосрочная модель:

1. При сопряжении Android создаёт аппаратно защищённую пару ключей.
2. Роутер сохраняет публичный ключ рядом с `deviceId`.
3. Каждый административный запрос подписывается с nonce, временем, методом, путём и hash тела.
4. Backend проверяет подпись и защиту от повтора.
5. MAC остаётся сетевым сигналом и поводом для уведомления, но больше не является единственным доказательством Android-устройства.

Эта миграция требует отдельного ADR, benchmark на слабом роутере и совместимости с Android 9. До неё административное сопряжение через NAT считается неподдерживаемым, а не «частично работающим».

Для детского APK нужен отдельный контракт. Нельзя выдавать статус конкретного ребёнка всем клиентам, скрытым за одним NAT, только по source IP. Варианты для будущего:

- ограниченный device credential детского APK;
- сопряжённый satellite-agent, который видит локальный MAC;
- перевод дочернего роутера в bridge/AP mode.

## Пользовательский интерфейс LuCI

В настройках интеграции домашней сети следует показать:

- переключатель `Разрешить доступ к Sheepfold из других роутеров домашней сети`, по умолчанию выключен;
- найденные интерфейсы и подсети;
- понятный статус каждого сегмента;
- адрес, который попадёт в QR;
- предупреждение, если виден NAT или MAC шлюза;
- список сопряжённых satellite-устройств, когда функция появится;
- кнопку отзыва доступа.

Пользователю не нужно показывать nftables, CIDR и CGI-термины без кнопки справки. Основной текст должен объяснять: «Телефоны из этой домашней сети смогут находить Sheepfold. Доступ всё равно защищён привязкой приложения».

При смене адреса или порта Android получает обновлённый список после защищённого запроса. Если старый endpoint уже недоступен, приложение использует только ранее сохранённые и криптографически связанные кандидаты.

## Журнал

Записываются:

- доверенная домашняя сеть включена или выключена;
- интерфейс или префикс изменился;
- firewall-правило применено или удалено;
- начато и завершено окно сопряжения;
- сопряжение успешно или отклонено;
- запрос пришёл через неподдерживаемый NAT;
- satellite добавлен, отозван или потерял связь.

Не записываются:

- QR;
- одноразовый код;
- Bearer;
- приватный ключ;
- полный Authorization header.

Повторяющиеся отказы объединяются, чтобы не переполнять RAM-журнал.

## Совместимость

Правило домашнего доступа относится только к input на Sheepfold API. Оно не должно менять:

- forwarding пользовательского трафика;
- DNS;
- маршруты Podkop;
- правила AdGuard Home;
- глобальный доступ устройств в интернет;
- SSH или LuCI.

Тесты выполняются во всех четырёх сочетаниях:

1. без Podkop и AdGuard Home;
2. с Podkop, без AdGuard Home;
3. с Podkop и AdGuard Home;
4. без Podkop, с AdGuard Home.

## Этапы внедрения

Исторический план шире реализованного v1. Изоляция и один upstream реализованы;
обобщённый registry, выбор нескольких QR-адресов, NSD, child discovery и NAT остаются планом.

### Этап 0. Документация и защита текущего QR

- Зафиксировать отсутствие второго проверочного кода.
- Показывать предупреждение под QR.
- Защитить предупреждение UI-тестом.
- Добавить архитектурный ADR и §-теги.

### Этап 1. Изоляция API

- Создать отдельный document root.
- Перенести в него только разрешённые Sheepfold endpoint.
- Привязать listener только к выбранным адресам, а не безусловно к `0.0.0.0`.
- Проверить, что `/cgi-bin/luci` и чужие CGI на API-порту возвращают отказ.
- Добавить cleanup при остановке и удалении пакета.

Без завершения этапа 1 доступ через upstream не включается.

### Этап 2. Trusted-network firewall

- Добавить UCI-модель доверенных сегментов.
- Реализовать manager nftables sets.
- Добавить fail-closed обработку смены адреса, роли интерфейса и порта.
- Разрешить временное окно pairing только на явно выбранном сегменте.
- Добавить глобальный rate limit и сборку мусора `/tmp`.

### Этап 3. Endpoint registry

- Расширить well-known JSON минимальным списком endpoint.
- Научить LuCI выбирать адрес для QR.
- Научить оба APK сохранять кандидаты только после защищённого ответа.
- Исключить публичные, loopback, multicast и CGNAT-адреса.
- Не увеличивать QR полным списком.

### Этап 4. Проверка на живой сети

- Телефон на `192.168.2.x` сопрягается с `192.168.2.179`.
- Повторное использование QR отклоняется.
- Неверный SPKI отклоняется до передачи кода.
- Чужой клиент без QR не получает административный credential.
- После отзыва телефон теряет доступ.
- Смена API-порта не оставляет открытым старый порт.
- Перезапуск, upgrade и uninstall не оставляют firewall-мусор.
- LuCI и SSH недоступны через API-порт.

### Этап 5. Локальное обнаружение

- Добавить mDNS/NSD.
- Проверить несколько AP одной L2-сети.
- Проверить изоляцию клиентов и понятную ошибку.
- Добавить `home.arpa` только там, где Sheepfold контролирует DNS.

### Этап 6. Routed/NAT-сегменты

- Сначала измерить реальные топологии.
- Спроектировать Android device-key вместо доверия только MAC.
- При необходимости сделать ограниченный `sheepfold-satellite`.
- Не выпускать универсальный port-forward helper.

## Обязательные тесты

### Статические и unit

- listener использует отдельный web root;
- firewall принимает только перечисленные интерфейсы и порт;
- публичный endpoint не возвращает секреты;
- endpoint list отклоняет неправильные адреса;
- QR остаётся одноразовым и без второго кода;
- warning присутствует в LuCI и переводах;
- port change обновляет listener и firewall одной операцией.

### Интеграционные

- один L2-сегмент;
- Sheepfold на дочернем роутере;
- телефон за NAT;
- гостевой VLAN;
- смена DHCP-адреса Sheepfold;
- включённый Android VPN;
- AP/client isolation;
- IPv6-only и dual-stack без случайного открытия;
- Podkop/AdGuard Home matrix.

### Негативные

- запрос с публичного интерфейса;
- source MAC равен MAC gateway;
- поддельный discovery JSON;
- SPKI mismatch;
- повтор pairing code;
- flood pairing/ping;
- обращение к LuCI через `5201`;
- stale firewall rule после crash и uninstall.

## Критерии готовности

Функция считается готовой для первого релиза только если:

1. API изолирован от общего `/www`.
2. Через дополнительный адрес невозможно открыть LuCI и SSH.
3. Доверенный сегмент включается явно и закрывается fail-closed.
4. QR одноразовый, короткоживущий и не содержит постоянных секретов.
5. Второго проверочного кода нет.
6. Android проверяет SPKI на каждом новом endpoint.
7. MAC шлюза не принимается как MAC телефона.
8. Изменение порта, upgrade и uninstall не оставляют открытых правил.
9. Живой тест подтверждает схему `192.168.2.x -> 192.168.2.179`.
10. NAT-сценарий либо криптографически поддержан, либо честно отклонён.
