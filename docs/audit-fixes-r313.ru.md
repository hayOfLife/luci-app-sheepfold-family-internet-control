# Аудит r313: выбранный журнал и согласованный снимок для Google Drive

Дата: **11 сентября 2026 года**. База: **`bf8e075` (r312)**, потомок принятого
`bdb3a92`. Результат находится в `main`, пакет **0.1.0-313**. Публикации в GitHub
и установки на роутер не было. Реестр содержит **105 карточек**, новые — **B104–B105**.

## Область и результат

Изменён `sheepfold-google-drive`: обе отправки обычного журнала используют выбранный
`log_cache_path` и проверенную локальную копию. Новая `drive_events_snapshot` подключает
существующие `sheepfold-log-common` и `sheepfold-lock-common`; их реализации не менялись.
Общая блокировка writer/API/rotator удерживается только при создании снимка, не при HTTP.

Сохранены выбор Google Drive только по `log_storage`, проверка OAuth/контекста,
remote ID/size, порядок подготовки config перед облачными изменениями, защита
исходников архивов и форматы имён в Drive. `upload_and_verify` не изменён: последний
контроль источника по-прежнему защищает удаляемые архивы. Не тронуты Android,
правила доступа, UCI defaults, CI workflows и скрипты запуска тестов. D01 сохранён.

Карта зависимостей дополнена: изменение общей библиотеки пути теперь выбирает и
`googleDriveUploadRuntime.test.mjs`. Это новая связь существующего модуля, не
переписывание принятого механизма отбора тестов. Проверка IPK подтверждает поставку
обеих библиотек и их подключение загрузчиком в обеих редакциях.

## B104: выбранный журнал не попадал в отправку

Writer, API и ротация уже использовали `log_cache_path`, а GDrive читал только
`/tmp/sheepfold/events.log`. На неизменённой r312 подтверждены два результата:

- Если старый default существовал, обе команды отправляли его вместо выбранного
  вложенного файла. Синтетические тексты имеют одинаковую длину: проверка размера
  проходила, но HTTP-трасса показывала не те байты.
- Если существовал только выбранный файл, `push-events` успешно выполнял no-op,
  а `archive-push` отправлял другие файлы без нужного журнала.

Теперь путь проверяется через общий контракт. Ошибка UCI не означает отсутствия
настройки; неправильный путь не заменяется другим файлом. Поддерживаются обычные
вложенные каталоги, пробелы и UTF-8. Отсутствующий выбранный журнал допустим, но
старый default не используется вместо него. Отказ пути/настройки/снимка даёт
`events_snapshot_failed` до сети и до удаления ожидающих архивов.

Почему не просто `uci get`: нужна общая классификация отсутствия, отказа и
недопустимого пути. Иначе новый экспортёр вновь разойдётся с записью/чтением.
Отрицательные контроли `..`, ссылок и специальных объектов проверяют добавленную
границу, а не доказывают новые обходы старого кода, который игнорировал настройку.
Полная карточка: [B104 в реестре](bug-register.ru.md).

## B105: нормальная запись события выдавала ложный отказ отправки

В неизменённой r312 `push-events` передавал живой журнал в функцию, которая после
HTTP сравнивала этот журнал со снимком. Дописанная новым процессом строка вызывала
`source_changed`, хотя HTTP-модель уже получила исходные байты и подтвердила размер.
Новые локальные данные не терялись; ошибочным был результат уже выполненной копии.

Обе отправки также обходили `log-maintenance.flock` при подготовке. Управляемый
Linux-процесс держит настоящий lock, а r312 начинает копирование и сеть без ожидания.
Это доказательство нарушения согласования, не утверждение о повреждении каждого лога.

Теперь локальное копирование, режим 0600, сравнение и повторная проверка пути
выполняются под тем же lock, что writer/API/rotator, с ожиданием до 5 секунд.
После освобождения в HTTP передаётся отдельный снимок. Позднее событие остаётся
живому журналу и следующей отправке; уже сформированная копия не меняется.

Почему не удалить `cmp` из uploader: это ослабило бы сохранность удаляемых архивов.
Почему не держать lock до конца upload: медленная сеть заблокировала бы запись
событий. Новый отдельный lock только облака тоже не согласовал бы его с writer.
Выбран короткий общий локальный этап, без изменения контракта остальных архивов.
Полная карточка: [B105 в реестре](bug-register.ru.md).

## Воспроизведение и границы стенда

Рабочий каталог — корень checkout. Требуются Node.js 22, Python 3, POSIX sh,
обычные файловые утилиты и tar; Linux-сценарии требуют `flock`/`fcntl`.
Все файлы и реквизиты синтетические, внутри `.build`; fixture удаляет собственные
каталоги. Реальный production-скрипт выполняется с перенаправленными путями.
HTTP, UCI и jshn — модели: реальный аккаунт Google не используется.

```sh
node --test --test-name-pattern='Google Drive configured journal snapshots|Google Drive journal snapshot failure boundaries|Google Drive journal shared-lock coordination' tests/googleDriveUploadRuntime.test.mjs
```

Ожидаемый результат на Linux — **38 pass, 0 fail/cancel/skip**, exit 0.
Отказы утилит оставляют trace вызова. Блокировки проверяются настоящими процессами:
пока writer держит lock, нет cp/HTTP; после освобождения отправка завершается.
Во время HTTP независимый процесс получает lock и добавляет событие. Сравниваются
старые отправленные байты, новые локальные байты и результат команды.

Сравнение с исходной r312 использует переменную `SHEEPFOLD_GDRIVE_TEST_SOURCE`,
указывающую на каталог с неизменённым `sheepfold-google-drive` из `bf8e075`.
Применялись те же конечные assertions; девять ключевых сценариев дали **7 fail и
2 pass**. Два контроля — пустой журнал и отсутствие журнала — не названы ошибками.
Первый 22-сценарный baseline сохранён отдельно: он дал 21 fail/1 pass, после чего
текст stale-default уточнён до одинакового размера для более точного воспроизведения.
Проверки старой версии намеренно завершаются с ненулевым кодом.

Ближайшие прежние проверки:

```sh
node --test --test-name-pattern='Google Drive independent upload evidence|Google Drive upload preparation|Google Drive checks preparation before remote mutation|Google Drive local archive snapshots|Google Drive archive format controls|Google Drive status observation safety' tests/googleDriveUploadRuntime.test.mjs
node scripts/run-test-category.mjs --file logStorage.test.mjs --file logWriterRuntime.test.mjs --file packageHardeningRuntime.test.mjs
node --test tests/changeImpact.test.mjs
python3 scripts/build-test-ipk.py --variant all
```

Для каждой редакции переменной `SHEEPFOLD_TEST_IPK` передаётся путь к её собранному
IPK, затем выполняется `node --test tests/testIpkPermissions.test.mjs`. Пакеты находятся
в `.build/ipk-output`; они не устанавливаются. Hardening запускается только с путём
к отдельно распакованному rootfs, не против корня текущей системы. Обе проверки
распакованных пакетов завершились с exit 0; байты загрузчика и обеих библиотек
совпали с исходниками, установленные режимы — 0755.

## Не подтверждено и что осталось

Нативные UCI/jshn и целевой BusyBox runtime, реальный Google Drive, физический
роутер, Android, SDK-сборка, flash и потеря питания не проверялись. Shell syntax и
Linux flock не выдаются за установку на OpenWrt. Проверка удалённого размера не
равна checksum. ESLint не выполнен: `npm exec --offline -- eslint` завершился
`ENOTCACHED`, нужной зависимости нет в локальном кэше. Проверка синтаксиса его
не заменяет. Подробный протокол поставки приводится в архиве доказательств.

Снимок увеличивает расход RAM; предел байтов и длительности cp не введён. При
очень большом файле локальная блокировка может задержать writer. Внешние writers
без этой блокировки, privileged symlink/mount/hardlink races, ABA и общая атомарность
UCI не покрыты. Смена пути после снятия снимка не отменяет уже начавшуюся отправку.
Нет exactly-once доставки новых событий, новой политики повторов или общей
блокировки параллельных облачных операций. Аварийное завершение или ошибка уборки
может оставить закрытые временные файлы. Остальные экспортёры — отдельный аудит.
Восстановление конфигурации не изменялось и не объявлено исправным.
