# Аудит r310: достоверный просмотр копий Google Drive

Дата: **11 сентября 2026 года**. База: **`0c27dff` (r309)**, потомок принятого
`bdb3a92`. Изменения подготовлены локально в `main`; push не выполнялся.
Версия пакета: **0.1.0-310**. Подробные карточки —
[B98–B99 в накопительном реестре](bug-register.ru.md).

## Результат и область

Исправлена самостоятельная команда `list`, которую LuCI вызывает через
`google-drive-list`. Теперь успешный ответ требует проверенных списков обеих
папок в одном обнаруживаемо неизменённом контексте настроек. Формат ответа
сохранён: `ok`, `root`, `logs`, `backups`; элемент — `name`, числовой `bytes`,
строковый `modified`. Восстановление конфигурации, выбор последней копии, загрузка
и удаление облачных файлов в этом проходе не включались и не переписывались.

Производственный источник — `sheepfold-google-drive` в
`package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/`.
Изменены `cmd_list`, `folder_list_json_array`, добавлены их узкие helpers.
`drive_inventory_item`, OAuth, download, квоты и upload не изменены. Версия
поднята в Makefile; значение UI asset version по-прежнему выводится из неё.

Модель `jshn` в существующем тестовом файле дополнена только используемыми здесь
операциями `json_add_string`, `json_add_int`, `json_dump`. Это модель зависимости,
а не альтернативный производственный код. Общие runner, workflow, Android,
правила доступа и подтверждённый владельцем D01 не менялись.

## B98: обычный просмотр останавливался до чтения списка

Неизменённая r309 выполняет `root logs_json backups_json root_name` как команду.
Результат корректного вызова — `root: not found`, а не список копий. После
устранения первого ошибочного объявления встречается самостоятельная команда
`response` внутри reader. Простая правка одного слова не восстанавливала путь.

Оба вызова изолированы дочерними оболочками. Все обязательные значения получают
явные присваивания, ошибки передаются вызывающему коду. Это не отключение
`set -e` и не игнорирование `not found`. Полезная изоляция переменных и trap
сохраняется при вложенном вызове.

Для исследования поздних дефектов создан **decl-only**: оригинал r309 с
исправлением только этих двух объявлений. Его исходник и diff входят в архив
проверок. Он не считается исходной r309, готовым релизом или безопасным restore.

## B99: неполный и ошибочный ответ выглядел как достоверный список

На decl-only из двух записей компактного JSON остаётся последняя; размер
возвращается строкой. С обычным многострочным форматированием список может
оказаться пустым. Имя с кавычками, Unicode escaping и backslash искажается.
HTTP 403 с правдоподобным телом не останавливает вывод `ok:true`; объект ошибки,
незаконченный ответ и неполный поиск не обрабатываются как надёжно отличимые
состояния. Между папками не удерживается исходный контекст настройки аккаунта.

Причина — `drive_request ... || true` и AWK с `getline`, предполагающий
расположение соседних name/size/modifiedTime на определённых строках. Общий
точный поиск уже был исправлен ранее, но отдельный пользовательский reader
продолжал использовать старую схему.

Теперь тело сохраняется отдельно от HTTP-кода. Проверяются curl, HTTP 200,
измерение объёма, чтение и вся JSON-структура. Проверка элементов переиспользует
правила уже существующего inventory-reader: ID, размер, имя, MIME, parents и
trashed. Время изменения проверяется как непустая строка ограниченной длины;
локальный семантический разбор календаря не добавлен.

Ответ формируется штатным `jshn`, не ручной заменой кавычек. Поддерживаются
Unicode, управляющие символы в имени, нулевой файл, числовой размер более 2 ГиБ.
Идентификаторы не повторяются внутри папки. Временные строки буферизуются, пока
вся папка не проверена; до проверки второй папки успешный результат не выдаётся.
Смена реквизитов/корня во время запроса останавливает команду без повторного
чтения под новым аккаунтом.

Технический отказ возвращает ровно:

```json
{"ok":false,"error":"list_unavailable"}
```

Код завершения ненулевой. Отсутствующие реквизиты/инструменты сохраняют прежние
контролируемые ответы require_tooling. Две реально пустые папки после успешного
чтения остаются двумя пустыми массивами при `ok:true`.

**Почему так:** расширение regex пробелами не исправляет типы, порядок и
экранирование. Подстановка пустого массива скрыла бы недоступность данных.
Подмена старого контекста новым при ошибке была бы незаметной сменой назначения.
Использован существующий jshn, без новой зависимости и без AI-only библиотеки.

### Предварительные отказы не скрыты

Первый новый прогон дал 35/36. Сбой был в fixture: `wc` получает файл через stdin,
поэтому поиск имени в argv не вызывал подставленную ошибку. Проверка трассы
подтвердила отсутствие вызова. Исправлен только тест: reached-барьер после HTTP
и отказ следующего `wc -c`. Production ради зелёного результата не менялся.
Окончательные проверки и первоначальный журнал сохранены раздельно.

Baseline сравнивает тот же окончательный тестовый файл на оригинале и decl-only.
Неуспешные assertions, требующие нового кода ошибки или нового этапа проверки,
не объявлены самостоятельными уязвимостями. Положительный контроль пустой очереди
проходит на decl-only, но это не доказывает корректность обработки непустой.

## Повторение на изолированном Linux-стенде

Из корня checkout нужны Node.js, Python 3, POSIX sh и обычные файловые утилиты.
Реальные токены Google, адрес роутера и права изменения системного UCI не нужны.
Все записи создаются внутри `.build/gdrive-fixtures` и удаляются обработчиками
тестов. При явном экспорте сохраняются только синтетические трассы.

```sh
node --test --test-name-pattern='Google Drive list safety' tests/googleDriveUploadRuntime.test.mjs
node --test --test-name-pattern='Google Drive lookup and folder publication|Google Drive lookup supplemental boundaries' tests/googleDriveUploadRuntime.test.mjs
python3 scripts/build-test-ipk.py --variant all
SHEEPFOLD_TEST_IPK="$PWD/.build/ipk-output/luci-app-sheepfold-family-internet-control_0.1.0-310_all.ipk" \
node scripts/run-test-category.mjs --file logStorage.test.mjs --file logWriterRuntime.test.mjs \
  --file packageHardeningRuntime.test.mjs --file testIpkPermissions.test.mjs
SHEEPFOLD_TEST_IPK="$PWD/.build/ipk-output/luci-app-sheepfold-ai-support_0.1.0-310_all.ipk" \
node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
node scripts/runQualityChecks.mjs --git 0c27dff --plan
node scripts/checkDocumentation.mjs --all
git diff --check
```

`SHEEPFOLD_GDRIVE_TEST_SOURCE` принимает **каталог**, содержащий сравниваемый
`sheepfold-google-drive`. Архив доказательств включает `baseline/` и `decl-only/`.
`SHEEPFOLD_GDRIVE_EVIDENCE_DIR` включает экспорт synthetic traces; не использовать
для настоящих реквизитов. В Linux используется системный sh, чтобы BusyBox applet
не обошёл подставленные файловые утилиты. Syntax-check BusyBox не равен runtime
всей системы под BusyBox.

Ожидаемый результат каждого итогового тестового запуска — exit 0. Отказы baseline
ожидаются и записаны отдельно. Проверки пакета требуют построенного IPK в
`SHEEPFOLD_TEST_IPK`: отсутствие файла не нужно лечить отключением assertions.

## Сверка внешних контрактов

Проверены 11.09.2026, отдельно от выводов об исходниках проекта:

- [Google Drive files.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list):
  `files`, `nextPageToken`, `incompleteSearch`, query и сортировка. Наличие следующей
  страницы не позволяет назвать полученный массив полным.
- [OpenWrt jshn.sh](https://lxr.openwrt.org/source/libubox/sh/jshn.sh):
  штатные `json_add_string`, `json_add_int`, `json_dump`; writer вызывается после
  проверки reader и его результат принимается только при успешном завершении.

Это сверка документации/исходников зависимостей, не запуск нативной libubox.
Попытка получить исходник для дополнительной нативной проверки остановилась
на DNS контейнера. Сборка или успешный запуск нативного jshn не заявляются.

## Ограничения и дальнейшая работа

Максимум 200 объектов и 256 КиБ ответа на папку — ограничение обработки, не
реализованная пагинация или потоковая RAM-квота. Неполный список возвращает отказ,
а не удаление данных. Отсутствующий size не заменяется нулём; неподдерживаемый
нативный объект Google может сделать список недоступным до отдельной доработки.
Модель не является замером производительности на слабом OpenWrt-роутере.

Две папки читаются последовательно, не атомарно. Облачные writers, ABA и изменение
после последней проверки остаются. Context-key связан с реквизитами и root, но
не является независимым доказательством прав/владельца Google-объекта. Существующий
cache bootstrap может создать отсутствующие ожидаемые папки: команда не объявлена
совершенно read-only на стороне Google. Успех не доказывает содержимое архивов.

Новый list не активирует `latest_backup_name` и `restore-config`. Эти пути всё ещё
нуждаются в отдельной проверке распаковки, допустимых файлов/ссылок/размера,
страховочной копии, pending UCI, применения и отката. Нельзя устранять их ранние
объявления и представлять это как законченное безопасное восстановление.

Общее сообщение UI об ошибке списка уже локализовано; отдельные подробные причины
здесь не добавляются в интерфейс. Рабочее дерево, кэш токена и модель HTTP не
равны физическому Google Drive, браузеру LuCI, нативному UCI или установке.
Android/SDK/Actions не запускались; прежние зелёные сборки не приписываются r310.
