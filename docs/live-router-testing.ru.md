# Тестирование на живом OpenWRT-роутере

Этот документ описывает полную матрицу автотестов Sheepfold в связке с настоящим тестовым роутером. Такие тесты полезны, потому что часть ошибок проявляется только на реальном OpenWrt: `opkg`/`apk`, `uci`, `ubus`, `rpcd`, LuCI, Wi-Fi, firewall, hotplug, права файлов и особенности конкретной прошивки.

<!-- §routerharness -->

Безопасная исполняемая основа уже находится в `tools/router-testing/`: она умеет подготовить SSH-ключ, определить менеджер пакетов, установить IPK либо SDK-собранный OpenWrt APK с backup, выполнить read-only и восстанавливаемые UCI-проверки, а также проверить LuCI через Playwright. Команды и точные границы описаны в [`live-router-automation.ru.md`](live-router-automation.ru.md). Остальные сценарии этого документа являются планом расширения и не должны считаться реализованными только потому, что они перечислены ниже.

Важно: тесты с живым роутером нельзя смешивать с обычными unit-тестами. Они должны запускаться явно, с понятным уровнем риска и с бэкапом конфигурации перед любыми изменениями.

## Проверка трафика телефона 24.10.2026

Физический ZTE Blade A51RU на Wi-Fi тестового Cudy WR3000S / OpenWrt 25.12.5.
Установленный Sheepfold остаётся `0.1.0-r286`; поверх него испытан только новый
`31-sheepfold-prerouting.nft` из source r325, а не полный пакет r325.
Основное Android-приложение не переустанавливалось и не очищалось: обновлён только
его instrumentation APK. Запросы привязаны к `Network` Wi-Fi с нужным gateway,
не к default network, cellular или VPN телефона.

Исходно обе службы были остановлены, dnsmasq направлял DNS на отсутствующий
`127.0.0.42`, прямой HTTP по IP работал, DNS — нет. Сам статус Podkop `running`
не подтверждал sing-box: проверены PID, listener, DNS и настоящие HTTPS-запросы.
Ранний запуск sing-box падал на remote rule-set с `reality verification failed`.
Для изоляции стенда внешние community lists отключены, пользовательские домены,
подсети и proxy сохранены; загрузка списков через proxy выключена.
Исходные настройки сохранены закрытым backup, не в Git. Это не проверка всех
внешних подписок Podkop и не основание отключать их на пользовательских роутерах.

До исправления реальный proxy HTTPS обходил общий запрет и `restricted`, хотя
прямой трафик блокировался. Ранний guard `prerouting -160` вызывает ту же политику
до TPROXY Podkop `-150`; локальные назначения оставлены `input`. `fw4 check` и
reload успешны, PodkopTable и route mark сохранены, sing-box не переустанавливался.
Подтверждены fake-IP `198.18.0.0/15`, правило маршрутизации Podkop и его nft counters.

| Сценарий | Прямые TCP/HTTP/HTTPS | HTTPS через Podkop | Веб-интерфейс роутера |
|---|---|---|---|
| Обычное устройство, интернет включён | доступен | доступен | доступен |
| Обычное устройство, общий запрет | закрыт | закрыт после исправления; до него обход | доступен |
| Белый список устройств, общий запрет | доступен | доступен | доступен |
| Чёрный список устройств, общий запрет выключен | закрыт | закрыт | закрыт |
| Чёрный список устройств, общий запрет включён | закрыт | закрыт | закрыт |
| `restricted`, общий запрет выключен | закрыт | закрыт после исправления; до него обход | доступен |
| Возврат обычного доступа | доступен | доступен | доступен |

Первый семифазный проход после hotfix не был полностью зелёным: две разрешающие
фазы получили transient `SocketException` на proxy; в этот период probe с самого
роутера также давал `000`, затем восстановился. Это не скрыто повтором. После
восстановления выполнен отдельный последовательный четырёхфазный gate: baseline,
белый список + общий запрет, обычное устройство + общий запрет, восстановление.
Все четыре дали `OK (1 test)`, каждая с пятью probes; параллельный контроль с роутера
каждый раз получил proxy HTTP `204`. Поэтому закрытый доступ телефона нельзя
объяснить отсутствием интернета у proxy. Общий долгий stability gate ещё нужен.

В конце общий запрет снят, телефон оставлен обычным устройством, обе службы
включены и находятся в автозапуске по разрешению владельца. Auto-configure на
стенде выключен для детерминированности, IPv6 отключён режимом Podkop.
Системный пакет, WAN, SSID и пароль Wi-Fi не обновлялись.

Локальный контроль: 49 Node-проверок firewall/ADR/impact/categories без ошибок,
ESLint, аудит 300 Markdown-файлов, сборка instrumentation APK, родительский
`:app:lintDebug` и `git diff --check` успешны. Дополнительный объединённый запуск
с `accessPolicyRuntime.test.mjs` завис в Windows на дочернем fixture-процессе и
был остановлен; он не записан как успешный. Это не отказ живого packet-level gate.
Init Podkop является одноразовым: после завершения запуска он может показывать
`not running`, хотя отдельный sing-box работает. Готовность определять по
sing-box, DNS, маршрутам, nft counters и ответам, а не этой одной строке.
В последней проверке прямой HTTPS работал, а proxy probe снова вернул `000`:
долговременная стабильность proxy не подтверждена и остаётся открытой проблемой.

### Дополнительный проход по открытым соединениям 24.10.2026

На том же r286 с nft hotfix выполнен `trafficEstablished=1` из
[инструкции Android-стенда](android-test-lab.ru.md#уже-открытые-соединения).
Каждый из двух TLS-сокетов сначала получил по два HEAD-ответа; после `TRAFFIC_READY`
backend-команда применена внутри 30-секундного окна. Следующий запрос использует
тот же сокет, без reconnect. Это проверка обмена после запрета, не измерение точного
времени реакции firewall и не непрерывная загрузка большого файла.

| Изменение после открытия двух соединений | Прямой TLS | TLS через Podkop | Результат |
|---|---|---|---|
| Контроль без смены политики, пауза 30 секунд | работает | работает | `OK (1 test)` |
| Обычный телефон: включить общий запрет | timeout | timeout | `OK (1 test)` |
| Телефон из белого списка: включить общий запрет | работает | работает | `OK (1 test)` |
| Обычный телефон: внести в чёрный список | timeout | timeout | `OK (1 test)` |

При трёх изменениях политики независимый запрос с роутера к proxy endpoint дал
`204`. После последней фазы телефон возвращён в `new`, общий запрет выключен;
обычный пятишаговый Android gate дал пять успешных probes и `OK (1 test)`.
`fw4 check` успешен, обе службы оставлены в автозапуске, sing-box PID не изменился.
Новые production-файлы на роутер в этом проходе не копировались, обновлён только
тестовый APK. `:app:assembleDebugAndroidTest` и `:app:lintDebug` успешны.

Начальные восемь последовательных пар запросов с роутера дали `302` на прямом
направлении и `204` через proxy, но три попытки подготовки established-теста
позднее упали до `TRAFFIC_READY` с `Connection reset`; они не засчитаны как
проверка запрета. В попытке с расширенной диагностикой сбой произошёл именно
на `www.gstatic.com`, после успешного прямого TLS. Независимый curl с роутера
также воспроизвёл exit `35`, HTTP `000`, `Connection reset by peer`; безопасная
выжимка журнала содержала `outbound/urltest` и `EOF`. Точный неисправный upstream
и первопричина сброса пока не определены. Конфигурация proxy и его credentials
не заменялись. Эти наблюдения не позволяют объявить длительную стабильность
Podkop, хотя обе проверенные политики Sheepfold действуют при рабочем proxy.

### Повтор ручного packet-level gate

Команды и сборка тестового APK описаны в
[Android-стенде](android-test-lab.ru.md#реальный-трафик-и-списки-устройств).
Отдельно сохранить закрытую копию UCI до любых изменений. Использовать только
согласованный тестовый телефон, не администратора и не члена «Без ограничений»;
MAC получить из актуального neighbour/DHCP роутера, а не из прежнего журнала.

На SSH тестового роутера, каталог `/`, проверить/установить одну фазу:

```sh
test_mac='ACTUAL_TEST_PHONE_MAC'
ctl=/usr/libexec/sheepfold/sheepfold-router-control
"$ctl" set-device-status "$test_mac" new 'Traffic test phone' '' '' phone
"$ctl" set-device-status "$test_mac" allow 'Traffic test phone' '' '' phone
"$ctl" global-block-on
```

`ACTUAL_TEST_PHONE_MAC` — MAC выделенного телефона, проверенный в текущей LAN.
Ожидаются exit `0` и `OK`, но они не доказывают остановку/разрешение пакетов:
сразу выполнить Android gate `trafficExpected=open`, `trafficLan=open`.
Для чёрного списка сначала вернуть `new`, затем выбрать `blocked`; ожидать
`trafficExpected=blocked`, `trafficLan=blocked`. Для общего запрета обычного
устройства использовать `new`, `global-block-on`, `blocked/open`; для `restricted`
выключить общий запрет и ожидать `blocked/open`. Перед каждой запрещающей фазой
подтвердить рабочий baseline, а через роутер проверить HTTPS независимо от телефона.

По завершении вернуть `new` и вызвать `global-block-off`, проверить baseline и
состояния служб. Не запускать последовательность на семейном MAC без backup,
не менять status родительского устройства ради удобства и не делать вывод по
одному `adb` exit code или одному timeout. При несовпадении сохранять результат,
а не ослаблять ожидаемую политику или TLS. Новый hook можно откатить удалением
только этого добавленного файла и reload fw4 после проверки сохранённого состояния.

**Границы:** backend-команды совпадают с используемыми UI, но сам тап кнопки в APK
не автоматизировался. Проверены два конкретных уже открытых TLS-соединения;
не проверены IPv6 при включённом Podkop, все виды длительных потоков,
hardware/software flow offload, power-loss/reboot,
OpenWrt 24.10 и четыре комбинации AdGuard Home. Этот результат их не закрывает.

### Диагностика URLTest и reload firewall 24.10.2026

В следующем проходе runtime sing-box содержал 46 VLESS-выходов, URLTest и selector.
Это не один фиксированный proxy. У URLTest были интервал `3m` и tolerance `50`;
по [контракту sing-box](https://sing-box.sagernet.org/configuration/outbound/urltest/)
проверка измеряет доступность/задержку заданного URL, а не гарантирует стабильность
всех запросов. Ошибки проверки отдельных кандидатов нельзя автоматически
приписывать текущему выбранному выходу.

Подтверждены 20 успешных HTTPS-запросов при автоматическом выборе. Затем через
локальный Clash API временно зафиксированы два существующих выхода: A/B/A,
по 12 запросов в каждой фазе, все 36 получили `204`. Проверка selector после
переключения подтвердила выбранный выход; `trap` вернул исходный автоматический
выбор. Исходные proxy URI, список кандидатов, UCI и ключи не изменялись.
Индексы выходов действуют только для текущего JSON, не являются постоянными ID.
Ещё 12 пар запросов через прозрачный маршрут и `socks5h://127.0.0.1:4534`
дали 24 ответа `204`. Оба входа маршрутизировались через тот же selector.
Итого 80 HTTP-проверок в этих сериях успешны, но прежние TLS reset не воспроизведены
и не объявлены исправленными. Различие TPROXY/SOCKS и конкретный неисправный узел
этим не доказаны. В данном runtime TPROXY и mixed/SOCKS слушают loopback.

Для повтора короткой read-only пары: SSH root тестового роутера, каталог `/`,
установленные `curl`/Podkop/sing-box. Сначала подтвердить фактический loopback-порт
mixed-входа по безопасным полям runtime JSON; `4534` относится к этому стенду.
Нужен работающий исходный proxy, конфигурация и служба Sheepfold не меняются:

```sh
curl -sS -o /dev/null -w 'transparent=%{http_code}\n' --connect-timeout 4 --max-time 6 https://www.gstatic.com/generate_204
curl -sS -o /dev/null -w 'socks=%{http_code}\n' --proxy socks5h://127.0.0.1:4534 --connect-timeout 4 --max-time 6 https://www.gstatic.com/generate_204
```

Ожидается exit `0` каждой команды и два `204`. `000` с exit `35` означает отказ
TLS, а не HTTP-ответ сервера; сохранить результат и проверить выбранный выход.
Не менять проверку сертификата на `-k`, не открывать SOCKS на LAN/WAN и не выводить
полный config или `/proxies` в отчёт: они могут содержать личные имена/credentials.
Ручной выбор через API может сохраниться в cache sing-box, поэтому возврат прежнего
selector и проверка результата обязательны даже при неизменённом UCI.
Пара запросов не доказывает правила доступа телефона, её выполняет сам роутер.

После `/etc/init.d/firewall reload` отдельно проверены обычный телефон с общим
запретом и чёрный список устройств: пять probes в каждой фазе дали `OK (1 test)`,
proxy-контроль с роутера получил `204`, sing-box PID сохранился, PodkopTable осталась.
В первой разрешающей фазе белого списка прямой домен дал `UnknownHostException`,
хотя прямой TCP/HTTP и proxy HTTPS работали. Это сохранённый неуспешный проход.
На роутере оба DNS-сервера затем разрешили имя, прямой HTTPS дал `302`.
Повтор белого списка с общим запретом до reload и после reload дал два полных
успешных пятишаговых gate. Причина единичного DNS-сбоя не установлена.
Эти проверки не измеряют краткий интервал внутри самой пересборки fw4.

`InternetPolicyLiveTest` усилен: `UnknownHostException` больше не может дать зелёную
запрещающую фазу. Сначала нужно подтвердить DNS; только отказ доставки трафика
при рабочем baseline может служить свидетельством блокировки.
Новая версия тестового APK собрана и установлена без переустановки основного APK;
Android Lint успешен. После усиления четыре фазы baseline / общий запрет /
белый список при общем запрете / восстановление дали четыре `OK (1 test)` и
20 совпавших probes, proxy-контроль в каждой фазе получил `204`. Телефон возвращён
в `new`, общий запрет снят; обе службы оставлены включёнными.

## Проверка экспериментального Podkop 0.8.1 24.10.2026

После установки владельцем подтверждены пакеты `podkop-exp 0.8.1-r1` и
`luci-app-podkop-exp 0.8.1-r1`. Sheepfold остался r286 с прежним отдельным nft hotfix
из r325. Это не установка полного нового Sheepfold и не испытание всех версий 0.8.
Стенд: Cudy WR3000S, OpenWrt 25.12.5, физический ZTE Blade A51RU / API 30.

В отличие от 0.7, работает `/usr/bin/podkop daemon` со встроенным движком; отдельные
`sing-box` process/init/config отсутствуют. PodkopTable маркирует в `prerouting -150`,
а TPROXY выполняет в `-100`. Sheepfold guard `-160` остаётся перед обоими шагами.
DNS `www.gstatic.com` вернул fake-IP `198.18.0.5`; счётчики proxy TCP росли,
контрольный HTTPS с роутера получал `204`, прямой `ya.ru` — `302`.

Перед изменениями сделана новая закрытая копия шести UCI-конфигов в
`/tmp/sheepfold-podkop081.GkKeCI` (RAM, не переживает reboot). Старую копию 0.7
поверх 0.8 не восстанавливали. URI proxy, подписки и настройки Podkop не редактировали.
Проверки используют прежние команды раздела «Повтор ручного packet-level gate»
и `InternetPolicyLiveTest` из Android-стенда; APK не пересобирался и не очищался.

Семь фаз основной таблицы этого документа дали семь `OK (1 test)` и 35 совпавших
probes: исходный доступ, общий запрет обычного устройства, белый список устройств
при общем запрете, чёрный список устройств без/с общим запретом, `restricted`,
восстановление. Во всех шести изменяющих фазах независимый контроль с роутера
получил proxy `204`. DNS-ошибок и TLS reset в этой матрице не было.
Первый запуск PowerShell-обвязки остановился до Android-проверки из-за проверки
массива строк через `-notmatch`; `finally` снял запрет. Повтор использует
`($result.Output -join "`n") -match ...`; ранний останов не засчитан как тест политики.

Дополнительно выполнены две фазы с `/etc/init.d/firewall reload`: общий запрет
обычного телефона и белый список устройств при общем запрете. Обе дали пять
совпавших probes и `OK (1 test)`, `fw4 check` успешен, PID Podkop сохранился,
контроль с роутера получил `204`. Ранний Sheepfold hook остался установлен.
После возврата телефона в `new` и снятия общего запрета финальные пять probes
успешны. Всего в этом проходе десять запусков Android gate, 50 совпавших probes.
Это проверка после reload, не измерение возможного интервала внутри его транзакции.

Обе службы оставлены работающими и в автозапуске. Наборы общего запрета,
чёрного списка устройств и `restricted` пусты. `cmp` подтвердил неизменность
`podkop`, `network`, `wireless`, `firewall`, `dhcp` относительно новой копии 0.8.
Локально прошли 16 проверок `routerInfo`/`firewallIntegration`, shell syntax,
ESLint и документационный аудит; `git diff --check` чистый. Impact advisor
предлагает `backendFast/tooling` из-за крупного legacy-файла, но изменение ограничено
двумя списками имён пакетов: незатронутые API/права/runner и Android UI не прогонялись.

Обнаружена B168: установленная диагностика писала `podkop_installed=no`.
В source helper добавлены `podkop-exp`/`luci-app-podkop-exp`. Проверка из отдельного
RAM-файла `router-control-candidate`, после сравнения SHA-256 и `sh -n`, дала
`podkop_installed=yes`, `podkop_version=0.8.1-r1`, `podkop_version_status=up_to_date`.
Постоянный helper r286 не заменяли; эта ошибка отображения исправлена в исходниках,
а не скрыта обещанием, что установленный пакет уже обновлён.

**Границы:** IPv6 и flow offload выключены; AdGuard Home, UDP/QUIC, reboot/power-loss,
OpenWrt 24.10, длительная стабильность и уже открытые TLS-соединения именно на 0.8
не проверены. Результат 0.7 для established-сокетов не переносится автоматически.
Исправление TPROXY обязательно: результат r286 с hotfix не доказывает безопасность
чистого r286. Наличие `up_to_date` не подтверждает latest release внешнего проекта.

## Сброс настроек и установка Podkop 23.10.2026

## Тестовый роутер

Желательно иметь отдельный роутер, который не является единственным домашним шлюзом семьи. Идеальная схема:

- роутер на актуальном OpenWRT;
- включён SSH-доступ;
- задан root-пароль;
- LuCI доступен из локальной сети;
- Sheepfold установлен из пакета формата целевой версии OpenWrt;
- есть хотя бы одно тестовое устройство в DHCP leases;
- желательно отдельно проверить сценарии с AdGuard Home, Podkop и без них.

Не использовать живой семейный роутер для write/hardware-тестов, если через него прямо сейчас работают работа, учёба, камеры, умный дом или мессенджер-бот.

## Профиль подключения

Исполняемый harness не хранит адрес, пароль или токены в репозитории. Команда
`npm.cmd run router:setup` создаёт несекретный профиль
`%LOCALAPPDATA%\Sheepfold\routerTest.json`, отдельный SSH-ключ и, по явному
параметру, защищённую Windows DPAPI копию учётных данных LuCI. Точная команда
первоначальной настройки приведена в
[`live-router-automation.ru.md`](live-router-automation.ru.md).

Переменные `SHEEPFOLD_ROUTER_HOST`, `SHEEPFOLD_ROUTER_USER`,
`SHEEPFOLD_ROUTER_SSH_PORT` и `SHEEPFOLD_ROUTER_IDENTITY_FILE` могут временно
переопределить SSH-поля готового профиля. Они не заменяют `router:setup`.
Переменной `SHEEPFOLD_ROUTER_API_URL` исполняемый harness не использует: URL LuCI
и порт Sheepfold берутся из профиля.

Разрешением изменять тестовый роутер служит сама явно выбранная команда
`router:install`, `router:writeSafe`, `router:runtimeMatrix` или
`router:fullSafe`. Старый флаг `SHEEPFOLD_ROUTER_WRITE_TESTS` текущему runner не
нужен. Hardware-in-loop сценарии пока не автоматизированы и не входят ни в один
из этих профилей.

## Уровень 1: read-only тесты

Эти тесты можно запускать чаще всего. Они не меняют постоянный UCI-конфиг,
установленные пакеты и runtime-политику Sheepfold. Harness создаёт только
изолированный временный каталог `/tmp/sheepfold-live-test-*`, копирует туда
проверяющие скрипты и удаляет каталог после прохода.

Если установлен helper QR v2, профиль сверяет `sheepfold-router-control tls-public-key-fingerprint` с независимым SHA-256 DER SubjectPublicKeyInfo из `/etc/uhttpd.crt`. Проверка пишет только временные файлы публичного ключа в `/tmp` и удаляет их; приватный ключ не копируется и не выводится (§tlspinv2).

Исполняемая команда:

```powershell
npm.cmd run router:readOnly
```

Что проверять:

- роутер отвечает по SSH;
- `/cgi-bin/sheepfold-api` отдаёт JSON с `app=sheepfold`;
- `/.well-known/sheepfold.json` существует и содержит `service=sheepfold`, версию, имя роутера и API base URL;
- `uci -q get sheepfold.global.ui_asset_version` совпадает с установленной версией пакета;
- `uci show sheepfold` содержит обязательные секции `global`, `allowlist`, `blocklist`, `no_restrictions`, `personal_devices`, дефолтного администратора и базовые настройки;
- `sheepfold-router-control status` отвечает без ошибки;
- `sheepfold-router-control router-info` отдаёт модель роутера, версию OpenWRT, статус интернета, Wi-Fi-модули, наличие AdGuard Home и Podkop;
- CGI endpoint `/router-info` не отдаёт Wi-Fi-пароли, токены, API-ключи, LuCI cookie, MAC-адреса клиентов и журнал;
- LuCI asset version в UCI не пустой;
- после установки нет очевидных неприменённых UCI-изменений Sheepfold;
- исполняемые файлы имеют нужные права: CGI, `init.d`, `sheepfold-router-control`, `sheepfold-device-detector`, `sheepfold-telegram-bot`.

Read-only тесты должны падать с понятной ошибкой: например, не `ECONNRESET`, а `роутер недоступен по SSH`, `Sheepfold API не установлен`, `ui_asset_version пустой`.

## Уровень 2: осторожные write-тесты

Исполняемый профиль запускается только явной командой:

```powershell
npm.cmd run router:writeSafe
```

Перед первым изменением harness вызывает `routerState.sh backup`, сохраняет
известные UCI-конфиги в архиве, копирует архив на Windows и сверяет SHA-256.
`routerState.sh restore` возвращает точные файлы `sheepfold`, `dhcp`, `wireless`
и `firewall` и побайтово сверяет их с backup. Сам `writeSafe` дополнительно
держит внутренний снимок Sheepfold, восстанавливает его и nftables runtime даже
при ошибке. Это шире простого `uci export sheepfold`, но не является резервной
копией всей системы.

Текущий `writeSafe` автоматически проверяет белый и чёрный списки устройств,
конфликт списков, блокирующие/разрешающие/ночные расписания, оба исхода конфликта
расписаний, группу «Без ограничений», приоритет чёрного списка устройств и
временный доступ. Ниже остаются дополнительные сценарии для расширения harness:

- создать тестовую группу, поменять цвет, привязать тестовое устройство, удалить группу;
- проверить, что группу с устройствами нельзя удалить без понятного предупреждения;
- сохранить настройки мессенджера с тестовыми значениями без реального токена;
- сохранить `log_cache_path` и убедиться, что путь не выходит за безопасную область;
- изменить настройку `ui_asset_version` в рамках теста и вернуть обратно;
- проверить, что `uci commit sheepfold` и apply проходят без зависшей LuCI-плашки;
- проверить, что экспорт журнала маскирует чувствительные поля.

Write-тесты не должны:

- менять Wi-Fi SSID/пароль;
- выключать Wi-Fi;
- перезагружать роутер;
- запускать WPS;
- менять firewall на постоянной основе;
- удалять реальные устройства пользователя;
- чистить пользовательские списки без восстановления.

### Матрица firewall и интеграций

<!-- §v7x2k9p -->

На отдельном тестовом роутере пройти четыре профиля: `none`, `adguard`, `podkop`, `adguard_podkop`. Это один firewall-движок Sheepfold, а не четыре реализации правил. Для каждого профиля:

- проверить `Выключить IPv6 на роутере`: без Podkop значение по умолчанию `Нет`, с Podkop — автоматически `Да`; после ухода с Podkop должны восстановиться прежние kernel-значения (§ipv6pod);
- импортировать резервную копию с включённым и выключенным IPv6 и убедиться, что runtime меняется сразу; обновление IPK не должно кратковременно возвращать старое состояние, а удаление пакета должно восстановить исходные kernel-значения, сохранив `/etc/config/sheepfold`;

- выполнить `fw4 print` и убедиться, что package drop-in файлы Sheepfold дают валидный ruleset;
- проверить наличие только собственных sets/chains `sheepfold_*` в `table inet fw4`;
- добавить тестовый MAC в чёрный список устройств и проверить отсутствие интернета и доступа к LuCI/SSH/API;
- создать для тестового устройства два пересекающихся расписания одного уровня с противоположными действиями; при `schedule_conflict_internet=off` проверить блокировку, при `on` — разрешение, а в обоих случаях наличие предупреждения/API-флага и ровно одной новой записи конфликта в журнале;
- отдельно проверить ночной интервал, например понедельник `22:00-07:00`, до и после полуночи, затем дождаться минутной границы без ручного сохранения и убедиться, что nftables и `/client-status` изменились согласованно;
- включить глобальную блокировку и проверить доступ настоящего allowlist/админского устройства, а также блокировку обычного устройства даже при ранее выданном временном доступе;
- выполнить `/etc/init.d/firewall reload` и убедиться, что фоновый сервис восстановил элементы Sheepfold sets;
- удалить пакет и убедиться, что собственные sets очищены, а чужие правила продолжают работать.

Для профилей с Podkop сохранить до теста вывод `nft list table inet PodkopTable`, `ip rule` и относящиеся к Podkop маршруты/марки, а после каждого действия сравнить их с исходным состоянием. Sheepfold не должен выполнять `flush ruleset`, удалять таблицу Podkop, менять packet marks, `ip rule`, `ip route`, Dnsmasq или sing-box. Для профилей с AdGuard Home отдельно проверить DNS после blocklist/global-block и после их отключения.

- при `site_filter_backend=auto` без AdGuard Home используется встроенный backend, а при профиле `adguard`/`adguard_podkop` локальный файл удаляется только после подтверждения фильтра `Sheepfold family site policy` через API;
- при `site_filter_backend=adguard` проверить правильные и неправильные credentials, недоступный API, выключенную DNS-фильтрацию AdGuard Home и ответ с повреждённым JSON: во всех ошибочных случаях LuCI показывает причину и реально работает встроенный fallback;
- при `adguard_auto_manage=0` Sheepfold не вызывает `add_url`, `set_url` или `refresh`, удаляет собственную локальную политику только как осознанную ручную передачу и показывает жёлтый непроверенный статус;
- до и после refresh сравнить пользовательские фильтры и custom rules AdGuard Home: Sheepfold не изменяет их, не вызывает `filtering/set_rules` и управляет только своим URL-фильтром;
- переключить backend с AdGuard Home на Sheepfold и обратно; старый управляемый фильтр отключается, а ошибка отключения даёт предупреждение о возможном двойном применении без потери встроенной фильтрации;
- изменить DHCP-адрес тестового устройства и проверить обновление `$client=<IPv4>` после события аренды; устройство без актуального IPv4 вызывает fallback, а не ложный зелёный статус;
- получить локальную ленту правильным токеном с `127.0.0.1`, затем проверить отказ по неверному токену и с LAN-адреса; пароль и токен не появляются в status, системном журнале и безопасном экспорте;
- устройство строгой группы открывает разрешённый домен и аварийно-полезный сайт, но не открывает случайный сайт, прямой IP и произвольный не-web порт;
- каждый режим чёрного списка сайтов затрагивает именно нужные устройства; исключённое из чёрного списка сайтов устройство всё равно блокируется глобальной кнопкой;
- чёрный список устройств остаётся сильнее доменных правил и закрывает LuCI, SSH и Sheepfold API;
- при dnsmasq без `nftset` строгая группа не теряет весь интернет, локальная фильтрация не считается активной, а администратор получает одно уведомление;
- ошибка `dnsmasq --test`, ошибка перезапуска DNS и ошибка `sheepfold-firewall domain-reset` сохраняют прежний DNS-файл, прежний marker готовности и прежние nftables-наборы;
- параллельный update/tick не оставляет частично применённое состояние, а просроченный lock восстанавливается;
- неожиданно укороченный либо полностью плохой внешний источник не заменяет последнюю рабочую копию; после трёх неудачных циклов приходит уведомление, после восстановления — одно сообщение о восстановлении;
- перезапуск firewall и роутера восстанавливает политику после загрузки RAM-кэша без изменения таблиц и marks Podkop;
- общий CDN-адрес проверяется отдельно: возможная побочная блокировка фиксируется как известное ограничение, а не объявляется успешной точной фильтрацией;
- DoH, внешний DNS, VPN и прямой IP проверяются как известные пути обхода. Текущая версия не должна обещать их блокировку.

До успешного прохождения этой матрицы новый firewall-код нельзя считать готовым к слиянию, даже если локальные статические тесты зелёные.

## Уровень 3: установка и обновление пакета

Эти тесты проверяют оба полных пути: `.ipk -> opkg -> LuCI/backend` и `OpenWrt .apk -> apk v3 -> LuCI/backend` (§pkgmgr1).

Для роутера с `opkg` harness по умолчанию собирает тестовый IPK. Можно явно
передать уже проверенный файл:

```powershell
npm.cmd run router:install
npm.cmd run router:install -- -IpkPath C:\path\to\sheepfold.ipk
```

Для OpenWrt с `apk` требуется пакет, собранный официальным SDK в GitHub Actions:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass `
  -File tools\router-testing\runRouterTests.ps1 `
  -Profile install `
  -ApkPath C:\path\to\sheepfold.apk
```

Набора `tests/router-install/*.test.mjs` в проекте нет: реальную установку
выполняет PowerShell harness, а `tests/liveRouterHarness.test.mjs` статически
защищает его стоп-правила и команды, не устанавливая пакет.

Автоматически проверяются выбор системного менеджера пакетов, внешний backup,
SHA-256 переданного пакета, установка и post-install профиль `readOnly`.
Следующие сценарии остаются отдельными ручными либо будущими тестами:

- проверить, что менеджер пакетов принимает контейнер, а внутренние имя, версия и архитектура совпадают;
- проверить, что `postinst` исполняемый и завершается без `Permission denied`;
- проверить, что default config создан, если его не было;
- проверить, что существующий `/etc/config/sheepfold` не затирается при обновлении;
- через штатную кнопку установить нормальный release asset и убедиться, что журнал показывает подтверждённую установленную версию;
- в отдельном контролируемом тесте подменить ответ загрузчика повреждённым файлом и убедиться, что установка не запускалась;
- в отдельных wrapper-тестах заставить `opkg` и `apk` вернуть ненулевой код после изменения копии конфига: updater должен вернуть тот же код и восстановить исходный файл;
- проверить, что новая версия записалась в `ui_asset_version`;
- проверить, что `/.well-known/sheepfold.json` обновился;
- проверить, что service/init script отвечает;
- проверить, что uninstall удаляет пакет без удаления пользовательских списков.

Перед тестом обновления нужно иметь внешний backup `/etc/config/sheepfold`. Встроенное восстановление UCI проверяется отдельно и не считается откатом бинарных файлов пакета (§updsafe).

## Уровень 4: LuCI через браузер

Эти тесты можно делать Playwright-скриптом против реальной LuCI-страницы тестового роутера.

Что проверять:

- вход в LuCI с тестовым паролем;
- открытие страницы Sheepfold без `RPCError`;
- верхние вкладки растянуты и выделяются;
- таблица “Все устройства” помещается без горизонтальной прокрутки на стандартной ширине;
- команды «Интернет включить» и «Интернет выключить» отделены от текста текущего состояния; неизвестное состояние не выглядит подтверждённым разрешением;
- настройки сохраняются только через кнопку `Сохранить`;
- после сохранения появляется центральное уведомление `Настройки успешно сохранены`;
- модалки администраторов, выбора устройств, групп и аварийно-полезных сайтов не выходят за экран;
- при изменении белого/чёрного списка не остаётся системная LuCI-плашка “не принятые изменения”;
- CSS/JS обновляются после поднятия `ui_asset_version`, без ручной очистки кэша.

## Аварийно-полезные сайты

Подробная матрица и ограничения описаны в [`emergency-sites-runtime.ru.md`](emergency-sites-runtime.ru.md) (§emerg1). На живом роутере обязательно проверить сохранение UCI-карточек, dnsmasq с `nftset` и без него, IPv4/IPv6, глобальную блокировку, расписание и чёрный список устройств. Для чёрного списка устройств разрешённый сайт может открываться, но LuCI, SSH и Sheepfold API должны оставаться недоступными.

Для этих тестов нужен отдельный тестовый пользователь/пароль LuCI или явное указание, что используется тестовый root-пароль. Пароль нельзя хранить в репозитории.

## Уровень 5: hardware-in-loop

Это самые рискованные тесты. Они трогают физическое состояние роутера и сети.
Автоматического runner для них пока нет. Будущий runner должен требовать
отдельное явное согласие, например `SHEEPFOLD_ROUTER_HARDWARE_TESTS=1`, но
сегодня установка этой переменной сама по себе ничего не запускает.

Что можно проверять:

- включение/выключение Wi-Fi по команде Sheepfold;
- дисклеймер и задержку подтверждения перед настройкой авто-выключения Wi-Fi;
- WPS-режим “дать подключиться к Wi-Fi”;
- WPS-режим “дать подключиться к Wi-Fi и добавить устройства в белый список” только на отдельной тестовой сети;
- LED-режимы: дефолтное поведение, отключение, сигнал о новом устройстве;
- возврат LED к дефолтному поведению после входа в LuCI или просмотра уведомления администратором;
- реакцию Sheepfold после `fw4 restart`, `network reload`, `rpcd restart`, `uhttpd restart`, reboot роутера.

Hardware-тесты должны всегда показывать предупреждение перед запуском. Нельзя запускать их автоматически в обычном CI.

## Тесты с Android-приложением

Android-тесты с живым роутером стоит делать отдельно от unit-тестов APK.
Подготовка AVD, instrumented smoke, физические телефоны и граница эмулятора
описаны в [`android-test-lab.ru.md`](android-test-lab.ru.md) (§andlab1). Текущий
Android runner сам не подключается к роутеру и не меняет его состояние.

Что проверять:

- Android видит `/.well-known/sheepfold.json` в локальной сети;
- QR из LuCI успешно привязывает телефон к выбранному администратору;
- одноразовый код после успешной привязки больше не работает;
- телефон появляется в списке устройств как админское устройство;
- у устройства появляется корона;
- в таблице администраторов устройство появляется в списке “Админские устройства”;
- смена порта Sheepfold на роутере доходит до APK;
- Android не продолжает первичную настройку через мобильную сеть;
- Android показывает предупреждение про реальный MAC, но не блокирует настройку, если это текущая выбранная логика;
- AI-помощник получает router-info/log context только после явных галочек.

## Импорт и резервные копии

Сценарии из [`settings-backup.ru.md`](settings-backup.ru.md) выполнять только после отдельной копии `/etc/config/sheepfold`, `/etc/config/dhcp` и `/etc/config/wireless` по SSH.

Проверить два маршрута:

- читаемый JSON сохраняет текущие совпадающие секреты, но не переносит их на чистый роутер;
- зашифрованная копия восстанавливает секреты только с правильным паролем.

После импорта сверить UCI, nftables-наборы, постоянные DHCP-аренды, SSID/каналы и повторное открытие LuCI после Wi-Fi reload. Повреждённый файл, неверный пароль и конфликт белого/чёрного списков устройств не должны менять конфиг. Bearer-токены Android не переносятся: приложения на другом роутере сопрягаются заново. (§cfgbak1)

## Стоп-правила

Тест должен немедленно остановиться, если:

- роутер не отвечает по SSH;
- не удаётся создать backup UCI;
- router host не похож на ожидаемый тестовый адрес;
- изменяющий профиль не был выбран явно либо для будущего hardware-теста не дано отдельное согласие;
- текущий default gateway компьютера совпадает с тестовым роутером, а тест собирается выключать Wi-Fi или перезагружать сеть;
- в `/etc/config/sheepfold` найдены реальные токены Telegram/VK/AI, а тест не read-only;
- невозможно восстановить backup после write-теста.

## Безопасность тестов

- Не хранить root-пароль, LuCI cookie, Telegram/VK token, AI API key и Wi-Fi-пароли в тестовых файлах.
- Не выводить секреты в stdout/stderr.
- Все тестовые MAC-адреса должны быть явно помечены как тестовые.
- Перед write-тестом сохранять backup, после теста восстанавливать.
- Для тестов списков использовать отдельный фиктивный MAC, которого нет среди реальных устройств.
- Для тестов Telegram/VK использовать отдельного тестового бота или mock-режим.
- Для тестов AI использовать fake provider/mock endpoint, если задача не проверяет реальный провайдер.

## Порядок внедрения

1. Готово: read-only тесты SSH/UCI/backend, права файлов и структура установленного пакета.
2. Готово: установка IPK с внешним backup, SHA-256 и post-install проверкой.
3. Готово: восстанавливаемые write-тесты списков устройств, расписаний, временного доступа и группы «Без ограничений» с фиктивным MAC.
4. Готово: read-only Playwright smoke-тест LuCI на desktop/mobile.
5. Готовы основа API 28/35 instrumented-стенда, smoke первого запуска и отдельный безопасный parent-router runner. QR из файла и paired-read проверены на API 30; камера, минимальная версия Android и разрушительные lifecycle-сценарии этим не закрыты. См. `docs/android-test-lab.ru.md`.
6. После отдельной разработки стоп-правил: hardware-in-loop тесты Wi-Fi/WPS/LED.

Главная идея: живой роутер нужен не для того, чтобы заменить unit-тесты, а чтобы ловить реальные OpenWRT-ошибки, которые невозможно честно увидеть в обычном Node/Android тесте.
