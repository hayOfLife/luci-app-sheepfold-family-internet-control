# Sheepfold r298: аудит просьб ребёнка о дополнительном времени

<!-- §child30 §testwhy §docops1 -->

Дата: **09.09.2026**. База: принятый владельцем `bdb3a92c699618dee229b145039d0811b642a7b1`.
Версия роутерных пакетов: **0.1.0-298**. Ветка: `main`.
Новые изменения локальные: push, установка на роутер и публикация релиза не выполнялись.

## Результат и граница изменений

Исправлены **B61–B64** в двух исполняемых файлах: `sheepfold-access-request` и
`root/www/cgi-bin/sheepfold-api`. Полные карточки с альтернативами и ограничениями
находятся в [реестре ошибок](bug-register.ru.md). Реестр содержит 64 карточки,
а не 64 независимо подтверждённые уязвимости.

Главная функциональная ошибка воспроизведена без искусственного отказа:
зарегистрированный ребёнок при включённом согласии родителя не мог отправить
просьбу. Общая переменная `section` после проверки согласия указывала уже на
администратора. Настоящий `sheepfold-device-id ensure` отклонял эту секцию, а CGI
возвращал `404 device_not_registered`. Исправление ограничивает область переменной
цикла и проверяет успешность получения ID, не обходя проверку типа секции.

Дополнительно устранены зависимость результата уже записанной просьбы от журнала,
преждевременный HTTP 200 при отказе чтения списка и неправильное экранирование
управляющих символов в JSON.

Не менялись выдача интернета, firewall, квоты, авторизация, список разрешённых домашних
маршрутов, настройки согласия родителей, формат очереди и код обоих Android-приложений.
Просьба по-прежнему не выдаёт 30 минут автоматически. D01 — «Без ограничений» выше
чёрного списка устройств для интернета при независимых management deny и карантине —
сохранено без изменений.

Принятые владельцем изменения тестового runner, Windows-путей и CI не откатывались.
Добавлены только карта нового fixture, его потребитель и категории нового теста;
существующий алгоритм выбора и запуска проверок не переписан.

## Карточки исправлений

| ID | Наблюдаемое последствие | Исправление | Почему |
|---|---|---|---|
| B61 | Зарегистрированный ребёнок получает 404; частичный ID мог считаться подтверждённым | Локальный `section` в проверке opt-in; проверка exit получения ID | Не меняем identity-проверку и не подменяем ошибку backend отсутствием устройства |
| B62 | После записи просьбы возвращается ошибка либо испорченный JSON | Изоляция stdout/stderr журнала, резервный syslog, предупреждение без смены результата | Побочная диагностика не должна отменять уже записанное действие |
| B63 | Родитель получает 200 с пустым/обрезанным телом при отказе helper | Буферизация результата и проверка exit до HTTP-заголовка | Только успешно завершённое чтение можно объявлять успешным |
| B64 | Управляющий символ в имени ломает весь JSON списка | Экранирование строк без уничтожения UTF-8 | Изменяем представление данных, не пользовательский текст |

## Точные изменения API

| Запрос и ситуация | Ответ r298 |
|---|---|
| `POST /access-request`, правильное устройство, opt-in включён | Прежний `200`, `requestId`, `duplicate` |
| Та же просьба повторно, последовательно | Прежний ID, `duplicate=true`, без нового события журнала |
| Устройство действительно не найдено | Прежний `404 device_not_registered` |
| Настоящий helper ID завершился ошибкой, даже после вывода числа | `503 access_request_unavailable`; запись просьбы не создаётся |
| Администраторское устройство пытается просить доступ | Прежний `403 administrator_device` |
| Никто из администраторов не принимает просьбы | Прежний `403 access_requests_disabled` |
| `GET /access-requests`, helper завершился с ошибкой или отсутствует | `503 access_requests_unavailable`, без частичного списка |
| Корректно прочитанная пустая очередь | Прежний `200` с `requests: []` |
| Родитель отказался от получения просьб | Прежний пустой список; сохранённые просьбы не потребляются |

`GET /access-requests` по-прежнему проходит `require_admin` и внешнюю квоту.
Домашняя сеть не получает новый доступ к `POST /access-request`.

Просмотрены непосредственные клиенты: `RouterAdminClient.loadChildAccessRequests`
использует общий обработчик неуспешного HTTP и не превращает 503 в пустой список;
детский `ClientStatusRepository.requestThirtyMinutes` проверяет HTTP и `ok`.
Kotlin не изменялся. Это сверка исходников и существующих контрактных тестов,
не JVM-прогон, не проверка физического телефона и не новая Android-сборка.
Новые коды не включены в отдельную локализованную карту клиентов: в этих версиях
используется существующее общее отображение ошибок. Автоповтор POST не добавлен.

## Как проверялось

### Среда и изоляция

Linux, Node.js 22.16.0, Python 3.13.5, системный `sh`; для синтаксиса также BusyBox ash.
Тестам не нужны роутер, телефон, реальные токены, внешняя сеть или root-доступ.
Все подменяемые пути находятся в `.build/test-fixtures`, удаляются в `finally`.

Новый fixture переносит по локальным путям настоящие CGI, helper очереди и
`sheepfold-device-id`. Модель UCI поддерживает чтение и регистрирует операции записи;
она не моделирует native UCI/pending-очереди и не доказывает корректность commit.
DHCP/ARP и администратор синтетические. Отдельные нижележащие тесты журнала/записи
используют явный stub ID, чтобы не маскировать их первичной ошибкой B61.

Подставленные `mkdir`, `mv`, ID-helper и оба журнала пишут trace перед отказом.
Тест проверяет этот trace. Автоматического переключения на BusyBox shell в новом
fixture нет: иначе встроенный applet может обойти подставленную команду. Проверка
`busybox ash -n` доказывает только синтаксис и не считается повтором fault-сценариев.

### Точный выборочный запуск

Из корня checkout в Linux с доступными Node, Python, POSIX sh и `flock`:

```sh
node scripts/run-test-category.mjs --file childAccessRequestRuntime.test.mjs --file childAccessRequest.test.mjs --file apiRateLimitRuntime.test.mjs --file tokenAuthenticationRuntime.test.mjs --file homeNetworkAccess.test.mjs --file deviceStableId.test.mjs --file packageHardeningRuntime.test.mjs --file parentRouterIntegration.test.mjs --file changeImpact.test.mjs --file testCategories.test.mjs
```

Фактически: **170 тестов в 10 файлах, 170 pass, 0 fail/skip/cancel**. Exit 0.
Файлы запускались последовательно отдельными процессами существующего runner.
Новые runtime-сценарии: **26**. На неизменённой принятой базе `bdb3a92` те же
сценарии дают **15 fail / 11 pass**; на исправлении **26 pass**.
Пятнадцать отказов — не пятнадцать отдельных дефектов: часть сценариев ловит одну
причину в разных слоях и некоторые проверки защищают прежнее правильное поведение.

Прямой короткий прогон нового теста:

```sh
node --test tests/childAccessRequestRuntime.test.mjs
```

Ожидаются exit 0 и 26 pass без пропусков. Для сравнения с исторической базой можно
указать `SHEEPFOLD_REQUEST_TEST_SOURCE` — абсолютный путь к checkout `bdb3a92`.
Это меняет только источник переносимых исполняемых файлов, не assertions теста.
Исходные и промежуточные результаты сохранены в архиве поставки, не переписаны как
успешные. Отсутствие host-утилиты, timeout либо невызванный fault-tool не является
подтверждением исправления.

### Почему не запущен весь проект

`quality:plan` прочитан и сохранён. Его консервативное правило для общего CGI и
Makefile рекомендует широкий барьер. Ручной разбор diff ограничил влияние двумя
маршрутами просьб и версией: нет изменений общих `require_admin`, rate limiting,
парсера формы, протокола токенов или остальных веток dispatch. По явному решению
владельца выполнены прямые тесты и непосредственные соседи, не полный suite.

Матрица `mandatory-companion-changes`: проверены строки CGI/API, shell-helper,
package release и тестовые зависимости. Новый UCI-параметр, миграция, APK,
визуальный интерфейс и геометрия значков не добавлялись, поэтому соответствующие
сборки/визуальные проверки не заявляются и не запускаются как несвязанные.

### Упаковка и статические проверки

```sh
python3 scripts/build-test-ipk.py --variant all
node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
node scripts/checkDocumentation.mjs --all
node scripts/runQualityChecks.mjs --git bdb3a92 --plan
busybox ash -n package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-access-request
busybox ash -n package/luci-app-sheepfold-family-internet-control/root/www/cgi-bin/sheepfold-api
git diff --check
```

Сборки остаются внутри `.build/ipk-output`. Это тестовые IPK, не каноническая
SDK-сборка и не установленные пакеты. Журналы упаковки, сверка payload с исходниками,
права файлов и hardening распакованных редакций включаются в архив проверок.

Фактически собраны обе редакции; 24 проверки `testIpkPermissions.test.mjs`
прошли на Standard и повторно на AI Support. Это одни и те же 24 сценария,
не 48 уникальных тестов. Исправленные helper и CGI совпадают с результатом
канонического `transform_payload` соответствующей редакции; оба имеют 0755.
Hardening обоих распакованных rootfs завершился с exit 0. Проверка Markdown:
264 файла, без ошибок. Синтаксис: 2 shell-файла и 5 изменённых JavaScript-модулей.

Первый дополнительный verifier ошибочно ожидал разные поля `Package:` у двух
редакций и отказал. Это ошибка нового проверочного скрипта, не дефект продукта:
канонический `package_name(variant)` намеренно один, различаются имена артефактов.
Verifier исправлен по существующему контракту, production и assertions штатных
тестов не ослаблялись. Неуспешный лог сохранён отдельно от окончательного.

ESLint запустить не удалось: локальных зависимостей нет, `npm exec --offline -- eslint`
завершился `ENOTCACHED`. Синтаксический `node --check` не заменяет ESLint. Зависимости,
lockfile, Gradle и CI не менялись ради обхода этой ошибки.

## Известные ограничения и следующий аудит

Очередь просьб пока не является транзакционной: параллельные create/list/cleanup
не согласованы одной блокировкой. `value_from_file` по-прежнему отдельно читает
поля и подавляет часть ошибок; cleanup может трактовать их как повреждение.
Новое правило HTTP проверяет **сообщённый exit helper**, а не доказывает, что
сам helper обнаружил абсолютно каждый внутренний отказ. Не заявлены проверка всей
схемы файла, atomic snapshot очереди, монотонный TTL и сохранность после reboot.
Эта область записана как R11 для следующего узкого прохода, без статуса «исправлено».

Открыты прежние R01–R10: native UCI и параллельные writers, flow offloading,
восстановление после потери питания, аппаратный Wi-Fi, сеансы и экспериментальные
функции. Успешные исторические Android/SDK/CI-прогоны базы из отчёта владельца
не отменены, но не приписываются новому r298. Роутер и телефон здесь не использовались.

## Технический источник

[RFC 8259, раздел 7](https://www.rfc-editor.org/rfc/rfc8259) проверен 09.09.2026:
JSON требует escaping кавычки, обратной косой черты и управляющего диапазона.
Он объясняет B64, но не является доказательством исполнения кода Sheepfold.
Страница POSIX shell в этом проходе не открылась; её свежая внешняя проверка не
заявляется. Семантика переменной B61 подтверждена запуском реальных скриптов.

## Проверка поставки

Итоговый bundle должен восстанавливаться в `main` с предком `bdb3a92` и всей
достижимой исходной историей. ZIP сверяется с деревом коммита. Контрольные суммы,
точный итоговый SHA, `git fsck` и повтор нового теста из восстановленного bundle
фиксируются в отдельном машинном протоколе архива проверок. Они не заменяют push.
