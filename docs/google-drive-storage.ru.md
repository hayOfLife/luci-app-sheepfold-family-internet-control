# Google Drive для журналов и бэкапов

## Статус реализации

CLI backend:

```text
/usr/libexec/sheepfold/sheepfold-google-drive
```

Диспетчер: `sheepfold-log-storage` (значение `log_storage=google_drive`).

Авторизация: **OAuth2 refresh token** + Google Drive API v3 (через `curl`).

## UCI

```uci
config global 'global'
    option log_storage 'google_drive'

config google_drive 'gdrive'
    option client_id ''
    option client_secret ''
    option refresh_token ''
    option root_folder '/sheepfold'
    option quota_mb '500'
    option authorized '0'
```

## Подключение (MVP)

1. Создайте проект в [Google Cloud Console](https://console.cloud.google.com/).
2. Включите **Google Drive API**.
3. Создайте OAuth client типа **Desktop app**.
4. Получите **refresh token** на ПК (OAuth Playground или свой скрипт) с scope `https://www.googleapis.com/auth/drive.file`.
5. В LuCI: **Настройки → Управление памятью роутера** → **Google Drive** → вставьте client ID, client secret и refresh token.

## Структура на диске

```text
/sheepfold/logs/events.log
/sheepfold/logs/<timestamp>-*.tar.gz
/sheepfold/backups/sheepfold-config-YYYYMMDD-HHMMSS.tar.gz
```

## Команды

```text
sheepfold-google-drive status|test|list|download|restore-config|sync-status|push-events|archive-push
```

LuCI вызывает через `sheepfold-router-control`: `google-drive-test`, `google-drive-list`, `google-drive-restore-config`, `google-drive-sync-status`.

## Граница проверенной загрузки r304

В r304 исправлены `push-events`, загрузка существующих архивов из `archive-push`
и используемые ими функции. Сначала подготавливается закрытый снимок файла,
затем отправка, затем отдельный запрос метаданных `files.get` с `fields=id,size`.
Только соответствующий ID и совпадающий нормализованный размер позволяют
считать эту проверку успешной. У исходного файла проверяется отсутствие
наблюдаемого изменения относительно снимка. Ошибка оставляет исходный архив.

Это проверка размера, не контрольной суммы; ошибку ответа после записи нельзя
считать доказательством отсутствия изменений на Drive. `verify <local> <bytes>`
остаётся локальной проверкой переданного размера. Для JSON-метаданных используется
штатная зависимость `jshn`, не AI-only библиотека.

Самостоятельные list/download/restore и остальные старые readers не объявлены
работающими после этой правки: в них остаются известные или непроверенные проблемы.
Подключение к настоящему аккаунту, OAuth refresh, libubox на роутере, квоты,
пагинация, конкурентные отправители и восстановление конфигурации требуют отдельного
проверочного прохода. Закрытый снимок увеличивает потребление RAM.

Подробности: [B82–B84 и R14](bug-register.ru.md),
[команды и доказательства r304](audit-fixes-r304.ru.md).


## OAuth и RAM-кэш: граница r305

B85–B87 проверяют обновление токена по refresh token: точное URL-кодирование формы,
exit curl, HTTP 200 и типизированный JSON. Используется штатный jshn; отказ его
исполняемого парсера не скрывается eval. Положительный expires_in обязателен;
пустой/неверный срок не становится разрешением использовать токен 3000 секунд.
Необязательный отсутствующий client_secret допустим.

TOKEN_CACHE теперь связан с client_id/client_secret/refresh_token через SHA-256
разделённых полей, содержит issued_at/expires_at и используется только при
совпадающих реквизитах и подтверждённом времени. Старый формат кэша обновляется
через OAuth, без использования старого токена как запасного после смены аккаунта.
Реквизиты перечитываются перед возвратом результата. Это не общая UCI-транзакция.

Подготовка в RAM: каталоги 0700, файлы 0600; секреты передаются curl через закрытые
файлы, не аргументы со значениями. Целевой кэш не должен быть symlink/каталогом.
Проверенный временный JSON публикуется rename; обработанный отказ не обнуляет
прежнюю запись. Следующая проверка всё равно отвергнет её при другом контексте.

Охваченный exchange проверен моделью HTTP, не настоящим Google. FOLDER_CACHE не
связан с новым аккаунтом; поиск, квоты, restore, общий статус authorized и
параллельные writers остаются R14. Проверка 64 КиБ выполняется после загрузки
OAuth-ответа, не ограничивает его потоковый расход RAM. Короткие действующие
токены не кэшируются с выдуманным длинным сроком. SIGKILL-cleanup не гарантируется.

Подробности: [B85–B87 и R14](bug-register.ru.md), [отчёт r305](audit-fixes-r305.ru.md).


## Точный поиск и кэш папок: граница r306

B88–B90 используют типизированный JSON для точного поиска папки/файла. HTTP или
transport-отказ не равен отсутствию. Только полный пустой `files` разрешает
создание; единственный ID — обновление. Дубли, `nextPageToken` или
`incompleteSearch=true` останавливают действие. Автоматическая чистка дублей и
обход страниц не добавлены. Запросы файлов исключают папки по MIME-типу.

Апостроф и backslash экранируются в языке Drive, затем curl кодирует весь параметр
через `--get --data-urlencode`. UTF-8 и значимые печатные символы сохраняются;
управляющие символы и превышение границ не заменяются другим именем. Отказ чтения
заданной root_folder не включает стандартную папку; отсутствие подтверждается UCI.

Кэш `.gdrive-folders.json` готовится закрытым файлом и публикуется rename после
проверок. Reader проверяет целый JSON и допустимые ID, а не частичный вывод.
Symlink/каталог по имени кэша отклоняются. При ошибке публикации прежний файл
сохраняется. Это **не привязка FOLDER_CACHE к аккаунту или root_folder** и не
общая транзакция разных отправителей. Смена контекста, непрерывная квота RAM,
привилегированные подмены и аварийная очистка остаются R14.

Обычный `test` по-прежнему сообщает об авторизации, а не гарантирует готовность
папок и резервной копии. Самостоятельные list/download/restore не включены в
исправленный путь. Подробности: [B88–B90](bug-register.ru.md),
[воспроизведение и команды r306](audit-fixes-r306.ru.md).


## Актуальное уточнение r307: назначение папок и контекст операции

B91–B92 дополняют исторические границы r305–r306. `context_key` папок связан
с проверенными client_id/client_secret/refresh_token и нормализованной root_folder.
Reader не использует старые ID после смены этих полей. Исправный legacy-кэш без
ключа требует повторного поиска; повреждённый формат отклоняется. При ошибке
поиска старые ID не становятся резервным вариантом. Сам ключ не удостоверяет
личность Google-пользователя или текущую структуру папок на сервере.

Активные push-events/archive-push фиксируют раздел настроек, наследуют его во
вложенных вызовах и останавливаются при обнаруженной смене или ошибке чтения.
Проверки стоят вокруг HTTP и перед публикацией кэша/подтверждением/удалением
архива. Уже отправленный запрос может завершиться на стороне Google: это не
откат. Автоматический повтор с другим аккаунтом не введён. Одновременная правка
любого поля раздела может консервативно остановить активную операцию; между
самостоятельными вызовами изменение одной квоты не меняет ключ папок.

Прежние рабочие форматы token cache и успешных CLI-ответов сохранены. Секреты
не дублируются в folder cache. Нет общего lock UCI и облачных writers, не закрыты
ABA/окно после check, серверное перемещение папок, подтверждение ACL, quota/list/
download/restore и аварийная очистка. Новых native/libubox/live-аккаунт доказательств
нет. [B91–B92 и R14](bug-register.ru.md), [отчёт r307](audit-fixes-r307.ru.md).


## Актуальное уточнение r308: расход и очистка квоты

B93–B94 проверяют целый список текущих файлов logs и backups, HTTP и JSON,
принадлежность папке, размеры, уникальность ID и полноту ответа. Сумма включает
обе папки, но cleanup удаляет только допустимые журналы .log/.tar/.tar.gz из logs.
Порядок — modifiedTime,name. Неизвестный расход не становится 0/100% свободного:
status возвращает state=error; archive-push сообщает ошибку квотной стадии.

Предел локальной обработки — 200 объектов и 256 КиБ ответа на папку. Следующая
страница/incompleteSearch означают отказ, не частичный подсчёт или удаление.
Полная пагинация не реализована. После каждого DELETE расход перечитывается;
сбой или отсутствие подтверждённого уменьшения останавливают проход. Backups,
подпапки и посторонние расширения не удаляются ради квоты.

Уже выполненные удалённые действия не откатываются. Сумма — не общая квота
Google, не история версий и не рекурсивный размер папок. Нет общей блокировки
серверных изменений или гарантии происхождения вручную помещённого .log.
Постпроверка размера ответа не заменяет потоковый RAM-лимит. Успешный status
пока сохраняет authorized прежним общим UCI commit; это остаётся R03/R14.
См. [B93–B94](bug-register.ru.md) и [команды/доказательства r308](audit-fixes-r308.ru.md).
