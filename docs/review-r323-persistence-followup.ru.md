## Исходная точка и результат

Работа продолжает `sheepfold-r323-review-import.patch` и соответствующий ZIP,
а не чистый r323 без защитных правок. Перед редактированием патч восстановлен
поверх исходного bundle. Предыдущие правки сохранены в индексе отдельной рабочей
копии как база delta; **индекс не является новым коммитом**.

Исправлены две воспроизведённые группы:

| Карточка | Результат |
| --- | --- |
| B142 | Поздняя локальная правка больше не принимается за собственную часть операции: замечанный конфликт останавливается до save без удаления смешанного черновика |
| B143 | Импорт сверяет текущий управляемый LuCI-кэш после ожидания очереди и не подставляет старый секрет при обнаруженном расхождении |

[Реестр](bug-register.ru.md) содержит **143 карточки**. Прежняя сводная строка
ошибочно оставалась равной 138 при наличии B139–B141; исправлено именно число в
шапке, исторические карточки не перенумерованы и не выданы за новые находки.
Подробное описание причин, решений и альтернатив находится в B142–B143.

Автоматический `archive-push` обоих облаков остаётся запрещённым с
`config_backup_unavailable`. Переданные ранее незашифрованные копии не удалялись.
Браузерный экспорт, формат шифрования, правила firewall, Android, backend, CI и
исполняющие runner-скрипты этой итерацией не менялись. Обновлены только непосредственные
модули, переводы, два mock-потребителя, навигация тестов и документация.

## B142: неправильный момент определения владельца изменений

Прежняя последовательность была такой:

```text
чистый локальный staging → проверка remote changes → stage
→ Promise yield → другой callback изменяет staging
→ ownedFingerprint включает чужую правку → save → apply → confirm
```

Новое поведение:

```text
stage → ownedFingerprint
→ Promise yield → замечено изменение относительно ownedFingerprint
→ uci_concurrent_local_changes, без save/apply/confirm/revert/unload
```

В тестах существуют отдельные local staging, переданные данные и сохранённые
значения. Прежний адаптер действительно передаёт неподтверждённую опцию в модель
save. Проверены также добавление и удаление секции, флаг перестановки. После
исправления не вызывается save вообще, поэтому результат не зависит от того,
сразу или позже сетевой слой превращает аргументы в JSON. Обе части смешанного
черновика остаются локально. Повтор без разбора очереди отказывает; автоматического
сохранения или удаления нет.

**Важная доработка первоначального решения.** Сначала была опробована передача в
save в том же JavaScript-turn. Первые упрощённые проверки с синхронным снимком
save проходили, но это было недостаточным доказательством. Дополнительная сверка
первичного LuCI показала, что request может отложить сериализацию, а некоторые
аргументы передаются по ссылке. Добавлена отдельная модель отложенного RPC:
промежуточное решение всё ещё передавало чужую опцию. Оно заменено отказом при
замеченном конфликте; промежуточный исходник и его неуспешный тест сохранены в
доказательствах, а не объявлены финальным успехом.

Первичные источники, просмотренные 13.09.2026:
[LuCI uci.save](https://openwrt.github.io/luci/jsapi/uci.js.html),
[RPC declare/call](https://openwrt.github.io/luci/jsapi/rpc.js.html),
[Request.request и flushRequestQueue](https://openwrt.github.io/luci/jsapi/luci.js.html).
В рассматриваемом источнике save формирует RPC-задачи, а request использует
Promise и очередь batch с последующей сериализацией. После RPC UCI также делает
unload/load. Это внешняя сверка контракта, **не установленная версия роутера и
не испытание настоящего браузера/rpcd**.

Отказ без cleanup выбран сознательно: после смешения адаптер не может безопасно
определить, какие общие данные разрешено удалить. При этом собственная подготовка
также остаётся несохранённой; обновление страницы может потерять её вместе с
другим локальным вводом. Нужен явный разбор черновика. Нормальная очистка после
ошибки собственной подготовки и после save-failure не отключена.

## B143: ожидание очереди не обновляло previousPayload

Контроллер получает текущий снимок до ожидания общей очереди. Предшествующий save
успевает сохранить новое значение, после чего импорт читает старый previous и
использует его при подстановке `[secret]`. В проверке читаемой Wi-Fi-копии:

| Этап | Прежний кандидат | Новый кандидат |
| --- | --- | --- |
| Предыдущая операция сохраняет ключ | `new-synthetic-value` | `new-synthetic-value` |
| Ожидающий импорт рассматривает старый current | Отправляет `old-synthetic-secret` | Обнаруживает различие до staging |
| Второй save | Выполняется | Не выполняется |
| Подтверждение импорта | Успех модели | `backup_current_settings_changed` |
| Явный повтор со свежим current | Отдельный сценарий | Успешен; новый секрет сохраняется |

Читается управляемая часть **загруженного кэша LuCI**, а не запрашивается новый
глобальный снимок роутера. Проверка выполняется внутри очереди перед stage. Она
не меняет данные при обнаруженном расхождении и не переигрывает выбор переноса
идентичности без пользователя. Порядок ключей опций игнорируется, порядок секций
и списков учитывается. Исключённый одноразовый pairing code не порождает ложный
конфликт; неуправляемые DHCP/Wi-Fi-секции не затрагиваются.

Панель показывает: «Пока импорт ожидал выполнения, настройки роутера изменились.
Резервная копия не применена. Обновите страницу и проверьте настройки перед
повторным импортом». Строка добавлена в PO/POT, русский и китайский JSON собраны
штатным `scripts/po2json.py`.

Полный suite не запускался. Новых проверок **23**: 21 consistency, одна UI,

14 отказов на старом варианте — не 14 самостоятельных уязвимостей: часть контролей

Дополнительно пройдены проверки синтаксиса **трёх LuCI-модулей и семи Node-модулей**,

## Доставка и применение

Это **альтернативные варианты**, не два последовательных патча.
Совокупный патч включает все предыдущие review-правки и применяется к чистому
r323 `1e9c43b`. Delta применяется только после `sheepfold-r323-review-import.patch`.
Оба варианта не предназначены для непосредственного применения к `bdb3a92`.

Из каталога с исходным bundle и полученными файлами можно создать отдельную копию:

```sh
git clone --branch main sheepfold-r323-main.bundle sheepfold-review-persistence
cd sheepfold-review-persistence
git switch -c review/persistence-followup
git apply --check ../sheepfold-r323-review-persistence.patch
git apply ../sheepfold-r323-review-persistence.patch
```

Если предыдущий кандидат уже применён и рабочая копия не содержит иных изменений:

```sh
git apply --check ../sheepfold-r323-review-persistence-delta.patch
git apply ../sheepfold-r323-review-persistence-delta.patch
```

Команды не делают commit/push и не устанавливают пакет. При наличии своих изменений
не применять вслепую: предварительная проверка патча должна завершиться успешно.
ZIP представляет полный исходный снимок без `.git` и временных `.build`-файлов.
В архив доказательств включены результаты применения обоих путей, побайтовой сверки
и повторного профильного запуска. Контрольные суммы вынесены отдельно; они
подтверждают соответствие поставки manifest, не безопасность кода.

## Что остаётся открытым

Правки не создают общую транзакцию UCI. После последней проверки ещё возможны
изменения через другую задачу, вкладку, rpcd-сессию или CLI. RPC batching может
читать некоторые аргументы позднее, а штатный unload уничтожать локальный cache.
Обнаружение только видимой смены snapshot не гарантирует неизменяемость backend.
Механизм аварийного rollback, потеря питания и обновление браузера во время записи
требуют отдельного испытания. UI не обещает сохранность старой конфигурации после
неподтверждённого apply.

Фоновые копии и облачное восстановление остаются выключенными до безопасного
общего export/restore-контракта. Старая часть cloud-тестов, ожидающая разрешённый
archive-push, не выполнялась и не объявлена исправной. Ни полная совокупная
приёмка кандидата, ни native Windows, ни физический LuCI/OpenWrt, ни Android,
ни настоящие облачные аккаунты в этом проходе не проверялись. Новые IPK/APK/SDK
сборки не создавались. Границы и следующий порядок описаны в R03 и B132.
