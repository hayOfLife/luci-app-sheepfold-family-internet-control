# Фоновые задания обслуживания Sheepfold

<!-- §maintjob1 -->

Документ фиксирует исполняемый контракт `sheepfold-maintenance`. Эти задания не меняют семейную политику. Безнадзорная установка обновлений разрешена только после явного включения бета-теста (§betatest1).

## Запуск

`sheepfold-service` не чаще одного раза в пять минут вызывает:

```sh
/usr/libexec/sheepfold/sheepfold-maintenance run
```

Сам helper проверяет отдельный срок каждого задания и использует общий kernel `flock`. Повторный service tick не запускает параллельный cleanup, update probe или rotation.

Доступны диагностические команды:

```sh
sheepfold-maintenance force
sheepfold-maintenance rotate-log
sheepfold-maintenance cleanup-devices
sheepfold-maintenance check-updates
sheepfold-maintenance status
```

`force` игнорирует расписание обычных заданий, но не часовой предел бета-обновлений. Он не ослабляет валидацию, не включает бета-тест и не удаляет защищённые карточки. При уже включённом бета-тесте `force` и `check-updates` могут запустить автоматическую установку, если часовой срок наступил: это не read-only команды.

## Ротация основного RAM-журнала

Используются:

- `sheepfold.global.log_retention`, например `3d`;
- `sheepfold.global.log_max_size_kb`, по умолчанию `1024`;
- безопасный путь `log_cache_path` только внутри `/tmp/sheepfold/`.

Журнал и rotator используют один `log-maintenance.flock`. Запись ограничивает одно сообщение 4096 символами. Rotation:

1. сохраняет строки за выбранное число локальных календарных дней;
2. сохраняет malformed/legacy-строки вместо их молчаливого удаления;
3. обрабатывает только ограниченный хвост `максимальный размер + 64 КиБ`, поэтому повреждённый производитель событий не заставляет сервис читать неограниченный файл;
4. затем оставляет самые новые полные строки в пределах размера;
5. заменяет файл атомарно и сохраняет режим `0600`.

С r303 путь rotator проверяет через `sheepfold-log-common`, как writer и API:
нет fallback после ошибки UCI, компонентов `..`/`.` и символических ссылок.
Ошибка чтения существующей настройки удержания/размера не разрешает default-pruning.
Промежуточные данные находятся в уникальном закрытом каталоге, конечный файл
проверяется до замены. Размер нормализуется десятично; дополнительный байт в
`tail` сохраняет целую строку на точной границе. Подробнее: [B79–B81](bug-register.ru.md)
и [протокол r303](audit-fixes-r303.ru.md).

`rotate-log` сообщает об отказе; агрегат `run/force` продолжает другие задания,
поэтому его exit 0 не гарантирует успеха ротации — проверяется `last_result`.
Ошибка до публикации сохраняет содержимое существующего журнала. Закрытые файлы
после SIGKILL, отказ записи state и общий UCI snapshot остаются ограничениями.

Если год роутера явно неверен, age-pruning пропускается, но ограничение размера продолжает работать. Это предотвращает удаление журнала из-за часов `1970`.

USB и облачные архивы не считаются основным RAM-журналом. Их отдельная ротация не расширяется скрытно этим заданием.

## Очистка старых offline-карточек

Используется `offline_device_retention_days`; проход выполняется не чаще раза в сутки и только при правдоподобном времени роутера.

Карточка удаляется только если одновременно выполнены все условия:

- presence-снимок содержит подтверждённый `last_seen`, который старше лимита;
- устройство сейчас offline;
- статус карточки всё ещё пустой или `new`; старые решения `allow/blocked/restricted/scheduled` сохраняются даже до появления нового маркера `user_configured`;
- оно не является администраторским;
- MAC отсутствует в allowlist и blocklist;
- нет постоянной DHCP-аренды;
- нет расписания, группы, activity journal или активного временного доступа;
- нет ручного типа, `user_configured`, пользовательского исключения из автогруппы;
- нет legacy/merge alias или identity-quarantine состояния;
- нет сохранённой SIM-истории или истории новых Wi-Fi-сетей детского устройства.

Родительское сохранение карточки и Android-редактор групп ставят `user_configured=1`. За один проход просматривается не больше 512 и удаляется не больше 32 карточек, поэтому повреждённый большой конфиг не создаёт долгую блокировку сервиса. Удаление выполняется через изолированный `uci -t/-p`, снимок `/etc/config/sheepfold`, единый commit и проверку main UCI. При ошибке снимок восстанавливается. Счётчик `next_device_id` не уменьшается, поэтому удалённый постоянный `#ID` никогда не выдаётся повторно (§deviceid2).

## Периодическая проверка обновлений

При выключенном бета-тесте `update_check_install_mode` задаёт только период проверки:

- `daily`;
- `weekly`;
- `monthly`;
- `never`.

Helper вызывает только:

```sh
sheepfold-updater probe
```

`probe` повторно использует проверку официального stable-release и сравнение версий updater, но не скачивает package asset и не вызывает `opkg`/`apk`. При новой версии создаётся дедуплицированное административное уведомление. Установка остаётся отдельным подтверждённым действием в LuCI или родительском APK (§updsafe).

Persistent state хранится в `/etc/sheepfold/maintenance/` с режимом `0600`; там нет URL с токенами, ключей или семейной конфигурации. Сетевой сбой записывается как `failed`, но не выдаётся за отсутствие обновления.

## Участие в бета-тесте

<!-- §betatest1 -->

Состояние: реализовано в ветке; полная установка на живом роутере с этой настройкой ещё не проверена. Решение и причины: [ADR-0028](architecture/decisions/0028-opt-in-beta-updates.ru.md).

В самом низу «Настройки → Общие» находится галочка **«Участвовать в бетатесте»**. UCI: `sheepfold.global.beta_testing=0|1`, по умолчанию `0`. Шаблон и оба postinst добавляют только отсутствующий ключ, не включают участие при обновлении. Подтверждение при выборе объясняет автоматические обновления и точный профиль; отказ не меняет черновик. Всё начинает действовать только после общей кнопки «Сохранить настройки».

При подтверждённом включении LuCI записывает в черновик:

| Настройка | Значение | Причина |
|---|---|---|
| `beta_testing` | `1` | Часовая проверка и автоматическая установка новой опубликованной версии |
| `sim_change_notifications` | `all` | Проверяются также возвращения к известной SIM, а не только новые SIM |
| `child_wifi_network_notifications` | `network_only`, либо прежнее `with_location` | Уведомления включаются без нового согласия на координаты; уже разрешённые координаты не отключаются |

Поля в «Уведомлениях» обновляются сразу в черновике. Затем их можно изменить отдельно, в том числе до первого сохранения. Профиль не навязывается снова при каждом сохранении, service tick или установке пакета. Снятие галочки меняет только `beta_testing`, не восстанавливает прежние уведомления; неприменённые изменения целиком отменяются уходом без сохранения. Ввод `beta_testing=1` вручную через UCI включает только обновления, не подменяет согласие на уведомления из LuCI.

Не включаются: история сайтов, ИИ, координаты при прежнем `off/network_only`, удалённая помощь, relay, выгрузка логов, облака, сторонние интеграции, запросы продления конкретному администратору. Группы, списки устройств, расписания и ограничения не меняются. Новые тестовые функции нельзя молча добавлять в этот профиль: нужна новая явная формулировка согласия. Уведомления требуют установленного детского APK, соответствующих Android-разрешений и настроенного канала доставки; галочка не обходит их.

### Часовой запуск

1. Пятиминутный service tick читает сохранённое `beta_testing`. Только точное `1` включает этот путь; обычный `update_check_install_mode` временно не используется, даже если равен `never`.
2. При правдоподобном годе и наступившем сроке helper записывает попытку в `/tmp/sheepfold/maintenance/beta-update.state` и вызывает `sheepfold-updater start-beta`. При ошибке записи таймера updater не запускается. Запуск не ждёт сетевой загрузки или установки внутри service loop.
3. Интервал 3600 секунд отсчитывается по `/proc/uptime`, а не настенным часам. Сдвиг NTP не ускоряет повторы. Файл в RAM не пишет flash ежечасно; после перезагрузки возможна первая проверка при ближайшем обслуживании. Обычно новая попытка приходится на 60–65 минут после предыдущей, если сервис не задержан другими работами.
4. Updater повторно проверяет участие, получает **последний опубликованный stable-релиз GitHub**, сравнивает версию через общий package-manager adapter и выбирает текущую редакцию и формат OpenWrt. Ветки, Actions artifacts, prerelease, Android APK, downgrade и переустановка той же версии не используются. Неизвестная текущая версия отменяет автоматическую установку.
5. Все ручные проверки и установки используют один `update.flock`, чтобы не перезаписывать общий временный пакет. Фоновый worker наследует lock; запускатель закрывает свой дескриптор без снятия блокировки. Менеджер пакетов и запускаемые init-службы не наследуют этот FD.
6. Перед вызовом менеджера пакетов снова проверяется участие: снятие галочки во время скачивания отменяет установку. Уже начатую транзакцию `opkg/apk` не обрываем, чтобы не повредить пакет. Дальше автоматических попыток не будет.
7. Обновляется только Sheepfold, не прошивка, Podkop или все пакеты системы. Проверка контейнера/версии, резервная копия настроек и восстановление при ошибке остаются у [общего updater](update-safety.ru.md). Бинарного rollback и гарантии восстановления после пропадания питания нет.
8. Успех/ошибка записываются в обычный журнал и очередь уведомлений. Успех дедуплицируется по версии, ошибка по дате; одинаковая ошибка не создаёт новое уведомление каждый час. Следующая попытка допускается через час и при сетевой ошибке, и при занятом updater.

`beta-update.state` показывает результат **запуска**, не успешную установку. Итог worker доступен через `sheepfold-updater status` (`running`, `ok`, `no_update`, `cancelled`, `failed:N`), детали через `sheepfold-updater log`. Обе команды только читают состояние. Диагностический `install-beta-foreground` также требует `beta_testing=1`, но не применяет часовой интервал: не используйте его как периодическое задание.

### Проверка бета-режима

Из корня репозитория в PowerShell, с Node, Python и Git Bash из [описанного окружения](agent-environment.ru.md):

```powershell
python scripts/build-test-ipk.py --variant sheepfold --out-dir .build/beta-testing
$env:SHEEPFOLD_TEST_IPK = (Get-ChildItem .build/beta-testing/luci-app-sheepfold-family-internet-control_*_all.ipk | Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName
node --test tests/maintenanceJobs.test.mjs tests/luciPersistenceAdapters.test.mjs tests/updateTransportSafety.test.mjs tests/installSettingsPreservation.test.mjs
Remove-Item Env:SHEEPFOLD_TEST_IPK
```

Ожидается exit `0`, отсутствие failed-тестов. На Git Bash без `flock` реальный тест взаимного исключения пропускается; transport-тесты используют явно тестовую заглушку lock. На Linux с `flock` этот тест должен исполняться, а не пропускаться. Проверяются подтверждение/отмена UI, ограниченный профиль, отдельный выбор уведомлений, часовой RAM-интервал, NTP-сдвиг, отключение перед установкой, отсутствие переустановки, фоновые завершения и прежние IPK/APK error-paths. Менеджеры пакетов и сеть подменены; реальный роутер не меняется.

Тестовый IPK и изолированные файлы остаются только в `.build`, экспорт в папку пользователя не нужен. Не запускайте тесты из `android/`, не направляйте фикстуры на реальные UCI/opkg, не заменяйте отсутствующий `flock` production-заглушкой. При `spawnSync python EPERM` используйте прямую подготовку IPK выше; если sandbox блокирует сам Git Bash, сверяйтесь с [руководством по ошибкам](troubleshooting.ru.md), а не переустанавливайте Python. Локальный успех не заменяет живые OpenWrt 24.10/25.12, установку с настоящим postinst и power-loss проверку.

## Доказательства и границы

Локальные тесты подтверждают:

- календарную и size-ротацию временного журнала;
- сохранение групповых, админских, DHCP- и schedule-карточек;
- удаление только одной подходящей ненастроенной карточки;
- вызов `probe` и отсутствие установки без участия; отдельный часовой `start-beta` только после opt-in;
- подключение helper к service loop и общий log lock.

Они не доказывают длительную работу на конкретном роутере, поведение при реальном заполнении RAM, GitHub outage, package-manager runtime или последствия аварийного отключения питания. Перед stable-релизом нужен длительный live-router проход с backup/restore и проверкой отсутствия pending UCI (§routerharness).
