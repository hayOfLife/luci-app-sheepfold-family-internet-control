# Категории автоматических тестов

<!-- §testcat -->

Этот документ отвечает на вопрос, какие автоматические тесты запускать при конкретной проблеме. Он не заменяет ручные сценарии из [`testing-cases.ru.md`](testing-cases.ru.md) и проверки на живом роутере из [`live-router-testing.ru.md`](live-router-testing.ru.md).

<!-- §testwhy -->

## Обязательная шапка теста

Каждый новый или существенно изменённый test-файл и вспомогательный тестовый скрипт начинается с короткого объяснения:

- какую пользовательскую функцию или риск регрессии он защищает;
- почему выбран именно этот уровень проверки;
- какое состояние тест может изменить и как восстанавливает его;
- чего успешный тест не доказывает и какая следующая проверка остаётся нужна.

Комментарий должен объяснять замысел конкретного теста, а не пересказывать вызовы и assertions. При содержательной правке старого теста его шапка приводится к этому правилу; не затронутые файлы можно переносить постепенно, без отдельного массового коммита из комментариев.

## Операционный контракт запуска

Для каждого отдельного тестового стенда, исполняемого helper или сетевого сценария профильная документация должна позволять повторить проверку без догадок. В ней обязательно указываются:

1. рабочий каталог и операционная система/оболочка;
2. необходимые программы, сервисы, ключи, переменные окружения и подключённое оборудование;
3. точная команда без условных фрагментов, если их можно заменить конкретным примером;
4. ожидаемый exit code, ключевые строки вывода и ожидаемое состояние после запуска;
5. какие реальные данные или настройки меняются, как они резервируются и восстанавливаются;
6. распространённые ошибки и способ отличить ошибку продукта от ограничения среды;
7. способы запуска, которые запрещены или заведомо дадут ложную ошибку;
8. что зелёный результат доказывает и что всё ещё требует другого уровня проверки.

Канонический пример такого runbook: [`testing-support-endpoint-discovery.ru.md`](testing-support-endpoint-discovery.ru.md). Нормативная матрица соседних изменений находится в [`mandatory-companion-changes.ru.md`](mandatory-companion-changes.ru.md) (§cmpchg1). Новая команда в Markdown считается частью интерфейса разработчика и должна пройти `npm.cmd run quality:docs:all` и хотя бы один фактический запуск в подходящей среде.

## Основной принцип

Тестовые категории намеренно пересекаются. Один файл может проверять несколько границ: например сопряжение относится к Android, устройствам и безопасности. При изменении двух областей запускаются обе категории одной командой; runner удалит повторы файлов.

```powershell
npm.cmd run test:category -- luci devices
```

Список категорий и число файлов:

```powershell
npm.cmd run test:list
```

Каноническая карта находится в `tests/categories.mjs`, выборочный runner — в `scripts/run-test-category.mjs`, полный — в `scripts/runAllTests.mjs`. Тест `tests/testCategories.test.mjs` не позволяет добавить новый `*.test.mjs` без категории или оставить ссылку на удалённый файл. Команда `quality:docs:all` дополнительно сверяет буквальные имена `*.test.mjs` и `npm run` в Markdown с реальными файлами и `package.json`, поэтому переименование теста должно сопровождаться правкой документации.

Перед выбором категорий можно получить консервативную карту влияния:

```powershell
npm.cmd run review:impact
```

Она связывает изменённые пути с соседними слоями и вопросами ревью (§impact1), но не запускает тесты, не заменяет ручную оценку неизвестного пути и не отменяет обязательную матрицу (§cmpchg1).

Изменение `icons/catalog.json`, генератора или сгенерированного реестра требует отдельной проверки источника истины:

```powershell
npm.cmd run icons:check
node --test tests/iconCatalog.test.mjs
```

После геометрической правки нужен также визуальный просмотр `icons/catalog.html`: автоматическая проверка видит рассинхронизацию и запрещённые копии, но не оценивает узнаваемость значка человеком (§iconcat1).

Для обычного цикла используйте автоматизированную оболочку (§qassist):

```powershell
npm.cmd run quality:plan
npm.cmd run quality:changed
```

Она запускает `git diff --check`, изменённую документацию, применимый ESLint/Android Lint и объединённый набор затронутых test-файлов без дублей. Это обычный pre-push путь. `quality:gate` выполняет строгий полный прогон только для отдельно обоснованного сквозного или релизного барьера. Подробная граница и JSON-отчёт описаны в [`quality-assistants/README.ru.md`](quality-assistants/README.ru.md).

GitHub Actions использует ту же карту: workflow вычисляет base SHA события и вызывает
`runQualityChecks.mjs --git <base> --skip-android --strict`; Android проверяется
отдельным `validate-android.yml` только при изменении APK, каталога значков,
Android-скриптов или самого workflow; ручной запуск всегда доступен. Запрещено
возвращать wildcard-запуск `node --test tests/*.test.mjs`,
потому что он одновременно исполняет конфликтующие runtime-fixture и тестирует
несвязанные области. Статический контракт защищает `staticAnalysisTooling.test.mjs`.

Тяжёлая SDK-сборка OpenWrt также не запускается от несвязанных изменений. Её
`pull_request`/`push` ограничены `paths` package payload, переводов и сборочных
Python-модулей; `workflow_dispatch` и опубликованный release остаются явными
полными барьерами. Этот контракт защищает `openWrtBuildWorkflow.test.mjs`.

## Внешние HTTP-квоты r293

Новый `tests/apiRateLimitRuntime.test.mjs` запускает реальные helper/CGI и два процесса
с управляемым барьером для гонки счётчика. 40 сценариев; общая выбранная область —
142 теста в 8 файлах. Команды, исходные 33 отказа r292, изоляция и ограничения:
[отчёт r293](audit-fixes-r293.ru.md). Внутренний pairing-limit и uhttpd не подменяются
этой проверкой. Полный gate остаётся отдельным условием только при критериях §testcat.

## Авторизация и установочный guard r292

Для текущей итерации владелец явно выбрал только изменённую область и соседей вместо
полного runner. Новые `tests/tokenAuthenticationRuntime.test.mjs` (42 сценария) и
`tests/packageHardeningRuntime.test.mjs` (7 сценариев) защищают reader/hash/HTTP и реальный
staged-root guard. Соседние наборы, команды, 503/401 контракт и ограничения указаны в
[отчёте r292](audit-fixes-r292.ru.md). Этот исторический выборочный результат не заменяет
будущий полный gate, если для следующего изменения выполнятся критерии §testcat.

## Привязка, случайность и публикация токена r291

Запускать из корня checkout в Linux с Node и BusyBox/обычными файловыми утилитами;
для полного runner также нужен Python. Роутер, телефон, root-пароль и доступ к сети
не нужны. Модель UCI/источника отказов и синтетические данные находятся в `.build`;
тесты переносят системные пути и удаляют fixtures через `finally`, не меняя реальный `/etc`.

```sh
node --test tests/pairingBoundaryRuntime.test.mjs tests/pairingStorageRuntime.test.mjs
```

Ожидаются exit 0, **55 pass, 0 fail/skip**. Проверяются вся форма до выдачи прав,
Content-Length, короткое/ошибочное чтение, SHA-процессы, частичная запись/chmod/link,
чужая запись и конкурирующие публикации, подготовка snapshot, повтор кода и весь CGI.
Те же тесты на r290: 39 падений, 16 контрольных успехов. Они зарегистрированы в backend
и security; полный runner исключает дубли категорий. Успех не доказывает качество RNG,
libuci, TLS, power loss, устойчивость flash или атомарность всей системы писателей.

Отсутствующий инструмент — ограничение среды, не основание отключить assertion.
Не запускать production pairing напрямую на реальной системе для повторения стенда.
Оставшиеся безопасные сценарии для роутера и причины решений: [r291](audit-fixes-r291.ru.md),
[карточки B31–B34](bug-register.ru.md). После изменения общего helper обязателен полный
`npm test`, docs/icons и оба IPK; проверка текстовых совпадений сама по себе недостаточна.

## Хранилище сеансов и результат команд r290

Из корня репозитория на Linux с Node.js, sh/BusyBox и обычными файловыми утилитами:

```sh
node --test tests/tokenStorageRecoveryRuntime.test.mjs tests/commandOutcomeRuntime.test.mjs
```

Ожидается exit 0, **40/40**, без пропусков. Первый файл защищает миграцию/отзыв записей,
второй — применение Wi-Fi и независимость результата команды от побочного журнала.
Настоящие CLI вызываются с системными путями в `.build`; UCI/nft/wifi и отказы
файловых команд заменены. После нормального завершения fixture удаляется. Не подменять
этот запуск прямым исполнением production helper от root. Частичная ошибка/конфликт
не обязаны означать rollback уже успешных операций — assertions проверяют именно это.
Нативная UCI, flash, живое радио и токены телефона не затрагиваются. Реальные
конкурентные pairing/revoke остаются отдельной проверкой R08. Разбор причин —
[B27–B30](bug-register.ru.md), доказательства и полный результат — [r290](audit-fixes-r290.ru.md).

## Согласованность входов и отказы помощников r289

Из корня проекта в Linux с Node.js и POSIX-утилитами:

```sh
node --test tests/policyConsistencyRuntime.test.mjs
```

Ожидается 21 тест без ошибок/пропусков. Стенд исполняет настоящие shell-файлы и
детерминированно меняет модель UCI между чтениями, ломает вывод evaluator, запись
отметки конфликта и генерацию home rules. Проверяется также отсутствие прогноза в
periodic firewall при сохранении его в клиентском статусе. На базе r288 этот же
набор даёт 19 ошибок и два успешных контрольных сценария.

Объекты UCI/nft заменены моделями: тест доказывает обработку наблюдаемой ошибки,
не изоляцию нативного UCI и не прохождение пакетов. Данные живут только в `.build`.
Подробные границы B22–B26 — в [реестре](bug-register.ru.md), результат полного прогона
и неуспешные промежуточные запуски — в [отчёте r289](audit-fixes-r289.ru.md).

## Восстановление и достоверность чтения r288

Из корня репозитория, Linux с Node.js, sh/awk/sed и Python для соседних упаковочных тестов:

```sh
node --test tests/recoveryRuntime.test.mjs tests/readModelRuntime.test.mjs
```

Ожидается 34 теста, `fail 0`, `skipped 0`. Настоящие shell-обработчики запускаются с
изолированными UCI/nft/часами в удаляемой `.build`-папке. Проверяются повтор после отказа,
runtime-маркер, атомарная команда очистки, неактивная будущая граница расписания,
длительность CLI, недоступный UCI, 503/пустой список и сериализация строк.

BusyBox ash используется при наличии; отдельный тест предпочитает BusyBox awk.
Отсутствие sh, невозможность дочернего процесса или записи `.build` — ограничение стенда,
не зелёный результат. Стенд не меняет реальный firewall, не обращается к роутеру и
не доказывает Netlink/packet path; production helpers напрямую на рабочем ПК не запускать.
Поведение реального OpenWrt и первоначальный HTTP auth остаются отдельными проверками.
Причины выбора каждого теста и границы: [подробный реестр](bug-register.ru.md).

## Статический анализ

<!-- §lint1 -->

Статические проверки запускаются отдельно от предметных Node-тестов:

```powershell
npm.cmd run lint:js
npm.cmd run lint:android
```

`lint:js` проверяет LuCI, Node-скрипты и тесты. Конфигурация знает о LuCI-loader, внедряемых глобалах и верхнеуровневом `return`, поэтому результат полезнее обычного `node --check`. `lint:android` последовательно запускает штатный `lintDebug` родительского и детского APK через их Gradle Wrapper. На Windows ему нужен доступ к установленным Android SDK и Gradle cache; в ограниченной Codex-песочнице команду может потребоваться выполнить вне sandbox.

Обе проверки обязательны перед push, если соответствующая часть исходников менялась. Полная команда `npm.cmd run lint` объединяет их, но при работе только с LuCI быстрее запускать `lint:js`. Android Lint может оставлять предупреждения об обновлениях зависимостей или планируемых ресурсах; ошибки CI не скрывать baseline-файлом без отдельного обоснования.

## Категории

| Команда | Когда запускать |
| --- | --- |
| `npm.cmd run test:smoke` | Небольшой репрезентативный набор после мелкой правки; не заменяет предметную категорию и исключает глубокий LuCI-аудит, долгие HTTP/shell-стенды и сборку IPK |
| `npm.cmd run test:luci` | Вкладки, таблицы, модалки, формы, переводы, CSS/JS LuCI, `overview.js` и frontend-модули |
| `npm.cmd run test:access` | Белый/чёрный список устройств, расписания, группы, администраторы, временный доступ, приоритеты |
| `npm.cmd run test:devices` | DHCP/ARP, автообнаружение, типы, ID, присутствие и сопряжение устройств |
| `npm.cmd run test:sites` | Белые/чёрные списки сайтов, аварийно-полезные сайты, DNS/nftables и AdGuard Home; набор медленный |
| `npm.cmd run test:backend` | Router backend, UCI, API, сервисы, импорт/экспорт и системные действия; набор широкий и может быть долгим |
| `npm.cmd run test:backendFast` | Быстрые backend-контракты без долгих HTTP/DNS/firewall-стендов и без сборки IPK; основной выбор во время точечной разработки |
| `npm.cmd run test:policySimulation` | Глубокие и долгие shell-сценарии классификатора устройств и вычислителя расписаний |
| `npm.cmd run test:networkIntegration` | Долгие AdGuard Home, DNS, nftables и site-list стенды; запускать при изменении сетевой интеграции и перед контрольной точкой |
| `npm.cmd run test:android` | Общие контракты родительского и детского APK, включая вычисляемый контраст темы и управляющих кнопок; после Kotlin/XML-правок дополнительно нужен Gradle и визуальная проверка на устройстве (§uicontrast) |
| `npm.cmd run test:security` | Авторизация, TLS, rate limit, секреты, firewall-границы и безопасное обновление |
| `npm.cmd run test:messaging` | Telegram, команды мессенджера и запрос ребёнка на временный доступ |
| `npm.cmd run test:ai` | Провайдеры, настройки и видимость AI-функций, а также автономные Python-контракты экспериментального server core; состав Standard/AI IPK проверяется отдельно категорией `packaging` |
| `npm.cmd run test:packaging` | Makefile, Standard/AI test-IPK и SDK feed, GitHub Actions IPK/OpenWrt APK matrix, локализация, права, updater и product boundary |
| `npm.cmd run test:tooling` | Windows/Node-инструменты, карта категорий, LuCI-аудит и test harness; не собирает IPK, но глубокий LuCI-аудит и shell-fixtures могут занять около минуты |

## Попарная матрица конфигураций

<!-- §pairmat -->

```powershell
npm.cmd run quality:matrix
node --test tests/runtimeCompatibilityMatrix.test.mjs
```

All-pairs генератор выбирает компактный набор, в котором встречается каждая пара значений: формат OpenWrt-пакета, редакция Standard/AI Support, четыре режима интеграций, backend списков сайтов, управление AdGuard Home и режим автоопределения. Обязательные строки сохраняют критические и деградировавшие сценарии, например явный AdGuard при отсутствующем AdGuard Home.

Матрица помогает не забыть сочетания и уменьшает обычный перебор. Она не заменяет исчерпывающие security-инварианты, повреждённый ввод, migration/rollback, установку IPK/OpenWrt APK и живые DNS/nftables/hardware проверки.

Произвольное объединение:

```powershell
npm.cmd run test:category -- access sites security
```

## Обычный цикл разработки

1. До правки выбрать одну ближайшую категорию по месту ошибки.
2. Во время работы запускать конкретный файл или даже один сценарий:

   ```powershell
   node --test tests/devicePresence.test.mjs
   node --test --test-name-pattern "rejects duplicate" tests/adguardIntegration.test.mjs
   ```

3. После завершения запустить целую категорию подсистемы.
4. Если правка пересекла соседний контракт, добавить вторую категорию.
5. Выполнить `git diff --check` независимо от выбранной категории.
6. Перед push выполнить `npm.cmd run quality:changed`, проверить его impact-отчёт и закрыть перечисленные ручные проверки. Неизвестная или необоснованно пропущенная область блокирует push.

Для backend-правки сначала использовать `test:backendFast`. Полный `test:backend` включает долгие сетевые стенды и глубокие симуляции и нужен только когда затронуты их контракты. На обычном Windows-компьютере один `adguardIntegration.test.mjs` может идти 6–7 минут, а вся `networkIntegration` — заметно дольше. Для этих команд внешнему runner нужен лимит не меньше 15 минут. Изменение классификатора устройств или вычислителя расписаний требует `test:policySimulation`; изменение AdGuard Home, DNS, nftables или загрузки внешних списков — `test:networkIntegration`. Сам по себе PR или merge не расширяет доказанный impact (§testcat).

Выборочный `run-test-category.mjs` объединяет категории без дублей, но каждый выбранный
test-файл запускает в отдельном дочернем Node-процессе и останавливается на первой
ошибке. Не возвращать общий `run({ files, concurrency: true })`: при широком, но всё
ещё выборочном impact он одновременно запускает десятки shell/HTTP-fixtures, создаёт
ложные timeout/race failures и не даёт локализовать проблему. Лимит одного файла
совпадает с полным runner: 1800 секунд на native Windows и 720 секунд на POSIX.

Категория `tooling` содержит только собственные контракты карты/runner, документации,
статического анализа и Windows-окружения. Тесты relay, remote support, LuCI и packaging
не дублируются в ней только потому, что используют локальный harness: их выбирают
предметные категории. `testCategories.test.mjs` доказывает и отсутствие потери файла,
и несколько таких границ.

Изменение общего runtime-fixture выбирает его прямых потребителей отдельно от категории:
например, `adminConfigRuntimeFixture.mjs` добавляет все пять admin-config runtime-файлов,
а `apiRateLimitFixture.mjs` добавляет только rate-limit runtime. Так длинные тесты не
гоняются на каждую tooling-правку, но не теряются при изменении собственной зависимости.

<!-- §testenv1 -->

Некоторые Node-тесты запускают Git Bash и создают изолированные fixtures. На
Windows канонические `runAllTests.mjs` и `run-test-category.mjs` направляют
`TEMP`/`TMP`/`TMPDIR` в абсолютный каталог репозитория `.build/test-tmp`: это
сохраняет обычный контракт `os.tmpdir()` для Node и Python. Общий test-helper
передаёт Git Bash fixture относительно фактического `cwd`; путь с `..` допустим
только тогда, когда после разрешения он остаётся внутри явно заданного корня
fixture. В
ограниченной песочнице `mkdir .build/...` разрешён, но эквивалентный абсолютный
MSYS-путь `/c/Users/User/.../.build/...` может быть отклонён ещё на сегменте
`/c/Users/User`. Такая ошибка не означает повреждение NTFS ACL и не исправляется
повторной установкой Git.

Прямой `node --test ...` обходит подготовку runner. Для него либо использовать
`npm.cmd run test:category -- --file ИМЯ.test.mjs`, либо заранее задать три
переменные локальным абсолютным temp-путём по примеру из
[`agent-environment.ru.md`](agent-environment.ru.md). Если тест намеренно работает
с абсолютным внешним каталогом, а не с fixture внутри репозитория, повторить его
вне песочницы. Успешный внешний повтор подтверждает ограничение среды; он не даёт
права удалить assertion или ослабить production-путь.

Runtime-fixture, который подменяет `cp`, `mv`, `sha256sum`, `date` или другую
системную команду, обязан устанавливать `PATH` внутри уже запущенного Git Bash
перед `exec`. Одной Windows-переменной `PATH` с разделителем `;` недостаточно:
MSYS нормализует её и может поставить `/usr/bin` раньше каталога fixture, тогда
fault injection фактически не выполняется. Пути внутри разрешённого корня fixture
передаются относительно `cwd`; абсолютная форма `/c/...` остаётся только fallback
для внешнего пути и в ограниченной песочнице может требовать неизменного внешнего
повтора. Node/Python продолжают получать обычные Windows-пути. Генерируемые Python-модели запускаются через
`PYTHON_EXECUTABLE` (`python` на Windows, `python3` на POSIX) и с UTF-8, иначе
кириллица/emoji способны дать ложный `UnicodeEncodeError` в русской CP1251.

Native Windows не доказывает Unix mode-биты `0600/0700`, создание файловой
символической ссылки без Developer Mode и конкуренцию kernel `flock`, если самой
утилиты нет. В таких случаях пропускается только соответствующий assertion/test
с явной причиной; содержимое, cleanup и коды ошибок продолжают проверяться.
Полные permission/symlink/flock-сценарии остаются обязательными на Linux CI.
Пакет OpenWrt по-прежнему явно зависит от `+flock`: тестовая последовательная
заглушка не является продуктовым fallback.

Локальный temp находится под корневым `package.json` с `type: module`. Временный
файл, которым `node --check` имитирует LuCI loader и допускает верхнеуровневый
`return`, поэтому обязан иметь расширение `.cjs`. Расширение `.js` здесь создаёт
ложный `SyntaxError: Illegal return statement`; оно не доказывает поломку LuCI.

Имена файлов `*.test.mjs`, внутренних идентификаторов и категорий тестов оформляются в `camelCase`, как имена переменных. Человекочитаемые заголовки `describe()` и `it()` остаются обычными фразами: они предназначены для отчёта, а не для обращения из кода.

Документация без изменения команд, контрактов и примеров кода обычно не требует предметных Node-тестов. Достаточны `npm.cmd run quality:docs:all` и `git diff --check`. Аудит проверяет локальные ссылки, §-теги, буквальные имена test-файлов и npm-команд, но не подтверждает истинность описанного поведения: существенное изменение тестовой стратегии всё равно требует ручной сверки с `tests/categories.mjs`, runner и реальными границами среды.

## Как читать результат

| Проверка | Успешный результат | Допустимые оговорки |
|---|---|---|
| `node --test ...` | exit code `0`, итоговая строка `fail 0` | `skipped` допустим только когда причина явно указана тестом и обязательная граница проверена отдельной командой |
| `npm.cmd run test:<category>` | runner завершился с `0`, каждый выбранный файл имеет результат, нет timeout/неучтённого процесса | число файлов меняется вместе с `tests/categories.mjs` и не закрепляется навсегда в документации |
| `npm.cmd run lint:js` | exit code `0`, нет ESLint diagnostics | уведомление npm о новой версии не является ошибкой проекта |
| `npm.cmd run lint:android` | обе Gradle-задачи завершились успешно, нет Android Lint errors | предупреждения оцениваются по смыслу; baseline нельзя добавлять только ради зелёного статуса |
| `npm.cmd run quality:docs:all` | сообщение о исправных ссылках, §-тегах, тестах и npm-командах, exit code `0` | количество проверенных Markdown-файлов не является контрактом |
| `git diff --check` | пустой вывод и exit code `0` | команда проверяет whitespace, но не корректность поведения |

При ошибке в отчёте сохраняются точная команда, exit code, первая содержательная причина,
название упавшего test-файла и факт внешнего повтора, если первоначальный запуск упёрся в
ограничение песочницы. Перечень распространённых ошибок окружения находится в
[`agent-gotchas.ru.md`](agent-gotchas.ru.md) и [`troubleshooting.ru.md`](troubleshooting.ru.md).

## Как запускать нельзя

- Не запускать одновременно два полных suite или два одинаковых сетевых/category runner из
  одного checkout: они конкурируют за порты, `.build`, дочерние процессы и усложняют диагноз.
- Не запускать `npm.cmd test` после каждой небольшой правки. Сначала direct test и предметная
  категория; полный набор используется в перечисленных ниже контрольных точках.
- Не считать `spawnSync ... EPERM`, `status: null` или MSYS `Permission denied` падением
  production-кода до неизменного повтора нужного теста вне песочницы.
- Не увеличивать timeout и не запускать вторую копию только потому, что долгий тест пока не
  печатает строки. Сначала проверить процесс и документированную обычную длительность.
- Не завершать все `node.exe`, `java.exe` или `python.exe` на компьютере. После подтверждённого
  зависания завершается только процесс с командной строкой конкретного теста.
- Не запускать `router:*` на домашнем/рабочем роутере вместо выделенного тестового и не запускать
  `androidLab:*` как часть обычного локального или always-on CI прогона.
- Не удалять assertion, не добавлять lint baseline и не менять production-код ради обхода
  ограничения среды. Сначала применяется документированный внешний или ручной уровень проверки.

## Когда нужен полный прогон

Команда полного набора остаётся:

```powershell
npm.cmd test
```

Полный runner запускает каждый test-файл ровно один раз. Сначала он разделяет
нагрузку на обычное ядро, `networkIntegration`, `policySimulation` и `packaging`,
а затем по умолчанию запускает каждый файл в отдельном процессе. Временно объединить
совместимые файлы можно через `SHEEPFOLD_TEST_BATCH_SIZE` от 1 до 32; внутренний
параллелизм такой партии задаёт `SHEEPFOLD_TEST_CONCURRENCY` от 1 до 16. Один файл
или партия получает лимит 720 секунд на POSIX и 1800 секунд на native Windows;
его можно явно изменить через `SHEEPFOLD_TEST_TIMEOUT_SECONDS` от 60 до 3600.
Повышенный Windows default нужен для административных shell/Python fixtures:
на текущем стенде `adminWifiValidationRuntime.test.mjs` исправно выполняется дольше
720 секунд под антивирусом. Такое разделение нужно не для пропуска
медленных проверок: один монолитный процесс на Windows смешивал fake-server, Git
Bash и дочерние Python builder и мог не завершиться за 20 минут; даже 70 обычных
файлов в одном процессе давали слишком широкую область диагностики. Контрольный
Windows-прогон всех 105 файлов по одному завершился за 18 минут 22 секунды. Между
партиями процесс освобождает порты, handles и дочерние процессы, а runner отдельно
проверяет, что ни один файл не потерян и не запущен дважды.

Полный набор запускается только с явным обоснованием:

- impact нельзя надёжно ограничить категориями либо `quality:plan` сообщает неизвестные пути;
- сквозной контракт действительно затрагивает большинство подсистем, а не просто имеет общее имя;
- изменён отбор/изоляция test runner так, что direct test не доказывает отсутствие пропуска файлов;
- владелец прямо запросил полный прогон;
- принят отдельный release-gate: его областью является весь выдаваемый артефакт.

Push, PR, merge, изменение документации, version bump или правка одной подсистемы сами
по себе не являются причиной тестировать остальные подсистемы. Для IPK/APK запускаются
соответствующие `packaging`/`android` и ручные проверки артефакта. Если после целевого
прогона изменились только документы, достаточно документационного gate; если изменился
исполняемый код, impact вычисляется заново.

Если владелец прямо ограничил текущую проверку затронутыми подсистемами, это ограничение
важнее консервативной рекомендации `fullTest`: выполнить весь рассчитанный impact-контур,
не запускать чужие категории и честно оставить результат `partial` с перечнем проверенного.

На Windows отдельная группа Node test runner может не показывать вывод конкретного файла до его завершения. Внешний тайм-аут `npm.cmd test` нельзя автоматически считать падением: в выводе полного runner найти незавершённую группу, проверить оставшиеся процессы и запустить её либо долгий файл отдельно. После принудительного тайм-аута завершать можно только дочерние процессы с командной строкой конкретного теста, не все процессы `node.exe` (§testcat).

## IPK-зависимые тесты на Windows/Codex

Категория `packaging` может запускать Python-сборщик из Node. Тест `aiServerCoreExperiment.test.mjs` аналогично запускает автономный Python-suite экспериментального ядра. В ограниченной песочнице это иногда даёт `spawnSync python EPERM`, хотя Python исправен. Полный runner теперь проверяет дочерний Python до долгого suite и останавливается с точным объяснением. AI-core в таком случае проверяется прямой командой из `experimental/ai-server-core`, а package-тесты запускаются вне песочницы либо с заранее собранными пакетами.

Различать установку и запрет среды нужно двумя проверками:

```powershell
python --version
node -e "const {spawnSync}=require('node:child_process'); const r=spawnSync('python',['--version'],{encoding:'utf8'}); console.log({status:r.status,error:r.error?.code,stdout:r.stdout,stderr:r.stderr})"
```

Если первая команда успешна, а вторая возвращает `error: 'EPERM'` до вывода
Python, ничего устанавливать не требуется: sandbox либо антивирус запретил именно
дочерний процесс. `ENOENT` или ошибка обеих команд уже указывает на `PATH`/установку.
Не считать пустой вывод успехом и не добавлять широкое исключение антивируса только
ради зелёного теста. (§testenv1)

К этой группе относятся прежде всего `productVariants.test.mjs`, `testIpkI18n.test.mjs`, `testIpkPermissions.test.mjs` и `updateTransportSafety.test.mjs`: без заранее переданного IPK они могут запускать `scripts/build-test-ipk.py` дочерним процессом. Это не тесты реального IPv6, firewall или роутера; им нужен только разрешённый запуск дочернего Python и запись временных архивов. Если среда Codex возвращает `EPERM` или `spawnSync(...).status === null`, запустить их вне песочницы либо использовать заранее собранные IPK по примеру ниже:

`openWrtVariantFeed.test.mjs` аналогично запускает подготовщик SDK feed. В
ограниченной среде сначала подготовить оба каталога прямым Python, затем передать
их тесту:

```powershell
python scripts\prepare-openwrt-sdk-feed.py --variant sheepfold --out-dir .build\sdk-standard
python scripts\prepare-openwrt-sdk-feed.py --variant sheepfoldAi --out-dir .build\sdk-ai
$env:SHEEPFOLD_TEST_STANDARD_SDK_FEED=(Resolve-Path .build\sdk-standard).Path
$env:SHEEPFOLD_TEST_AI_SDK_FEED=(Resolve-Path .build\sdk-ai).Path
node --test tests\openWrtVariantFeed.test.mjs
```

```powershell
python scripts/build-test-ipk.py --variant all --out-dir .build/category-ipk
$env:SHEEPFOLD_TEST_IPK=(Get-ChildItem .build/category-ipk/luci-app-sheepfold-family-internet-control_*_all.ipk | Sort-Object LastWriteTime | Select-Object -Last 1).FullName
$env:SHEEPFOLD_TEST_IPK_DIR=(Resolve-Path .build/category-ipk).Path
npm.cmd run test:packaging
```

Перед использованием готового IPK убедиться, что его версия совпадает с `PKG_VERSION-PKG_RELEASE`. Не подставлять старый архив с тем же удобным именем после изменения package payload.

## Android и живой роутер

Категория `android` проверяет договорённости исходного кода, но не заменяет сборку:

```powershell
npm.cmd run lint:android
android\gradlew.bat -p android :app:assembleDebug
android-child\gradlew.bat -p android-child :app:assembleDebug
```

Android runtime проверяется отдельным ручным стендом (§andlab1):

```powershell
npm.cmd run androidLab:doctor
npm.cmd run androidLab:smoke
npm.cmd run androidLab:full
```

`androidLab:smoke` запускает API 35 при непосредственной Android-работе.
`androidLab:full` последовательно запускает API 28 и API 35 перед выдачей APK,
релизом или после изменения общих Android lifecycle/navigation/network
контрактов. Эти команды не входят в `npm.cmd test` и `quality:changed`, потому
что скачивают тяжёлые образы и запускают виртуальный телефон только по прямой
необходимости. Полная матрица и physical-профиль описаны в
[`android-test-lab.ru.md`](android-test-lab.ru.md).

Категории `sites`, `access` и `backend` не доказывают поведение конкретного железа. Firewall, Wi-Fi/WPS/LED, DHCP-события, DNS-путь и интеграционные топологии дополнительно проверяются по [`live-router-testing.ru.md`](live-router-testing.ru.md).

Проверки на живом роутере не входят в `npm.cmd test`: они меняют настоящее состояние OpenWrt, Wi-Fi, firewall, sysctl и интеграций, поэтому запускаются вручную на отдельном тестовом роутере.

Эмулятор также не подтверждает реальную камеру, private MAC, SIM, OEM background
restrictions и связь с домашним gateway. Изменения этих областей требуют
выделенного физического телефона, а pairing/API/firewall — ещё и живого роутера.

### Как разбирать внешние отчёты о покрытии

Процент либо обещание «100% регрессионной безопасности» не является целью само по
себе: тест доказывает только явно названную границу. Перед созданием предложенного
файла сначала проверить, не защищён ли механизм уже существующим тестом:

- form-urlencoded, malformed `%XX`, NUL и wiring `jshn` защищает
  `aiJsonBoundary.test.mjs`; настоящий payload со сложными символами дополнительно
  разбирается штатным `jshn` в read-only live-router проверке AI Support;
- лимиты `nmap`, `nice -n 19`, суточный retry и общий `flock` защищены
  `backendRuntimeSafety.test.mjs`, `deviceDetectorSafety.test.mjs` и
  `lockCommon.test.mjs`;
- cleanup таймера конфликта расписаний проверяет поведением
  `modalTimerCleanup.test.mjs`, а не только поиском текста;
- WorkManager сейчас относится к `android-child/`, а не к родительскому `android/`.
  Статический контракт защищает `androidChildPolling.test.mjs`; фактическое
  исполнение требует emulator/physical-device instrumentation.
- ciphertext-only маршрут баг-репорта проверяет `supportReportTransport.test.mjs`,
  но совместимость Tink HPKE доказывает только Android runtime test
  `SupportReportCryptoTest`; server signature/queue отдельно проверяет private repo
  `sheepfold-support-server` (§srep001).
- формат резервного endpoint и совместимость Ed25519 signer/verifier проверяет
  `supportEndpointDiscovery.test.mjs`; реальный GitHub fetch, отказ основного endpoint и
  сохранение UCI проверяются только на тестовом роутере (§srepdisc1).

Не добавлять wall-clock assertion вроде «100 расписаний быстрее 50 мс» в обычный
unit suite: результат зависит от Windows, CI и фоновой нагрузки. Сначала отдельный
benchmark подтверждает проблему и целевой бюджет, затем unit-тест сравнивает
результат новой функции с эталонной реализацией на фиксированных наборах.

Тест для ещё не принятой реализации не должен незаметно принимать решение за
проект. Поэтому `uci export`, OkHttp/Retrofit и индекс расписаний получают
специализированные equivalence/instrumentation тесты только одновременно с
отдельно одобренной миграцией (§auditopt1).

## Ручной агентный security-аудит

<!-- §secaudit1 -->

Внешний LLM-аудит намеренно не входит в обычный CI и полный Node-suite. Он
недетерминирован, расходует токены, требует внешней учётной записи и передаёт
исходный код выбранному провайдеру. Его запускают вручную перед релизом либо после
изменения критической границы:

```powershell
npm.cmd run security:audit:manual
npm.cmd run security:audit:manual -- -RunScan -ConfirmSourceUpload
```

Первый вызов выполняет только doctor/estimate. Второй создаёт отдельный clone и
запускает detection-only стадии до S9. Сам runner защищён обычным быстрым тестом
`agenticSecurityAudit.test.mjs`, который не обращается к сети и не расходует
токены. Полный порядок описан в
[ручном агентном аудите](manual-agentic-security-audit.ru.md).

## Правило поддержки карты

При добавлении теста разработчик обязан:

1. Добавить файл минимум в одну предметную категорию.
2. Добавить в `smoke` только если он не собирает IPK, не поднимает долгий сетевой стенд и стабильно выполняется быстро.
3. Не включать packaging-тест в обычную предметную категорию только из-за одного статического assertion внутри файла; тяжёлая сборка делает всю категорию тяжёлой.
4. Обновить описание категории, если смысл набора изменился.
5. Запустить `node --test tests/testCategories.test.mjs` и саму изменённую категорию.

## Внутренняя квота pairing и восстановленные проверки LuCI r294

Проверяются выбранный путь/отсутствие, контроли недопустимых путей, UCI/FS-отказы,
настоящая блокировка во время cp и её отсутствие во время HTTP, сохранность новых
событий, отсутствие сети при неподготовленном снимке и очистка собственного workspace.
Протоколы и ограничения: [отчёт r313](audit-fixes-r313.ru.md).

## Выборочные проверки подготовки Яндекс-backup (r317)

Из корня репозитория: `node scripts/run-test-category.mjs --file yandexBackupRuntime.test.mjs --file yandexDiskRuntime.test.mjs`.
Нужны Node.js, Python 3, POSIX sh и cp/cmp/tar; на Windows — Git Bash и
`PYTHON_EXECUTABLE`. Сценарии ссылок/прав требуют POSIX, отдельный BusyBox tar
сценарий выполняется при наличии applet. Ожидается exit 0; меняются только
уникальные `.build`-fixtures, очищаемые после теста. Сеть/UCI моделируются.
Положительная модель uploader доказывает подготовку, не доставку; полный native
uploader пока обязан сообщить собственный известный отказ, а не фиктивный успех.
Точные команды, прошлые неуспехи и зависимости: [r317](audit-fixes-r317.ru.md).

## Выборочные проверки Yandex PUT и HEAD (r318)

`yandexUploadRuntime.test.mjs` исполняет настоящий uploader/verify и архивный caller,
с реальными файлами и моделями UCI/curl. Fault-утилита выбирается только там, где
проверяется её отказ; trace доказывает достижение. Из корня, при Node/Python/POSIX:

```sh
node scripts/run-test-category.mjs --file yandexUploadRuntime.test.mjs --file yandexDiskRuntime.test.mjs --file yandexBackupRuntime.test.mjs
```

Exit 0 и отсутствие fail/skipped подтверждают локальную границу. Все фикстуры
создаются в `.build` и убираются при нормальном завершении. Настоящие Яндекс/TLS
сервиса, OpenWrt и восстановление этим не проверены. Для нового HTTP-контракта есть
дополнительный loopback TLS-стенд в поставленных доказательствах; точный запуск,
сертификат и сравнение staged/baseline описаны в [r318](audit-fixes-r318.ru.md).

## Выборочные проверки снимка журнала Яндекс Диска (r319)

`yandexEventsRuntime.test.mjs` исполняет полный entry/uploader/verify с HTTP/UCI-моделями
и реальными файлами/flock. Проверяются выбранный/default/отсутствующий журнал,
ошибки подготовки, сохранность очереди, блокировка только до HTTP и рост живого файла.
Два прежних теста `yandexDiskRuntime` больше не исправляют entry в fixture.

Команды, выбор смежных проверок, сравнение исходников и получение трасс —
[runbook r319](audit-fixes-r319.ru.md). На Windows неконкурентные fixtures явно
моделируют flock; Linux-поведение доказывается только POSIX-тестами. Пропуск не
считается аппаратным подтверждением. Общие библиотеки не изменены, добавлен новый
потребитель в карту влияния. Нет оснований запускать Android или весь suite.

## Проверки результата и файла синхронизации Яндекс Диска (r320)

`yandexSyncRuntime.test.mjs` проверяет оба полных входа и отдельный status-reader:
ранние отказы, неизменный основной ответ при недоступном статусе, сохранность прежних
байтов/чужого файла, закрытые права, проверку схемы и ограничение чтения. В тестах
UCI/HTTP/jshn — явно обозначенные модели; rename и параллельные процессы настоящие.
Не выдавать synthetic symlink/fault за сетевой взлом. Windows-пропуск POSIX-сценария
не доказывает его прохождение. Вызовы отказавших утилит подтверждаются trace.
Достаточен профильный и прямой зависимый набор; команды и границы —
[runbook r320](audit-fixes-r320.ru.md). Полный suite по факту этой правки не требуется.


## Скачивание Яндекс Диска: r321

`yandexDownloadRuntime.test.mjs` запускает настоящий CLI на изолированных файлах;
HTTP/UCI моделируются, отказы обязаны оставлять trace. Выборочная группа: этот файл,
`yandexDiskRuntime`, `yandexUploadRuntime`, `yandexSyncRuntime`, `logStorage`,
`portableShellAndStatus`, package hardening/IPK и изменённая карта тестов. Полный
suite, Android и несвязанные writers не требуются для узкой правки download.
Поздние ошибки сравниваются отдельно с r320, где исправлена только одна строка
объявления; это не доказательство полного исполнения неизменённого старого CLI.
Loopback HTTPS-стенд с настоящим curl приложен к доказательствам, не использует
аккаунт Яндекса и не отключает TLS. Команды и ограничения —
[отчёт r321](audit-fixes-r321.ru.md).

## Квота и общий контекст отправителя Яндекс Диска: r322

`yandexContextRuntime.test.mjs` исполняет полный CLI с двумя настоящими локальными
архивами и настоящей подготовкой config; UCI/HTTP представлены моделями. 42 сценария
проверяют quota-reader и вложенный контекст на определённых границах запросов;
каждый отказ/смена обязан оставить trace. Реальные аккаунты и router не используются.
Прежняя r321 сравнивается без поправок исходника. Поздний сценарий намеренно не
требует восстановления уже удалённых ранее подтверждённых архивов.

Область: этот файл, direct consumers изменённых credentials/root/probe/MKCOL/PUT
helpers (`yandexDiskRuntime`, `yandexUploadRuntime`, `yandexBackupRuntime`,
`yandexEventsRuntime`, `yandexSyncRuntime`, `yandexDownloadRuntime`), dispatcher,
writer, package hardening/IPK и карта отбора. Несвязанные Android/firewall не нужны.
Полный suite не требуется по факту нового коммита. Повторение и ограничения —
[отчёт r322](audit-fixes-r322.ru.md).

## Облачные отправители: выбор backend в r323

`yandexContextRuntime.test.mjs` и `googleDriveUploadRuntime.test.mjs` содержат
`selected storage boundary`: HTTP-модель меняет только `global.log_storage`,
проверяются след изменения, последующие запросы и сохранность архивов. Успех не
означает нативный UCI, живое облако или возможность отозвать уже ушедший HTTP.
Системное sh используется для детерминированных подстановок; BusyBox syntax не
подменяет fault-injection runtime. [Runbook r323](audit-fixes-r323.ru.md).
