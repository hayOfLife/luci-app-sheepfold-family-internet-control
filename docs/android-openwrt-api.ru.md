# API между Android-приложением Sheepfold и OpenWRT

С r293 внешний ограничитель запросов возвращает **503 `rate_limit_unavailable`**, если
нельзя проверить/сохранить квоту или обязательный helper отсутствует. Это не отзыв
привязки. **429 `rate_limited`** означает подтверждённое исчерпание квоты, `Retry-After`
содержит проверенный остаток окна в секундах, а не всегда 60. Изменение не добавляет
автоповторов команд и не меняет внутренний pairing-limit. [Проверки r293](audit-fixes-r293.ru.md).

С r292 отказ чтения token-записи, SHA-256 или часов при server-bound авторизации
даёт **503 `auth_backend_unavailable`**, а не окончательный 401; прежняя привязка не
отзывается сервером. Неизвестный/истёкший Bearer и повреждённые метаданные остаются
ошибками авторизации. Это не новая политика повторов команд и не типизация всех
возможных отказов UCI/storage. Подробности: [B35–B37 и проверки](audit-fixes-r292.ru.md).


Документ описывает целевой API для связи родительских Android-телефонов с backend-частью Sheepfold на OpenWRT-роутере.

Административные endpoint предназначены только для устройств родителей. Отдельное детское приложение получает через публичный `/client-status` только статус собственного устройства и разрешённые родителем возможности; административных функций у него нет.

## Текущий статус реализации

### Исправления чтения и повторов r288

`GET /cgi-bin/sheepfold-api/devices` возвращает 503 `devices_unavailable`, если CLI
завершился ошибкой или не вернул результат. Частичный вывод не публикуется, настоящая
пустая коллекция `[]` остаётся успешной. Это временная server error, не признак отзыва
токена. Старый успешный формат и десять полей устройства сохранены; все строки корректно
экранируются, а `adminLogin` по-прежнему ограничен валидным владельцем admin-устройства.

Недоступная конфигурация не превращается в разрешающий `/client-status`: результат
`unknown`. При корректном `status=none` от evaluator сохраняется известное время будущего
начала расписания; внутреннее название правила ребёнку не раскрывается. Это расчёт,
не доказательство успешного применения nft или отключения потока точно по часам.

Повтор `device-allow` с уже сохранённым allow подтверждает firewall sync до успеха.
Непосредственный CLI `device-temp-access` также валидирует 1–1440 минут до записи UCI:
ведущие нули — десятичные, ошибочное явное значение отклоняется. Отсутствующий CLI-аргумент
сохраняет прежний default 30 минут; HTTP endpoint по-прежнему требует явное `minutes`.
Подробные причины, проверки и границы: [реестр](bug-register.ru.md), B14–B21.

### Исправления CGI r287

Legacy form-endpoints используют общий `sheepfold-lib-form`: последнее поле не требует
завершающего `&`. До dispatch проверяется вся форма, включая неиспользуемые поля;
повтор ключа, ошибочный percent-encoding и NUL отклоняются. Отказ чтения тела завершает
родительский CGI, а не только подстановку команды. Ограничение тела — 65536 байт;
заявленная длина должна совпасть с прочитанной. Размер сверх лимита возвращает 413,
некорректная длина/форма — 400; backend-команда в этих случаях не запускается.

Действующий POST `/cgi-bin/sheepfold-api/device/temp-access` требует `minutes` — целое
десятичное число 1–1440; пропуск/ошибка возвращают 400 `invalid_minutes`, не 30 минут
по умолчанию. `/log/clear` возвращает 500 `log_clear_failed`, когда файл очистить нельзя.
Обычные restricted/scheduled результаты передаются child API как `disabled`, не `unknown`;
внутренние названия разрешающих правил ребёнку по-прежнему не выдаются.

### GET `/cgi-bin/sheepfold-api/devices`: принадлежность родительских устройств

Авторизованный текущий endpoint дополнен необязательным `adminLogin`. Для устройства с
`adminDevice=true` это валидный `admin_login` из UCI; для остальных либо повреждённого
логина это пустая строка. Пароли, QR-коды и токены сюда не добавлены.
APK сопоставляет логин с безопасной проекцией `admin-config.administrators` и определяет
текущего родителя по `deviceId` своей парной записи. Старый клиент игнорирует новое поле,
новый клиент без поля не угадывает владельца. Это добавочное поле, не новая UCI-схема.
Ниже целевой `/api/v1/devices` с `adminOwnerId` остаётся проектным контрактом, не этим endpoint.

### GET `/cgi-bin/sheepfold-api/support-report/config`

Авторизованный endpoint родительского APK возвращает public-only Tink HPKE keyset, key ID,
crypto suite и максимальный размер ciphertext (§feedback, §srep001). Private key на роутере
отсутствует. При пустой production-конфигурации ответ содержит
`support_report_not_configured`.

### POST `/cgi-bin/sheepfold-api/support-report`

После точного предпросмотра APK шифрует `support-report-v1` на телефоне и передаёт только:

```text
reportId=canonical base64url, 16 случайных байт
recipientKeyId=ID публичного операторского ключа
ciphertext=canonical base64url HPKE payload
```

Роутер не принимает plaintext, контакт, диагностику или флаг её включения. Он проверяет поля,
подписывает envelope отдельным Ed25519-ключом и отправляет его на HTTPS endpoint без redirect.
Ограничение: не более трёх попыток в час. Полный контракт, whitelist диагностики и ротация
ключей описаны в [документе транспорта](support-report-transport.ru.md).

Если центральный сервер достиг безопасного лимита хранения, роутер возвращает HTTP `503`,
`error=support_report_server_maintenance` и сообщение «Отказано, ведутся работы на сервере.».
Android сохраняет заполненную форму и позволяет повторить отправку позже; повторное сопряжение с
роутером для этой ошибки не требуется.

Legacy `POST /feedback` остаётся только для LuCI и прежнего Yandex Cloud канала. Родительское
APK его больше не вызывает; детское APK не содержит ни один feedback/report маршрут.

Этот документ описывает целевой контракт. В текущей ветке уже есть локальный сервис на порту `5201`, discovery-файл `/.well-known/sheepfold.json` и CGI endpoint `/cgi-bin/sheepfold-api`, который отдаёт базовые сведения о роутере, версии, порте и пути API, диагностический снимок `/cgi-bin/sheepfold-api/router-info`, привязку админского телефона `/cgi-bin/sheepfold-api/pair` и ранний endpoint ИИ-помощника `/cgi-bin/sheepfold-api/ai-assistant`.

Рабочий локальный API сейчас доступен через `/cgi-bin/sheepfold-api`. Сопряжение родительского телефона использует короткоживущий одноразовый код, HTTPS с закреплением публичного ключа из QR v2 и Bearer-токен, привязанный к числовому ID и MAC админского устройства. Backend изолированно подготавливает ID, токен, белый список устройств и административные права и фиксирует настройки со сжиганием кода. Ошибки обрабатываются cleanup/rollback (§pairtx1, §tlspinv2); границы конкурентных записей, файловых отказов и потери питания уточнены ниже, универсальная атомарность не заявляется.

### Уточнение текущего pairing в r291

Успешный `/pair` сохраняет прежние JSON-поля и 40-символьный Bearer. Но весь POST теперь
проверяется общим строгим form helper: некорректное кодирование, повтор поля (включая
кодированное имя) и сырой управляющий символ дают `400 invalid_form` (сырой NUL,
непредставимый в shell, обнаруживается как ошибка длины). Literal backslash больше не
интерпретируется как escape; в `code` он отклоняется прежним `400 invalid_code`. Отказ чтения,
недопустимая Content-Length или усечённое тело дают `400 body_read_failed`, тело больше
4096 байт — `413 request_too_large`. Ошибки имеют прежний envelope `app/ok/paired/error`,
не меняют целевой `errorCode`; это не новый endpoint и не требование завершающего `&`.

Отказ случайности/SHA/записи токена или подготовки снимка даёт существующий server-error
путь без успешной привязки. QR не расходуется до подтверждения подготовленного изменения.
Повтор автоматически не выполняется: после неоднозначного сетевого сбоя всё равно нужно
проверить состояние. С r291 локально проверены явные подготовительные отказы и сохранение
чужой записи; rollback при power loss, параллельных UCI-писателях и отзывах не считается
доказанным. Подробности: [B31–B34 и R03/R08](bug-register.ru.md), [прогоны](audit-fixes-r291.ru.md).

Для защищённых текущих endpoint-ов backend отвечает `401` с машинным кодом: `device_unbound`, если записанные на роутере ID/MAC больше не принадлежат админскому устройству, `device_source_mismatch`, если фактический MAC у IP соединения отличается от привязанного, и `invalid_token` для недействительного, истёкшего или отозванного токена. Android начинает новое сопряжение при `device_unbound`/`invalid_token`, не весь onboarding. Начиная с parent `0.1.61`, явный `device_source_mismatch` сохраняет прежнюю привязку и сообщает об отказе текущему источнику; возврат в прежнюю сеть может восстановить доступ без QR. Сам запрос не разрешается и не повторяется автоматически. `5xx` и транспортные ошибки credential также не удаляют (§authrs1).

Нестандартные заголовки `X-Sheepfold-Device-Id` и `X-Sheepfold-Device-Mac` не являются источником права доступа. Некоторые сборки uhttpd не передают их CGI вообще. Backend находит файл токена по Bearer, читает из него ID/MAC и только затем проверяет привязку и сетевой источник. Android может отправлять эти заголовки для диагностики и обратной совместимости, но отсутствие или подмена заголовка не меняют серверную личность токена (§pairtx1).

Имя роутера допустимо только в подписанном `SF2`: Android один раз разрешает его, отбрасывает публичные/loopback/multicast-адреса, пробует локальные IP с проверкой SPKI и сохраняет IP успешного endpoint. После сопряжения обычные команды, ИИ и восстановление изменённого порта используют этот IP без нового DNS-разрешения. Ручной ввод и старый `SF1` требуют прямой локальный IP; старое сохранённое подключение с hostname просит выполнить сопряжение заново (§dnsbind1). Будущий alias `/api/v1/*` и refresh-token ещё не завершены, но текущий CGI pairing уже не является UI-заглушкой.

Детский APK не получает административный QR и поэтому не разрешает сетевые имена вообще: автопоиск использует IP шлюза активной Wi-Fi/Ethernet-сети, а ручное поле принимает только локальный IP. Та же проверка стоит в общем `ChildRouterHttps`, поэтому status, просьба о времени, SIM/Wi-Fi-отчёты и детский ИИ не могут уйти на публичный адрес (§dnsbind1).



### Родительский `/api/v1/admin-config`

Авторизованный `GET /cgi-bin/sheepfold-api/api/v1/admin-config` возвращает
`schemaVersion`, `revision`, отдельную `wifiRevision`, capabilities, расписания,
группы, безопасные поля администраторов, устройства, политики уведомлений,
итоговое состояние Wi-Fi, его общее расписание и редактируемые точки доступа.
`password_hash`, pairing-коды, Bearer-токены и секреты интеграций в ответ не входят.
Wi-Fi-ключ является узким исключением: он передаётся только уже сопряжённому
администраторскому APK по HTTPS с проверкой сохранённого отпечатка роутера и нужен
для QR-кода и редактирования той же сети, которую показывает LuCI.

Запись выполняют POST-подмаршруты `schedule/save`, `schedule/delete`, `group/save`,
`group/delete`, `device/save`, `notifications/save`, `wifi/save`,
`wifi-automation/save` и `wifi-control`. Sheepfold UCI payload передаёт
`schemaVersion` и `expectedRevision`; Wi-Fi дополнительно передаёт
`expectedWifiRevision`. Устаревший снимок получает `409 revision_conflict`.
Backend сериализует изменения одним `flock`, проверяет committed state и держит
снимок изменяемого файла для отката. Если сохранённый `/etc/config/wireless` не
удалось применить, прежний файл и прежнее состояние Wi-Fi восстанавливаются.

С r295 неуспешный `uci show` не создаёт ревизию из пустого или частичного вывода;
неуспешный/повреждённый SHA-256 также отклоняется. `config_read_failed` и
`revision_hash_unavailable` отображаются как HTTP 503. Это не равнозначно конфликту
ревизий и не разрешает автоматически повторять запись: ошибка окончательного чтения
может возникнуть уже после commit. Файл wireless может штатно отсутствовать на
роутере без Wi-Fi. Значения JSON экранируются без замены управляющих символов пробелами.
Списки ID обрабатываются без filesystem globbing: `*` не означает «все устройства».
Доказательства и ограничения целостности снимка — [B50–B52](bug-register.ru.md).

Реализация разделена по ответственности (§apicon1):

- `sheepfold-api-admin-config` проверяет окружение и диспетчеризует действие;
- `sheepfold-lib-admin-config-model` только читает UCI, вычисляет ревизии и строит JSON;
- `...-common` владеет общей блокировкой, optimistic revision и UCI-транзакцией;
- `...-schedules`, `...-groups`, `...-wifi`, `...-notifications` и `...-devices`
  проверяют и выполняют команды своих областей.

Доменные файлы подключаются в один shell-процесс: это не отдельные конкурирующие
commit-точки. Модель чтения не должна записывать UCI, а доменный модуль не должен
создавать собственный обход общей транзакции.

Для каждой группы ответ содержит вычисляемый `scheduleIds`. Это проекция групповых
расписаний, чьи `targets` содержат ID секции группы, а не самостоятельное поле UCI.
`POST group/save` меняет связи только при `scheduleIdsPresent=1`; поле `scheduleIds`
содержит разделённые запятыми ID групповых расписаний. Отсутствие признака сохраняет
существующие связи для совместимости со старым APK. Расписание устройства передать в
этом поле нельзя (§grpsch1).
При изменении устройства UCI записывается до обновления firewall. Если UCI полностью
совпадает с запросом, но runtime-обновление не удалось, ответ остаётся успешным и
содержит `mutation.runtimeApplied=false`; APK показывает, что настройки сохранены,
но применение нужно повторить. Ошибка до полного сохранения возвращается как ошибка,
поэтому частичное состояние не маскируется под успех.
Администраторские устройства запрещены как цели расписаний и участники семейных групп.

APK не выпускает административный QR. Сопряжение новых администраторских устройств
остаётся в защищённом LuCI. Уже сопряжённый родительский APK может редактировать
свои Wi-Fi-сети и строить QR подключения (§pairsec, §apicon1).

### Server-driven доступность ИИ (§prodvar)

Единый родительский APK читает из авторизованного `GET /router-info`:

```json
{"capabilities":{"aiAssistant":true}}
```

`true` означает, что на роутере установлена редакция AI Support, ИИ включён, выбран поддерживаемый провайдер и для него сохранён ключ. Формат роутерного пакета IPK/OpenWrt APK значения не имеет. Поле не раскрывает провайдера или ключ. При отсутствии поля Android использует `false`.

Детский `GET /client-status` дополнительно может вернуть `aiAssistantAvailable`, `childAiAvailable`, `childAiAllowed` и `personalGroupRequired`. Вкладка показывается только при `childAiAvailable=true`; без личной группы она остаётся заблокированной с понятным баннером. Каждый POST к ИИ всё равно повторно проверяет разрешение на роутере.



### Минимизированный детский status API v3

`GET /cgi-bin/sheepfold-api/client-status` использует `apiVersion=3`. Публичный ответ не содержит `accessMode`, имени разрешившего правила, `scheduleConflict` или имени личной группы. При `internetState=enabled` поле `message` равно `null`; приложение показывает только факт доступа и `nextAccessChangeTime`. При `disabled` или `unknown` разрешено короткое безопасное объяснение без раскрытия внутреннего порядка семейных правил.

Политика функций передаётся отдельными булевыми полями `simChangeReporting`, `wifiNetworkReporting` и `wifiLocationReporting`. Детский APK показывает объяснение и запрашивает соответствующие Android-разрешения только после получения `true`; отказ не ломает основной статус. Подробный AI-контекст при необходимости должен готовиться внутри защищённого router-side gate, а не восстанавливаться из публичного child response (§b5wkq2e, §simchg1, §childwifi1).

### Время следующего изменения доступа

`GET /client-status` возвращает `nextAccessChangeTime` в строгом формате локального времени
роутера `HH:mm` либо `null`. Backend вычисляет не ближайшую границу любого расписания, а первую
границу, на которой фактический итоговый доступ этого устройства действительно изменится с
учётом расписаний устройства и группы, их приоритета и обычного fallback-доступа.

Детский UI показывает только это время, например `Следующее изменение доступа: 19:30`, без
обратного отсчёта и без раскрытия названия правила. Поля `accessEndsAt` и `minutesRemaining`
сохраняются для совместимости и локального уведомления о завершении временного доступа, но не
должны дублироваться на экране. Расчёт будущих границ запускается только по запросу статуса
детского устройства; минутная синхронизация firewall его не выполняет.

### POST `/cgi-bin/sheepfold-api/sim-report` (§simchg1)

Публичный локальный endpoint детского APK для best-effort снимка активных SIM. Он не принимает MAC, Sheepfold ID или роль от клиента: backend определяет устройство только по `REMOTE_ADDR`, DHCP lease и ARP. Допускается не более 12 запросов за 5 минут от IP и не более 2048 байт.

Формат `text/plain; charset=utf-8`:

```text
version=1
sim=0|<64 hex SHA-256>|+79991234567|250|01
```

Можно передать до четырёх строк `sim`; номер и MCC/MNC могут быть пустыми. Первая SIM, уже установленная при первом отчёте приложения, создаёт событие с пометкой `(обнаружена в телефоне при установке приложения)`. Повтор того же снимка не пишет UCI и журнал. Роутер хранит не более 16 отпечатков и 16 впервые замеченных пар `отпечаток + доступный номер`; позднее появление номера сохраняется без ложного события смены SIM. Подробности и границы точности: [`sim-change-notifications.ru.md`](sim-change-notifications.ru.md).

### Новые Wi-Fi-сети детского устройства (§childwifi1)

Публичный `GET /cgi-bin/sheepfold-api/client-status` сообщает детскому APK два логических поля:

```json
{
  "wifiNetworkReporting": true,
  "wifiLocationReporting": false
}
```

APK не собирает и не отправляет сведения о сети, пока `wifiNetworkReporting` не равен `true`. Поле `wifiLocationReporting` отдельно разрешает добавить последнее доступное местоположение телефона. Последняя успешно полученная политика сохраняется на телефоне: пока домашний роутер недоступен, APK может накопить до 100 безопасных отчётов и передать их после возвращения. `false` удаляет очередь, а отзыв геолокации вырезает координаты из неотправленных записей.

`POST /cgi-bin/sheepfold-api/wifi-network-report` принимает не более 1024 байт `text/plain; charset=utf-8` и ограничен 12 запросами за 5 минут от IP:

```text
version=1
fingerprint=<64 hex SHA-256>
ssid=School guest Wi-Fi
observed_at=<Unix time>
location=<latitude>|<longitude>|<accuracy meters>|<Unix time>
```

Строка `location` необязательна. Открытый BSSID не передаётся: APK вычисляет `fingerprint` из `SSID+BSSID` до отправки. Backend не принимает MAC, Sheepfold ID или роль от клиента, а определяет устройство по `REMOTE_ADDR`, DHCP и ARP. Старые координаты отбрасываются; сохранённое значение обозначает последнее доступное положение телефона, но не подтверждённый адрес Wi-Fi-точки.

Административные маршруты требуют Bearer-токен, серверно связанный с числовым ID и MAC привязанного родительского устройства:

- `GET /cgi-bin/sheepfold-api/child-wifi-networks` — ограниченная история, не более 100 сетей на детское устройство и не старше 90 дней;
- `DELETE /cgi-bin/sheepfold-api/child-wifi-networks` — очистка истории.

Первый отчёт о новом отпечатке создаёт запись журнала и событие общей очереди `/notifications`. Поэтому все сопряжённые родительские APK получают его обычным механизмом административных уведомлений; настроенный Telegram также получает событие. Полный контракт: [`child-wifi-network-notifications.ru.md`](child-wifi-network-notifications.ru.md).

Немедленная доставка из чужой сети не обещается: Sheepfold не использует для этой функции облако или прямое внешнее подключение к домашнему роутеру. Фоновый Android-опрос является best-effort и может пропустить очень короткое подключение.

## ИИ-помощник

### POST `/cgi-bin/sheepfold-api/ai-assistant`

Текущий CGI endpoint отправляет запрос к выбранному ИИ-провайдеру от имени роутера. API-ключи хранятся в UCI-настройках роутера и не передаются в APK.

Формат запроса: `application/x-www-form-urlencoded`.

Поля:

- `message`: текст вопроса;
- `deviceId`: числовой ID парного устройства;
- `clientRole`: `parent` или `child`; backend не доверяет полю и сверяет его с токеном, MAC и UCI;
- `isAdministrator`: `1` для родителя, `0` для ребёнка; также перепроверяется backend-ом;
- `consentVersion`: для детского клиента текущее значение `child-ai-v1`;
- `includeInfo`: `1`, если родитель явно разрешил добавить контекст со страницы `Настройки -> Информация`;
- `includeLogs`: `1`, если родитель явно разрешил добавить журнал программы Sheepfold;
- `googleAccount`: зарезервированное административное поле; текущий родительский UI его не отправляет, а детскому клиенту оно запрещено.

Провайдер, модель, URL, API-ключ и версию системного промпта выбирает только роутер из UCI. Значения `provider` и `model`, присланные клиентом, не являются источником конфигурации.

Перед отправкой журнала backend маскирует MAC-адреса, IP-адреса и похожие на секреты поля. По контракту APK обязан показывать отдельные переключатели и preview. В текущем родительском UI этот экран ещё не реализован, поэтому `includeInfo` и `includeLogs` отправляются как `0`.

Для `deepseek` и `grok` backend проксирует OpenAI-совместимый JSON, Android читает `choices[0].message.content`.

Для `gemini` backend вызывает Google Gemini `models/{model}:generateContent`, Android читает `candidates[0].content.parts[0].text`. В интерфейсе этот вариант называется `Gemini Free`, потому что он рассчитан на бесплатные лимиты Google AI Studio; фактические лимиты зависят от аккаунта Google, региона и текущих правил Google.

Ошибки Sheepfold возвращаются в формате:

```json
{
  "app": "sheepfold",
  "ok": false,
  "error": "deepseek_api_key_missing",
  "message": "DeepSeek API key is not configured on the router."
}
```

## Базовая схема

- Android дома подключается к роутеру напрямую по локальной сети.
- Первичное сопряжение выполняется локально: родитель открывает LuCI, создаёт/открывает администратора и сканирует QR-код или вводит ручные данные.
- Полный API, LuCI и SSH остаются локальными. Вне дома Android не должен подключаться к ним через VPN/WireGuard или проксировать их через публичный сервер.
- Короткие подтверждаемые команды и уведомления смогут проходить через выбранный мессенджер либо отдельный family message relay. Его политика `local_preferred`, credentials, E2E envelope, TTL и fallback заданы в [`android-router-message-relay.ru.md`](android-router-message-relay.ru.md) (§mrelay1).
- Family message relay выключен по умолчанию. Strict protocol, synthetic-only server pilot и
  unwired Android client foundation реализованы; Android production provisioning/UI/lifecycle и
  device/field tests отсутствуют, OpenWrt runtime отсутствует до отдельного native-helper и
  target/live-router gate. Поэтому `clientsReady=no`, `realDataAllowed=no`. Он не меняет
  существующие `/api/v1/*` endpoint и никогда не получает локальный Android Bearer.
- Один роутер может иметь несколько администраторов и несколько привязанных телефонов.

## Транспорт

Целевой основной backend Android API:

```text
https://<router-host>:5201/api/v1
```

Порт по умолчанию: `5201`. Его можно изменить в LuCI в настройке `Порт`.

Для первичного обнаружения используются или допускаются публичные endpoint-ы без авторизации:

```text
https://<router-host>:5201/.well-known/sheepfold.json
https://<router-host>:5201/cgi-bin/sheepfold-api
https://<router-host>:5201/api/v1/ping
```

`/cgi-bin/sheepfold-api` сейчас используется как ранний lightweight endpoint. Боевой вариант должен постепенно перейти к `/.well-known/sheepfold.json` и `/api/v1/ping`.

Домашний доступ v1 описан в [`home-network-access.ru.md`](home-network-access.ru.md).
После аутентификации dispatcher добавляет заголовок `X-Sheepfold-Home-Endpoints` с CSV
из первого IPv4 LAN и разрешённого прямого WAN API URL. Старые клиенты игнорируют его;
старые роутеры могут не выдавать его. Parent APK сохраняет список только после успешного
ответа и SPKI-проверки. `403 home_network_not_allowed` означает запрет сетевого источника,
не отзыв токена. Child API на дополнительной сети закрыт; публичный WAN не открывается (§homen01).

## QR и ручное сопряжение

QR не должен содержать root-пароль роутера, LuCI session cookie, токены ботов, AI-ключи или постоянные Android credentials.

QR содержит короткоживущие одноразовые данные и публичный отпечаток TLS-ключа:

```text
SF2|h=192.168.2.1|p=5201|u=owner|c=Ab7+qK92mN|spki=<64-hex-sha256>
```

Поля:

- `h`: адрес роутера, который видит LuCI.
- `p`: порт Sheepfold Android API.
- `u`: логин администратора.
- `c`: одноразовый код сопряжения, действующий 10 минут.
- `spki`: SHA-256 от DER SubjectPublicKeyInfo активного публичного ключа uhttpd. Это не секрет и не позволяет восстановить приватный ключ.

LuCI не показывает QR, если backend не смог прочитать сертификат, вычислить SPKI или вернуть ровно 64 шестнадцатеричных символа. Android проверяет `spki` во время TLS handshake до отправки логина и одноразового кода. Перевыпуск сертификата с прежним ключом не ломает pinning. Формат `SF1` читается только для совместимости со старыми QR и использует прежний TOFU-путь; новые LuCI-сборки выпускают только `SF2` (§tlspinv2).

Сверка дополнительного короткого кода между Android и LuCI намеренно не используется. Первый телефон, успешно предъявивший действующий QR, получает credential, а backend сразу сжигает код. LuCI обязан предупреждать владельца не показывать и не пересылать QR (§pairux1).

Для ручного ввода показывается тот же временный пароль без QR:

```text
адрес 192.168.2.1, порт 5201, логин owner, код Ab7+qK92mN
```

Требования к ручному временному паролю:

- 10 случайных символов;
- наборы: `abcdefghkmnpqrstuvwxyz`, `ABCDEFGHKMNPQRSTUVWXYZ`, `2456789`, `+-*()[]{}<>?@#$%^&:;.,`;
- не больше 3 спецсимволов;
- генерируется только backend-частью роутера через криптографически стойкий генератор;
- хранится на роутере только как hash/невосстановимый секрет;
- после успешного использования немедленно помечается как `consumed`.

## Действия по подтверждению ИИ-помощника

ИИ-помощник не выполняет действия напрямую. Он может только подготовить предложение, которое APK показывает родителю для подтверждения.

Рекомендуемый поток:

1. ИИ распознаёт намерение пользователя.
2. APK показывает карточку: что будет изменено, кого затронет, как отменить.
3. Родитель нажимает подтверждение.
4. APK вызывает backend.
5. Backend пишет административное событие в журнал.

Примеры будущих endpoint-ов:

```text
POST /api/v1/devices/{id}/static-lease
POST /api/v1/emergency-sites
POST /api/v1/groups/{id}/allowlist-only
POST /api/v1/groups/{id}/activity-log
POST /api/v1/devices/{id}/activity-log
POST /api/v1/devices/{id}/temporary-access
```

Передача MAC/IP/имён устройств/журналов ИИ-провайдеру допускается только после отдельного подтверждения со списком полей.

## Журнал интернет-активности

Журнал интернет-активности не является обычным административным журналом.

Целевые endpoint-ы:

```text
GET /api/v1/devices/{id}/activity-log/status
POST /api/v1/devices/{id}/activity-log/export
POST /api/v1/devices/{id}/activity-log/analyze
POST /api/v1/groups/{id}/activity-log
```

Требования:

- не собирать для админских устройств, белого списка и чёрного списка;
- показывать размер и период, но не показывать сырой журнал по умолчанию;
- для анализа ИИ передавать только подтверждённый период и только перечисленные поля;
- если есть только router/DNS-данные, не утверждать, что доступны заголовки видео, описания или комментарии.

Отзывает refresh token текущего телефона.

LuCI показывает эту ссылку как отдельный QR рядом с QR подключения к Wi-Fi. Телефон сначала подключается к Wi-Fi, затем открывает `/q/{quickAllowlistToken}`.

Backend роутера обязан:

- проверить TTL и одноразовость `quickAllowlistToken`;
- определить MAC телефона только по router-side данным DHCP/ARP/neighbor, а не по данным, присланным браузером телефона;
- отклонить повторное использование токена;
- не добавлять устройство, если MAC уже находится в чёрном списке;
- записать действие в журнал администраторов;
- вернуть понятную HTML-страницу результата для телефона.

Если политика проекта требует подтверждения родителем, endpoint должен добавить устройство в список кандидатов быстрого добавления, а не сразу в белый список. Если родитель явно включил режим прямого добавления по одноразовой ссылке, backend может добавить устройство в белый список сразу после всех проверок.

## Wi-Fi

### GET `/api/v1/admin-config`

Ответ:

```json
{
  "wifiRevision": "sha256-of-wireless-uci",
  "wifiEnabled": true,
  "wifiAutomation": {
    "enableMode": "never",
    "enableTime": "07:00",
    "disableMode": "time",
    "disableTime": "23:00"
  },
  "wifiNetworks": [
    {
      "section": "default_radio0",
      "device": "radio0",
      "band": "2.4GHz",
      "ssid": "mySweetHome",
      "password": "password",
      "encryption": "sae-mixed",
      "channel": "auto",
      "enabled": true
    }
  ]
}
```

Пароль Wi-Fi возвращается только после Bearer-аутентификации сопряжённого
администраторского устройства. Android сам строит стандартный `WIFI:` QR; пароль
не попадает в диагностический `/router-info`, журналы или AI-контекст.

### POST `/api/v1/admin-config/wifi/save`

Изменяет SSID, пароль, защиту, канал и состояние одной точки доступа. Запрос
передаёт `section`, новые значения, `expectedWifiRevision` и `confirm=1`.
Backend принимает только существующую `wifi-iface`, проверяет связанную
`wifi-device`, сохраняет `/etc/config/wireless`, перезапускает Wi-Fi и откатывает
файл при ошибке применения.

С r296 имя SSID сохраняется без удаления краевых пробелов; допустимы 1–32 байта,
не 32 символа Unicode. Для `psk`/`psk2`/`psk-mixed` принимаются фразы 8–63 байта
или ровно 64 hex-символа готового ключа. Неверный ввод даёт прежние ошибки 400
до записи и перезапуска. Для `owe` и `none` пароль не требуется, старый `key` удаляется.
Это не полная проверка SAE/Enterprise/WEP и возможностей установленного wpad.

Если восстановить файл не удалось, API возвращает **500 `config_rollback_failed`**;
если файл восстановлен, но повторный запуск Wi-Fi не подтверждён —
**502 `wifi_rollback_apply_failed`**. Имеющиеся аварийные копии не удаляются уборкой;
их путь передаётся только системному журналу, а не HTTP-клиенту. Они находятся
в RAM и не гарантированно переживут перезагрузку. Перед повтором требуется проверить
состояние роутера. Общая pending-очередь UCI и конкурентные изменения не объявлены
атомарными. Доказательства: [B54–B57 и R10](bug-register.ru.md).

Новый числовой `channel` должен присутствовать в `wifi_channel_list` выбранного радиомодуля.
Иначе `invalid_wifi_channel` возвращается до создания транзакции/записи. Прежний канал и `auto`
можно сохранить без iwinfo, чтобы отсутствие необязательного read-back не блокировало смену SSID.

### Каналы радиомодулей

`GET /api/v1/admin-config/wifi/channels` требует прежнюю Bearer-аутентификацию администратора,
доступен только как GET и входит в лимит `admin_read` 120 запросов за 60 секунд. В `admin-config`
capability `wifiChannelsRead=true` означает поддержку endpoint, не наличие каналов у каждого радио.
Без capability Android endpoint не вызывает. Пример ответа с синтетическими каналами:

```json
{"app":"sheepfold","radios":{"radio0":[1,6,11],"radio1":[36,40]}}
```

Это read-only запрос: до четырёх UCI `wifi-device`, два `ubus -t 1` вызова на радио:
`iwinfo phyname` с `section`, затем `iwinfo freqlist` с найденным `device`.
Ограничения ответов: 4 КиБ для имени phy, 64 КиБ для частот, до 256 элементов на радио.
Разбор через установленный OpenWrt jshn, без текстового извлечения JSON. Выбираются каналы
1–233 только с `restricted=0` и частотой своего `band`/legacy `hwmode`; дубликаты удаляются.
Неизвестный диапазон, отсутствие RPC/jshn или повреждённый/слишком большой ответ дают пустой список.
Это не активное сканирование эфира, flash не меняется, зависимости автоматически не устанавливаются.
Новые чтения запускаются только на Wi-Fi, не при обычном чтении других панелей и не в service tick.

Источник контракта: [OpenWrt rpcd iwinfo](https://lxr.openwrt.org/source/rpcd/iwinfo.c).
DFS, текущая country policy и драйвер всё равно могут отвергнуть канал или задержать включение:
список кандидатов не доказывает успешный запуск AP. Production shell-фильтр проверен локально
с контрактной заглушкой jshn/iwinfo в `tests/wifiChannelSafety.test.mjs`; реальная смена канала
и восстановление связи на OpenWrt в этом проходе не выполнялись.

### POST `/api/v1/admin-config/wifi-control`

Поле `enable=1` включает весь Wi-Fi, `enable=0` выключает. Оба действия требуют
`confirm=1`; перед выключением APK предупреждает, что телефон может потерять
соединение с роутером.

### POST `/api/v1/admin-config/wifi-automation/save`

Настройки автоматического включения/выключения всего Wi-Fi.

Если сохраняется любое автоматическое выключение Wi-Fi (`autoDisable.mode = "time"`), UI обязан показать непропускаемый дисклеймер минимум на 10 секунд. Кнопка подтверждения должна называться `Я понимаю риск, продолжить` и разблокироваться только после обратного отсчёта.

Текст дисклеймера должен объяснять: когда Wi-Fi отключится, через телефон, подключённый только по Wi-Fi, пользователь не сможет включить его обратно; заранее должен быть настроен мессенджер или действие кнопки WPS для включения Wi-Fi вне расписания.

Запрос использует тот же `application/x-www-form-urlencoded`, optimistic revision
и UCI-транзакцию, что другие изменения `admin-config`:

```text
schemaVersion=1
expectedRevision=<revision из GET>
enableMode=never
enableTime=07:00
disableMode=time
disableTime=23:00
confirmRisk=1
```

`confirmRisk=1` обязателен при `disableMode=time`; это дополнительная backend-защита
от случайного вызова, но она не заменяет десятисекундное предупреждение в UI.

`mode`:

- `never` — не выполнять автоматически;
- `time` — выполнять каждый день в указанное время роутера.

Backend должен использовать системное время роутера и журналировать фактическое включение/выключение.

### PATCH `/api/v1/router/buttons/wps`

Настройки короткого и долгого нажатия кнопки WPS.

```json
{
  "shortPressAction": "router_default",
  "longPressAction": "router_default"
}
```

Возможные значения:

- `router_default` — функционал роутера по умолчанию;
- `allow_wifi_connection` — дать подключиться к Wi-Fi;
- `allow_wifi_and_allowlist` — дать подключиться к Wi-Fi и добавить устройства в белый список, опасный режим;
- `disable_wifi` — отключить Wi-Fi.

Режим `allow_wifi_and_allowlist` нельзя включать без явного предупреждения: `Добавление устройств в белый список через WPS кнопку опасно так как при нажатии на неё, в течении 30 секунд - любое устройство сможет подключиться к вифи и попасть в белый список.`

Когда кнопка WPS нажимается и открывается 30-секундное окно подключения, все светодиоды должны мигать паттерном `1010000`. Один тик — полсекунды.

### PATCH `/api/v1/router/leds`

Настройка управления светодиодами роутера.

```json
{
  "mode": "router_default"
}
```

Возможные значения:

- `router_default` — функционал роутера по умолчанию;
- `off_forever` — отключить навсегда все светодиоды;
- `new_device_alert_until_luci_login` — сигнализировать светодиодами о новом устройстве до успешного авторизованного входа в LuCI.

Для `new_device_alert_until_luci_login`:

- в интерфейсе пояснение для режима сигнала показывать только при выборе этого режима: `Когда подключилось новое устройство, светодиоды на роутере зажгуться.`;
- после успешного входа в LuCI с паролем backend должен сразу вернуть дефолтное поведение светодиодов роутера;
- после просмотра уведомления о новом устройстве на телефоне любым администратором backend тоже должен сразу вернуть дефолтное поведение светодиодов роутера;
- простое открытие страницы без успешной авторизации не должно сбрасывать сигнал.

Реализация зависит от модели роутера и доступных OpenWrt LED triggers. Если устройство не поддерживает нужный режим, API должен вернуть понятную ошибку, а не молча делать вид, что настройка применена. Старое значение `blink_new_device_until_luci_seen`, если встретится в конфиге раннего прототипа, можно мигрировать в `new_device_alert_until_luci_login`.

Сбрасывает LED-сигнал о новом устройстве после того, как любой администратор просмотрел уведомление на телефоне или в выбранном мессенджере.

Backend должен проверить, что запрос пришёл от авторизованного администратора, записать событие в журнал действий и вернуть дефолтное поведение светодиодов роутера.

### GET/POST локальной страницы блокировки

Заблокированные HTTP-запросы должны получать быстрый локальный ответ от роутера, а не бесконечную загрузку.

Требования:

- браузерные GET/HEAD-запросы получают простую HTML-страницу с текстом из `blockedPageText`;
- POST/PUT/PATCH/DELETE получают завершённый ответ `403` с JSON, если клиент принимает JSON;
- игровые консоли, роботы-пылесосы, колонки и другие IoT-устройства должны получать короткий plain text или JSON-ответ, если они не ожидают HTML;
- ответ должен содержать технический маркер вроде `X-Sheepfold-Blocked: 1`;
- страница блокировки не должна открывать доступ к LuCI, SSH или Sheepfold API.

## Безопасность

- Все постоянные токены хранить на роутере только как hash/невосстановимые секреты.
- Access token должен быть короткоживущим.
- Refresh token можно отозвать отдельно для каждого телефона.
- Pairing token/code одноразовый и сжигается только backend-частью роутера.
- Android не должен принимать решение о “сожжённости” токена сам.
- Все административные действия пишутся в журнал с указанием администратора и телефона.
- Экспорт логов должен маскировать MAC, IP, chat/user ID и исключать секреты.
- Обычный API журнала не должен отдавать историю сайтов или DNS-query-log устройств в Android-приложение.
- Если отдельная функция истории интернет-активности будет добавлена позже, для неё нужен отдельный opt-in API, отдельные права, исключение устройств администраторов и белого списка, короткий срок хранения и отдельное предупреждение в интерфейсе.

### Защита сохранения и черновиков в локальном r297

Общие транзакции настроек Sheepfold (группы, расписания, уведомления, автоматизация
Wi-Fi) и `wifi-save` проверяют общую видимую очередь UCI перед подготовкой и перед
commit. Обнаруженные несохранённые изменения дают HTTP 409 `config_pending_changes`.
Пользователь должен завершить или отменить их в исходном редакторе; API не выполняет
общий `uci revert` и не коммитит чужой черновик как часть своей операции. Это не
утверждение о видимости всех отдельных rpcd session delta paths.

Wi-Fi хранит собственные промежуточные изменения в приватном каталоге транзакции.
После раннего отказа они удаляются вместе с ним, без замены действующего файла и
без перезапуска Wi-Fi. Откат файла вооружается только перед попыткой commit; прежние
коды неуспешного восстановления из r296 сохранены. Перед commit повторно проверяется
ревизия; наблюдаемый конкурентный commit даёт 409 `revision_conflict`.

Если не удалось создать защищённый каталог или проверенную исходную копию,
возвращается HTTP 503 `config_snapshot_failed`. Новые настройки в этой ветви не
записывались. Ошибка чтения очереди возвращает 503 `config_read_failed`. Ответы не
означают отзыва привязки и не запускают автоматический повтор команды. Изменение
после последней проверки всё ещё возможно: общего протокола всех UCI-writers нет.
Доказательства и границы — в [отчёте r297](audit-fixes-r297.ru.md).

## Просьбы ребёнка: подтверждение результата в r298

`POST /access-request` сохраняет прежние поля `ok`, `requestId`, `duplicate`.
Отказ получения ID от backend теперь даёт `503 access_request_unavailable`, а не
ложное отсутствие уже найденного устройства. Реально неизвестный источник остаётся
`404 device_not_registered`. Отказ журнала после сохранения не меняет успешный ответ.

`GET /access-requests` буферизует вывод своего helper до HTTP 200. Его ненулевой exit,
в том числе отсутствие исполняемого файла, даёт `503 access_requests_unavailable`
без частичного массива. Настоящий пустой список по-прежнему `200`/`requests: []`.
Auth, source guard, квоты и opt-in не изменены. Текущие APK обрабатывают не-2xx своим
общим путём ошибки; специальный новый экран или автоматический повтор не добавлен.
Историческая граница r298: внутренние read errors и гонки ещё не были закрыты.
Runbook: [r298](audit-fixes-r298.ru.md) (§child30).

### Очередь r299: сохранность при отказах

Оба пути используют отдельный lock очереди; проверка ID/opt-in не стала транзакцией UCI.
Проблемная или непрочитанная запись сохраняется и даёт HTTP 503 вместо успешного
пустого списка. Та же `access_request_unavailable` теперь охватывает очередь, часы
и её подготовку, поэтому message не ограничен ошибкой ID. Файловая публикация
по-прежнему даёт `500 request_failed` при отказе. Новые поля и повтор POST не добавлены.
Одинаковые параллельные просьбы возвращают один ID, duplicate не продлевает TTL.
Схема/часы и права проверяются, но лимиты RAM, аварии и несогласованные writers
остаются R11. Команды и доказательства: [r299](audit-fixes-r299.ru.md).
