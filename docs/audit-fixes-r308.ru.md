# Sheepfold r308: проверяемый расход и безопасная остановка очистки Google Drive

Дата: 10 сентября 2026 года. База: `abb68ca` (r307), потомок принятой `bdb3a92`.
Обе роутерные редакции: `0.1.0-308`. Работа локальная в `main`, push не выполнялся.
Коммит, дерево и контрольные суммы приводятся во внешнем протоколе поставки:
собственный будущий Git hash не записывается внутрь коммита.

## Результат и границы изменения

Исправлены две группы **B93–B94**. В [реестре](bug-register.ru.md) теперь **94
карточки**, не 94 независимо подтверждённые уязвимости. Изменены один production
shell-файл Google Drive, версия пакета, существующий runtime-тест и документация.
Новые зависимости, Android, приоритеты доступа, workflow, runner, категории и общие
fixtures не менялись. D01 и принятые доработки тестирования сохранены.

Это продолжение аудита облачного журнала, а не изменение правил детского доступа.
Тесты запускают настоящий shell-код, но HTTP, UCI и jshn представлены моделями.
Реальные Google-аккаунты не подключались; сетевых удалений в этом проходе не было.

## B93: корректный ответ давал ноль вместо фактического расхода

На неизменённой r307 три файла размером 10, 20 и 7 байт в двух папках дают расход
**0 вместо 37**, когда size передан строкой по схеме Google. Контроль с числовыми
size в компактном JSON даёт **27 вместо 37**: жадный regex видит лишь последнее
совпадение на строку. Ошибки HTTP/curl и повреждённый ответ также превращались в
успешный ноль. Публичный status мог возвращать state=ok и free_pct=100 при HTTP 403.

Reader теперь проверяет завершение запроса, HTTP 200, JSON, поля и типы каждого
элемента, совпадение parent, отсутствие trashed, каталога и повторных ID. Суммируются
все подтверждённые size обеих папок. Пустой проверенный список остаётся нулём;
недоступный список возвращает ошибку. Status показывает state=error и free_pct=0;
used_mb=0 в ошибочном ответе — совместимое числовое поле, не измеренный расход.

Отказ чтения заданной quota_mb больше не заменяет пользовательские 50 MB на 500.
Default применяется только после успешного подтверждения отсутствия опции.
Контекст status изолирован от вызывающей команды: его прежняя запись authorized
не переносит устаревшую проверку в следующую операцию archive-push.

Почему выбран этот способ: расширение regex не проверяет массив и полноту, а ноль
при отказе скрывает необходимость восстановления. Используется уже имеющийся jshn.
Для ответов установлены консервативные границы: 200 элементов, 256 КиБ после
загрузки, числовая сумма до 999999999999999 байт. При nextPageToken,
incompleteSearch или превышении границы операция отказывает. Полная пагинация
не добавлена; неполный список не становится основанием для удаления.

## B94: потеря последней строки, неверный порядок и скрытый отказ очистки

Нулевой счётчик B93 в оригинале часто не даёт дойти до удаления. Поэтому отдельно
сохранён промежуточный `counter-only`-исходник: проверенный счётчик плюс старые
prune/archive-ветви. Это не неизменённая r307 и не отдельный выпуск.

На нём дополнительно обнаружено, что `while read` теряет последнюю строку без LF.
Компактный JSON после подстановки команды не даёт нужного терминатора. Для проверки
более поздней ошибки тест использует допустимый внутренний перенос перед закрытием
массива: regex выдаёт завершённую строку. Трасса подтверждает **DELETE newLog**,
хотя порядок списка начинается с oldLog. Извлечён последний ID на строке, а не первый
по modifiedTime. Удаление произошло только в синтетической HTTP-модели.

Второй поздний контроль намеренно доводит DELETE до HTTP 500. В промежуточном коде
этот одиночный сценарий **уже возвращает ошибку** через последнюю проверку цикла.
Он не выдан за исправленную потерю данных. Отдельно доказан внешний дефект: настоящая
archive-push r307 подавляет отказ квотной проверки после загрузки и возвращает
ok=true. Исправление сохраняет различие между этими уровнями.

Новый prune полностью проверяет обе папки до первого DELETE. Файлы из logs
обрабатываются в запрошенном порядке modifiedTime,name. Только допустимые имена
`.log`, `.tar`, `.tar.gz` становятся кандидатами; другие документы учитываются в
сумме, но не удаляются. Backups не удаляются. Совпадение ID двух папок и повторные
ID отклоняются. ID для DELETE проверяется отдельно.

После каждого подтверждённого удаления перечитываются обе папки. Отказ, неполный
ответ или отсутствие уменьшения наблюдаемого расхода прекращают обработку.
Достижение квоты прекращает цикл немедленно. Если достигнуть её без backups или
других документов невозможно, возвращается ошибка. Archive-push учитывает ошибку
prune в errors и sync-status вместо ложного успеха.

Почему: защита только отдельных DELETE не исправляет неправильный план. Вычитание
размера из старого total не замечает сбой перечитывания. Удалять чужие типы объектов
ради квоты нельзя. Метод files.delete не использует корзину; переход к trash был бы
изменением продуктового поведения и здесь не включён незаметно.

## Проверки и воспроизводимость

Проверенный контур: **266 уникальных тестов в 5 файлах**, все прошли, без
пропусков и отмен. Основной последовательный runner завершил **264 теста**:
Google Drive 184 (141 прежний + 43 новых), logStorage 4, logWriterRuntime 34,
packageHardeningRuntime 17, testIpkPermissions 25. Два дополнительных поздних
сценария добавлены после загрузки первого test-файла runner и отдельно прошли
2/2; они же входят в последующий повтор всех 45 новых тестов из bundle. Поэтому
264 не переписано как 266 тестов одного фактически выполненного запуска.

Новые проверки: **45** — 43 основных и два поздних контроля. Первые 43 на оригинале
r307 дают 41 fail / 2 pass; последние два на оригинале не достигают DELETE и
завершаются отказом assertions. Итого на оригинале **43 fail / 2 pass**, но это
не число самостоятельных ошибок. Первичный запуск двух поздних тестов с ошибочным
путём к baseline дал ENOTDIR: он сохранён как ошибка запуска, исключён из сравнений
и повторён с правильным каталогом.

На промежуточном counter-only первые 15 cleanup-проверок не проходят, а поздние
два дают **1 fail / 1 pass**. Трассы отделяют недостигнутую DELETE от реально
выполненной; проходящий контроль HTTP 500 явно описан выше. На исправлении
43 основных и оба поздних проходят. Повтор из финального bundle фиксируется во
внешнем протоколе после commit; дубли не прибавляются к уникальным сценариям.

Тестовые Standard и AI Support IPK собраны. Для обоих пройдены по 25 архивных
проверок. Payload загрузчика совпадает с преобразованием исходника для редакции,
0755 подтверждён; hardening распакованных пакетов прошёл. Это не SDK-сборка и не
установка на физический роутер.

Проверены один shell-файл через sh и BusyBox ash и один JavaScript-файл через
node --check. Проверены 9 изменённых Markdown-файлов; ссылки, теги и команды исправны. ESLint попытался
запуститься offline, но завершился ENOTCACHED: закреплённых зависимостей нет в
локальном кэше. Проверка синтаксиса не заменяет lint.

## Что не объявлено исправленным

Удаления не являются общей транзакцией: успешный DELETE не отменяется последующим
отказом. Ошибка cleanup также не возвращает локальный архив, удалённый после уже
подтверждённой загрузки. Данные должны оставаться в проверенной облачной копии;
этот проход не добавляет проверку checksum содержимого или облачное восстановление.

Перемещение файлов после чтения, параллельные отправители, ABA и неизменяемый снимок
UCI остаются R03/R14. Повторное чтение не доказывает, что расход уменьшился именно
за счёт нашего удаления при конкуренции. Расширение файла не доказывает его автора:
выделенную папку logs нельзя использовать для чужих журналов, которые требуется
сохранить. Квота отражает текущие файлы двух папок, не всю квоту аккаунта/историю
версий/вложенные каталоги. Отсутствующий size не считается нулём.

Байтовая проверка после загрузки не ограничивает потоковую запись на сетевом слое.
Полная пагинация, жёсткие RAM-квоты, безопасная уборка аварийных временных каталогов,
самостоятельные list/download/restore и запись authorized через общий UCI commit
остаются открытыми. Живой Google, native jshn/UCI, физический роутер, нагрузка,
новые Android/SDK-сборки в этом проходе не проверялись.

## Первичные источники

Документация проверена 10.09.2026. Это основание для схемы HTTP, не доказательство
работы против настоящего аккаунта:

- [Drive File resource](https://developers.google.com/workspace/drive/api/reference/rest/v3/files):
  size — string (int64), отдельные типы объектов могут не иметь size.
- [files.list](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/list):
  files, nextPageToken, incompleteSearch, порядок modifiedTime/name.
- [files.delete](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/delete):
  постоянное удаление, включая потомков папки; именно поэтому папки исключены.
