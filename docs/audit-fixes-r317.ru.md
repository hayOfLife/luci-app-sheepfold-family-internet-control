# Sheepfold r317: достоверная подготовка локальных копий Яндекс Диска

Дата: **12 сентября 2026 года**. База: **`17eab4b` (r316)**, потомок принятого
`bdb3a92`. Результат — локальная ветка `main`, пакет `0.1.0-317`; в GitHub ничего
не отправляется. Это интеграционный снимок, не подтверждённый стабильный релиз.

## Итог

Две группы ошибок **B114–B115** исправлены в `sheepfold-yandex-disk`. Накопительный
[реестр](bug-register.ru.md) содержит **115 карточек**: сценарий, причина, решение,
почему выбран этот способ, альтернативы, тесты и ограничения. Google Drive, Android,
политика доступа, workflow и runners не менялись. Сохранены «Без ограничений» выше
чёрного списка устройств для обычного интернета и независимые запреты управления
роутером/карантина. Это утверждённое решение владельца D01.

Проверен именно этап **подготовки локальных данных перед архивной отправкой**.
Известные ранние ошибки `upload_and_verify`/`verify_upload`, неполноценный WebDAV XML,
самостоятельные list/download/push-events и restore-config не открывались и не
объявлены исправленными. Успешная подготовка архива не доказывает его доставку.

## B114: tar отказывает, а архивная команда сообщает об успехе

На неизменённой r316 с синтетическим config, без очереди архивов и живого журнала,
подставленный tar пишет `partial` и возвращает 1. Trace подтверждает его вызов.
Получен exit 0 и `{"ok":true,"pushed":0,"errors":0}`. Подстановка затрагивает
только команду отказа и HTTP/UCI, production entry/upload не редактируется.
После исправления тот же запрос возвращает exit 1, `backup_prepare_failed`,
`pushed:0`, `errors:1`; MKCOL/PUT/DELETE не выполняются, прежние локальные файлы
сохранены. Транспортная проверка доступа перед этим возможна, она не создаёт папки.

Причина — подавленный `create_config_backup ... || true` и пропуск ветви без учёта
ошибки. Сам backup создавался слишком поздно — после подготовки папок и очереди
отправок. Теперь config и имеющийся events.log готовятся **до первой облачной
мутации и удаления локальных архивов**. Копия config проверяется cmp; tar должен
содержать ровно один `sheepfold`, успешно прочитанный обратно в stdout и совпадающий
со снимком. Права и каждый exit проверяются. Дополнительная сверка обнаруживает
изменение источника в охваченном окне. Отказ snapshots имеет отдельную причину.

Проверены tar.gz и обычный tar при исключённом gzip из PATH, действительные байты
config с UTF-8, повреждение архива при exit 0, лишний элемент, неправильные байты,
ошибки списка/извлечения, cp/cmp/chmod/date, symlink и отсутствие config.

Выбор предварительной подготовки предотвращает уже совершённые побочные действия
до известного локального отказа. Проверка только длины или одного exit tar слабее
сравнения содержимого. Извлечение в stdout не применяет настройки к роутеру.
Компромисс: ошибка config останавливает весь этот архивный проход, включая журналы;
универсального режима «пропустить backup и считать всё успешным» не добавлено.

## B115: имя до секунды не определяет владельца копии

В старом общем staging заранее сохранены config/events с именем той же секунды.
**Полная исходная r316 со штатным uploader**, который затем отказывает, перезаписывает
и удаляет оба файла. Получен `ok:false`, но старые данные уже исчезли. Этот сценарий
доказывает потерю локальных копий без утверждения о полноценной загрузке в облако.
Положительный путь проверяется отдельно, с явно заменённым uploader, и не смешан
с неизменённой командой. Проверен также symlink вместо старого staging.

Теперь каждый проход владеет уникальным `/tmp/sheepfold/.yandex-archive.XXXXXX`.
Ограничительный umask действует до создания, права доступа каталога 0700, файлов
0600. Право удаления появляется после успешного mktemp. При неуспехе mktemp его
частичный stdout не интерпретируется как каталог, разрешённый к очистке. При отказе
chmod после успешного mktemp удаляется только созданный каталог. EXIT/сигнальные
обработчики и переменные изолированы subshell. Старый общий staging не затрагивается.

Добавление PID или более точного времени лишь уменьшило бы вероятность совпадения;
безусловная очистка старого staging уничтожила бы возможную аварийную копию.
Сохранены внешние имена объектов, а владение разделено на уровне локальных каталогов.
Облачные совпадения имён при параллельной отправке этим не устранены.

## Уровень доказательств

В `tests/yandexBackupRuntime.test.mjs` исполняется настоящий shell-файл проекта,
с заменой системных путей на уникальный `.build`-каталог. UCI и curl — модели с
синтетическими реквизитами; доступа к аккаунту и реальной сети нет. cp/cmp/tar —
настоящие утилиты. Fault wrappers либо возвращают намеренный отказ с trace, либо
делегируют настоящей программе. Для каждого заявленного отказа проверено достижение.

Из 33 новых сценариев 24 проверяют preflight/отказ со штатным uploader, 9 используют
**явную модель границы uploader** для проверки подготовленных байтов и очистки.
Это не HTTP-модель успешного WebDAV: поздняя проверка удалённого размера остаётся
неисправной. Отдельный native-скрипт тест требует её существующий отказ.
Один сценарий выполняет настоящий BusyBox tar; это не полный прогон под BusyBox ash.

На исходной r316 этот же набор даёт **5 pass / 28 fail**. Многие failures означают
отсутствие нового защитного этапа (например, не достигнут новый cmp), не 28 отдельных
ошибок старого кода. Прямые доказательства — ложный успех после tar и исчезновение
старых копий при полном native-entry; они вынесены в сравнительные JSON трассы.

## Повторение и окружение

Рабочий каталог — корень клона. Нужны Node.js 22+, Python 3, sh/cp/cmp/tar/chmod,
mktemp и обычные POSIX-команды. Для native BusyBox случая нужен `/usr/bin/busybox`.
На Windows применяется Git Bash и `PYTHON_EXECUTABLE`; особенности прав и symlink
имеют явные ограничения. Тесты не трогают настоящие `/etc/config` или `/tmp/sheepfold`.

```sh
node scripts/run-test-category.mjs --file yandexBackupRuntime.test.mjs --file yandexDiskRuntime.test.mjs
node scripts/run-test-category.mjs --file logStorage.test.mjs --file logWriterRuntime.test.mjs --file portableShellAndStatus.test.mjs --file packageHardeningRuntime.test.mjs
node scripts/run-test-category.mjs --file testCategories.test.mjs --file changeImpact.test.mjs --file qualityAssistants.test.mjs
python3 scripts/build-test-ipk.py --variant all
SHEEPFOLD_TEST_IPK="$PWD/.build/ipk-output/luci-app-sheepfold-family-internet-control_0.1.0-317_all.ipk" node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
SHEEPFOLD_TEST_IPK="$PWD/.build/ipk-output/luci-app-sheepfold-ai-support_0.1.0-317_all.ipk" node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
sh -n package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-yandex-disk
busybox ash -n package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-yandex-disk
node scripts/checkDocumentation.mjs --git 17eab4b
node scripts/inspectChangeImpact.mjs --git 17eab4b
git diff --check
```

Ожидается exit 0 и перечисленные pass без fail. Fixtures удаляются после теста;
SIGKILL внешнего процесса может оставить каталог в `.build`, не состояние роутера.
Обычные тестовые пакеты остаются `.build/ipk-output`. Прямой запуск production-скрипта
на рабочем компьютере вместо fixture недопустим: он рассчитан на OpenWrt.

Для сравнения с исходным кодом сохранить только исходный `sheepfold-yandex-disk`
в отдельный каталог и передать `SHEEPFOLD_YANDEX_TEST_SOURCE`. Ожидаемые провалы
такого запуска — результат сравнения, не успешный gate. Для экспорта синтетических
JSON-трасс задать `SHEEPFOLD_YANDEX_BACKUP_EVIDENCE_DIR`; реальные секреты не включать.

ESLint: `npm exec --offline --no -- eslint --version` завершился ENOTCACHED.
Синтаксис пяти затронутых JavaScript-модулей проверяется через `node --check`, но
это не ESLint. Android/официальные SDK/реальное облако в этом проходе не проверялись.

## Проверка поставки и внешняя семантика

Standard и AI Support r317 собраны тестовым builder. По 25 архивных проверок прошли,
исправленный uploader в обоих IPK совпадает с исходником и имеет 0755. Hardening
выполнен на распакованных rootfs; это не установка opkg на живой OpenWrt.
Версия пакета увеличена через PKG_RELEASE; asset version берётся из него без правки UI.

Финальный bundle проверяется восстановлением и git fsck; полный manifest с коммитом,
деревом, версиями, числом экспортированных файлов и SHA-256 входит в поставку.
Журналы, сравниваемый исходник, новый тест и патчи сохраняются вместе с тестовыми IPK.

Официальная справка BusyBox (`https://busybox.net/downloads/BusyBox.html`) проверена
12.09.2026 для mktemp/tar и их конфигурируемости. GNU-страница Writing-to-Standard-Output
при повторном открытии дала timeout; успешная новая сверка этой страницы не заявляется.
Семантика чтения tar в stdout дополнительно проверена реальными GNU/BusyBox утилитами
в Linux. Это не подтверждает applet-конфигурацию каждой сборки OpenWrt.

## Оставшиеся границы

Новый снимок увеличивает потребление RAM; лимиты объёма, длительности копирования и
обслуживание аварийных каталогов не добавлены. Нет общей транзакции UCI, защиты от
привилегированного подменяющего writer или гарантии после отключения питания.
Копирование events пока не связано с общей блокировкой writer/rotator и настройкой
log_cache_path в Яндекс-пути. Эти отдельные дефекты остаются R15. PUT, namespace-aware
XML, удалённый размер, quota/prune, download/list и безопасное restore требуют следующих
проходов. Нельзя исправлять их ранние объявления и считать весь путь безопасным.
