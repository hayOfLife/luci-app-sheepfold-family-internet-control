## B139: синхронные ошибки до Promise и после расшифровки

При вызове `deps.apply(...).then(...)` исключение во время самого `deps.apply`
происходило до подключения обработчика отказа. Настоящий контроллер способен
синхронно отказать при построении текущего снимка. Кнопка уже была выключена,
а текст `Applying backup...` оставался после прекращения операции.

Аналогичный пробел был в decrypt. Дополнительно после успешного WebCrypto
отказ текущего снимка подавлялся внутри предварительного просмотра. Диалог
расшифровки оставался в состоянии `Decrypting backup...`, хотя дешифрование
закончилось. В этих воспроизведениях сохранение UCI не выполнялось.

Теперь операции входят в Promise через `Promise.resolve().then(...)`, а
завершающий catch охватывает синхронные и асинхронные ошибки. Ошибку preview
обрабатывает владелец активного диалога. После успешной расшифровки ошибка
снимка не выдаётся за неправильный пароль. Занятая кнопка игнорирует повторное
событие; после раннего отказа она доступна для ручного повтора.

Почему: отдельный try/catch не охватывает поздний Promise, а второй аргумент
`.then()` не ловит ошибку успешного продолжения. Исправлена панель, владеющая
состоянием кнопок, без ослабления backend или автоматического повторения команд.

## B140: неизвестный результат не равен восстановлению

Реальный `core/persistence/uci.js` выполняется с моделью, разделяющей текущие,
подготовленные и сохранённые значения. Трасса: `save → apply → confirm → revert`.
Модель apply меняет `before` на `after`; confirm и последующий revert отказывают.

| Наблюдение | Предыдущий кандидат | Текущий кандидат |
| --- | --- | --- |
| Сохранённое синтетическое значение | `after` | `after` |
| Сообщение | `Could not import settings. The previous settings were kept.` | Не удалось подтвердить результат; проверить настройки перед повтором |
| Автоматический повтор | Нет | Нет |
| Сброс черновика и автоматический reload после отказа | Нет | Нет |

Новый русский текст: «Не удалось подтвердить результат импорта. Обновите
страницу и проверьте настройки роутера перед повторной попыткой».
Предсказуемые ошибки формата/пароля/секретов сохраняют специальные сообщения.

Почему: признак попытки cleanup не доказывает успешного восстановления.
Повторное применение или общий revert из интерфейса могли бы затронуть чужой
черновик. Эта правка честно описывает неопределённость; исходный отказ и общая
согласованность UCI остаются отдельными задачами. Это не аппаратное испытание.

## B141: подтверждённое сохранение и последующий UI-сбой

При правильном сохранении исключение в resetDraft, уведомлении, закрытии
окна или подготовке таймера обновления происходило в успешном обработчике
`.then(onSuccess, onFailure)` и не попадало в соседний onFailure. Возвращённый
Promise терялся в event handler. Настройки уже изменены, но результат терялся.

Теперь успех принимается только при `result.persisted === true`. После него
локальный флаг отделяет UI-ошибку от неизвестного результата backend. Сообщение:
«Настройки импортированы, но обновить страницу не удалось. Обновите её перед
дальнейшими изменениями». Старая кнопка применения остаётся выключенной —
безусловный finally не должен разрешать повтор уже совершённой мутации.

Диалог закрывается последним: отказ уведомителя или подготовки reload не
оставляет сообщение только в отсоединённом DOM-элементе. Сохранено предупреждение
об отказе обновления служб `servicesRefreshed:false`. Искусственные ответы без
подтверждённого `persisted:true` не запускают успех, resetDraft или reload;
это защитные контроли, не утверждение о штатной выдаче таких ответов адаптером.

Ограничения: отказ resetDraft может оставить локальную модель устаревшей.
Дальнейшая асинхронная ошибка внутри browser reload не проверялась. Если сами
DOM и механизмы уведомления одновременно недоступны, видимость сообщения
не гарантируется. Отмена/смена диалога и параллельные вкладки требуют отдельного
прохода. Подтверждение сохранения не доказывает работоспособность радио и служб.

### Первоначальные ошибки проверки и новые промежуточные отказы

Журналы сохранены, не заменены итоговыми. Ранний стенд не дожидался реального
WebCrypto при старом handler, не возвращавшем Promise; ожидание исправлено в
стенде. Ещё одна проверка ошибочно считала любой созданный `E('p')` видимым
сообщением; теперь анализируется содержимое показанного диалога.

Новый контроль открытого preview обнаружил ошибку промежуточной правки:
вызов confirmation ещё оставался вне try. Он перенесён внутрь, тест сохранён.
Отдельный `node --check` LuCI-файла ошибочно применял семантику CommonJS и
сообщал `Illegal return statement`; корректная проверка использует function-
обёртку, как загрузчик LuCI. Прямой node --check применяется к четырём .mjs.
ESLint через `npm exec --offline` не выполнен из-за `ENOTCACHED`, это не успех.

## Поставка без коммита

Совокупный патч `sheepfold-r323-review-import.patch` включает все защитные правки
кандидата и применяется **к чистому r323**, вместо прежних review-патчей.
`sheepfold-r323-review-import-delta.patch` содержит только эту итерацию и применяется
**к состоянию после `sheepfold-r323-review-followup.patch`**. Это альтернативные
способы получения одного дерева, не два последовательных шага.

Совокупный вариант в новой отдельной рабочей копии:

```sh
git clone --branch main sheepfold-r323-main.bundle sheepfold-review-import
cd sheepfold-review-import
git rev-parse HEAD
# Ожидается 1e9c43bfea54aba15d7020fbdbe84ad5dc23b7c0 и чистая рабочая копия.
git apply --check ../sheepfold-r323-review-import.patch
git apply ../sheepfold-r323-review-import.patch
```

Дополнительный вариант допустим только для точного предыдущего кандидата
без других локальных изменений. Сначала сохранить собственную незакоммиченную
работу; эти команды её автоматически не резервируют:

```sh
git apply --check ../sheepfold-r323-review-import-delta.patch
git apply ../sheepfold-r323-review-import-delta.patch
```

Ни один патч не предназначен для непосредственного применения к принятому
`bdb3a92`. Новый bundle не создаётся: без нового коммита он не включал бы правки.
Полный ZIP не содержит `.git`, `.build`, node_modules или тестовых временных данных.
Реестр содержит 141 карточку разных групп дефектов/мер защиты, не 141 независимо
подтверждённую уязвимость.
