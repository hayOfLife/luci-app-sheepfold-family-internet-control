### Подтверждённая запись не означает успешного NTP

После проверенных commit/readback существующая стадия транзакции закрывается,
затем выполняется restart доступного `sysntpd`. Его ненулевой результат теперь
возвращается так:

```text
status=error
error=ntp_restart_failed
persisted=1
runtime_applied=0
```

Код завершения — **5**. Это новый точный контракт охваченной ветви, а не общий
признак для всех ошибок. Настройки уже сохранены; они не откатываются из-за
неуспешного restart. Перезапуск и повторное сохранение не повторяются автоматически.

Общий action-wrapper отклоняет ненулевой exit раньше `.then` вызывающей панели.
Поэтому адаптер перехватывает отклонение, а `time.normalizeSaveError` принимает
**все четыре поля вместе с числовым code=5**. Только этот результат становится
`persisted=true`, `runtimeApplied=false`. Вывод с теми же полями при exit 4 или
124 не подтверждает запись и не очищает черновик. Обычный успешный протокол не
изменён; отсутствие необязательного init сохраняет прежнюю ветвь без restart.
Эта совместимость не означает подтверждённую синхронизацию времени.

Интерфейс показывает:

> Настройки времени сохранены, но службу синхронизации не удалось перезапустить. Проверьте время на роутере перед использованием расписаний.

из корня репозитория:


### Отправленный снимок, а не текущие поля

Time-saver сохраняет отправленные опции только после подтверждённого успеха либо
именно описанного post-commit отказа. `accept()` принимает их, не перечитывая DOM
как якобы сохранённый снимок. Новое значение того же поля, другой часовой пояс или
флаг NTP остаются несохранёнными. Явное следующее сохранение передаёт новый снимок.
Ошибка до подтверждения не переиспользует снимок предыдущей операции.

Выбор профиля страны сам по себе не считается записью новых настроек часов;
существующие рекомендации применяются отдельной кнопкой. Контроль этого поведения
сохранён. Общая блокировка всех полей не добавлена.

### Диагностика отдельно от результата

Основной журнал подавляет свой stdout/stderr. При его отказе используется
системный `logger`, также без вывода в машинный ответ. Если отказали оба пути,
в stderr выдаётся короткое предупреждение без секретов. Уже известный результат
сохранения или отказа restart остаётся неизменным. Существующий префикс actor
сохраняется. Новый тайм-аут для журналирования не вводился: зависание внешнего
журнала и гарантированная доставка события остаются вне этого изменения.

### Проверяется настоящая цепочка, не только подставленный успешный callback

Новый тест исполняет реальные `time`, `draft/save-flow`, адаптер из настоящего
`application.js`, `core/backend/actions` и `router`. Отдельный связанный сценарий
передаёт реальные аргументы UI из action-wrapper в настоящий `sheepfold-luci-action`
и `sheepfold-time-control`. Wrapper сохраняет реальный exit 5 в action metadata.
Нативные UCI и службы при этом не вызываются: UCI представлен узкой shell/awk-
моделью сохранённого состояния и отдельной pending-очереди; init/log — записывающие
двойники. Эта модель не доказывает все свойства libuci и восстановление снимков.

В первой промежуточной UI-проверке raw runner был подставлен напрямую: все 22
тогдашних сценария прошли, но это пропустило преждевременный reject общего actions.
После подключения настоящего wrapper две проверки стали неуспешными. Классификация
перенесена в общий catch вызывающего адаптера; повтор успешен. Неправильный
промежуточный исходник и log сохранены в checks, не включены в поставку.

Другой соседний тест обнаружил рост application до 658 строк при лимите менее
650. Вместо увеличения лимита или удаления пояснений разбор ошибки перенесён
в профильный модуль времени; application теперь только вызывает его. Первоначальный
отказ сохранён. Предварительные запуски медленной Python-модели UCI, прерванные
лимитом среды, не считаются успешными; окончательный узкий shell/awk-стенд проходит
через неизменённый штатный runner.

## Как повторить

Из корня отдельной рабочей копии кандидата, Node.js, POSIX sh/Git Bash и awk должны
быть доступны. Для Linux требуется настоящий flock. Windows использует уже принятую
ограниченную последовательную fixture-модель при отсутствии flock; сам Windows
в этом проходе не запускался. Тестовый каталог создаётся в `.build/time-lifecycle`.
Ни один production-helper из примеров нельзя запускать напрямую на рабочем роутере.

```sh
node scripts/run-test-category.mjs --file timeSettingsLifecycle.test.mjs --file timeAndDetectionSetup.test.mjs --file settingsSaveLifecycle.test.mjs --file luciCommandActions.test.mjs --file portableShellAndStatus.test.mjs --file overviewSettingsExtraction.test.mjs --file overviewFinalRuntime.test.mjs --file frontendModules.test.mjs --file overviewLocalization.test.mjs --file cloudArchiveSafety.test.mjs --file changeImpact.test.mjs --file testCategories.test.mjs --file runtimeProcess.test.mjs
```

Ожидается exit 0 и все 13 файлов успешны. При отказе runner останавливается;
перечисленные, но не запущенные файлы не засчитываются. Ошибка инфраструктуры
(например, отсутствует shell/flock) должна быть исправлена в среде, а не ослаблением
рабочей блокировки. `runtimeProcess` диагностирует ошибку запуска/тайм-аут до JSON.

Для отдельного повтора новых сценариев:

```sh
node scripts/run-test-category.mjs --file timeSettingsLifecycle.test.mjs --file cloudArchiveSafety.test.mjs
```

Ожидается **34 успеха**, это повтор 26+8, не новые сценарии. Для сравнения из Linux
и корня кандидата с распакованными evidence рядом:

```sh
SHEEPFOLD_TIME_SOURCE=../evidence/before node --test tests/timeSettingsLifecycle.test.mjs
```

В `evidence/before` нужны прежние `time.js`, `application.js`,
`sheepfold-time-control`, `ru.json`. Ожидается exit 1, 10 успехов и 16 отказов.
Путь нужно заменить фактическим путём распаковки; Windows-синтаксис переменной
отличается. Это отрицательное сравнение, не тест готовности старого кода.

## Границы и отдельные нерешённые проблемы

- Успешная запись/exit службы не означает, что часы синхронизированы, timezone
  применён всеми процессами или расписания уже совпадают с реальным трафиком.
- Существующие подготовка транзакции и откат `sheepfold-time-control` в этом
  проходе не переработаны. По коду там остаются подавленные ошибки восстановления
  и удаление снимков; гарантия надёжного отката не заявляется. Для этих ветвей
  нужен отдельный fault-injection аудит и затем тестовый OpenWrt.
- Принятие снимка работает в памяти одной панели. Полная перезагрузка страницы,
  другие вкладки/CLI и несогласованное чтение libuci остаются отдельной задачей.
- Снимок специального saver формируется при его фактическом запуске, не на общем
  нажатии Save для всех блоков сразу. Новая глобальная транзакция не добавлена.
- Модель UI не является настоящим браузером; модель pending/commit — не нативный
  UCI. Настоящие Windows, роутер, NTP-серверы, Android и облака не проверялись.
- Нет IPK/APK/SDK-сборки и установки. Проверка синтаксиса не заменяет ESLint.
  Локальная offline-зависимость ESLint отсутствует, линтер не выполнен.

## Применение и поставка

**Выберите один вариант**, не применяйте оба патча последовательно:

1. В чистой копии кандидата r323 (`1e9c43b`) —
   `sheepfold-r323-review-time.patch`. Он включает все прежние review-правки.
2. Где уже применён `sheepfold-r323-review-messenger.patch` — только
   `sheepfold-r323-review-time-delta.patch`.

```sh
git apply --check ../sheepfold-r323-review-time.patch
git apply ../sheepfold-r323-review-time.patch
```

Для второго пути используются те же команды с именем delta. Перед применением
сохранить собственную незакоммиченную работу. Нельзя применять эти патчи напрямую
к принятому `bdb3a92`: их база другая. Source ZIP содержит полный кандидат без
`.git` и тестовых временных файлов. Bundle не создаётся, поскольку незакоммиченные
изменения в него не войдут. Ни одна команда не публикует изменения.

Проверка поставки выполняется двумя независимыми клонами исходного bundle:
совокупный патч в первом; предыдущий messenger-патч и текущий delta во втором.
Их полные деревья должны совпасть с исходниками ZIP по байтам и режимам, с учётом
`.gitattributes`. Фактический manifest и протокол входят в checks. SHA256SUMS
содержит суммы шести файлов: source ZIP, два патча, отчёт, реестр и checks ZIP.


### Окончательная локальная сверка

Оба способа применения проверены на независимых чистых клонах r323. Получены
одинаковые деревья из **1080 файлов**: байты и режимы совпадают с независимым
Git-экспортом и source ZIP. HEAD остаётся `1e9c43b`; commit не создавался.
В восстановленном кандидате повторены **34 сценария** (новые 26 и восемь защитных

Синтаксис проверен у двух LuCI-модулей в Function-обёртке, четырёх Node-модулей
