# Аудит и исправления r319: снимок выбранного журнала Яндекс Диска

Дата: **12.09.2026**. База: **`ea0d1db5287c78ab38e8e6d1ea19557388cd2218`**, r318.
Новая версия тестового пакета: **0.1.0-319**. Работа локальная, без push в GitHub.
Принятые изменения `bdb3a92`, история исходных четырёх веток и решение D01 сохраняются.

## Результат и граница

Исправлены **три группы B119–B121**, [реестр](bug-register.ru.md) содержит 121 карточку.
Изменён только один исполняемый backend: `sheepfold-yandex-disk`. Новая функция
`yandex_events_snapshot` использует уже поставляемые `sheepfold-log-common` и
`sheepfold-lock-common`; сами библиотеки, общий uploader/verify, Google Drive,
Android, firewall, миграции, CI и исполняющие test-runner скрипты не изменены.

Теперь обе команды экспортируют проверенный снимок выбранного административного
журнала. Подтверждённое отсутствие выбранного файла не заменяется старым default,
а технический отказ не выдаётся за отсутствие событий. Копирование согласовано
с writer/API/rotator, но сетевой запрос не удерживает их lock. Новые события остаются
в живом журнале для следующего прохода. Нового сбора пользовательской активности нет.

Это **локальный интеграционный снимок**, не подтверждённый стабильный релиз.
Доставка в настоящий Яндекс Диск, нативный UCI и испытание на роутере не выполнены.

## Что воспроизведено до исправления

### B119: корректная команда не запускается

Полный `push-events` на неизменённой r318 возвращает exit 127:
`remote_path: not found`. Строка `remote_path verify_json` является вызовом команды,
а не объявлением переменных. Ошибка возникает даже до проверки выбранного backend.
Архивный caller этой ошибки не имеет. Теперь прямая команда изолирована subshell;
значения присваиваются явно, последующие шаги проверены, а не просто открыты.

### B120: правильный размер, неправильный источник

В выбранном журнале — `selected journal\n`, в старом default — `obsolete journal\n`.
Оба файла имеют 17 байт. Неизменённая r318 отправляет старый файл и сообщает
`ok:true,pushed:3,errors:0`. Источники и записанные PUT-байты проверены отдельно.
После исправления отправляются выбранные байты. Когда выбранный файл отсутствует,
old default игнорируется; когда default отсутствует, существующий custom всё равно
экспортируется. Сетевые имена остаются совместимыми: `events.log` для прямой команды
и `events-<stamp>.log` для архивного прохода.

Причина — обе команды жёстко читали `EVENTS_LOG`, хотя другие потребители журнала
уже учитывали `log_cache_path`. Путь теперь читается существующей общей библиотекой,
без новой независимой реализации проверки. Отказы UCI/path/cp/cmp/chmod и отсутствие
библиотеки дают `events_snapshot_failed` до MKCOL/PUT/DELETE; archive probe мог уже
быть выполнен. Существующая очередь архивов сохраняется при таком отказе.

### B121: несогласованное копирование и ложная ошибка после новой строки

Неизменённый `archive-push` продолжает работу, пока независимый процесс держит
настоящий writer-lock. В новом коде trace фиксирует отказ первой попытки flock,
до освобождения lock PUT отсутствует. После ожидания настройка перечитывается;
если writer перешёл к другому файлу, снимок использует заново проверенный путь.

Для поздней ошибки `push-events` создан промежуточный исходник r318, в котором
исправлено **только** объявление из B119. Он не назван неизменённой r318. Во время
PUT/HEAD модель дописывает `new event\n` в живой default-журнал. Копия уже передана,
размер подтверждён, но прежний caller возвращает `source_changed`. Новый caller
передаёт снимок: успешный результат сохраняется, а новая строка остаётся локально.

Сравнение в общем uploader не удалено: для архивов, удаляемых после подтверждения,
его защита необходима. Lock удерживается только во время локального снимка, не во
время HTTP. Это важнее, чем просто запретить параллельную запись на всю загрузку.

## Проверки и их уровень

| Область | Число уникальных сценариев |
| --- | ---: |
| `yandexBackupRuntime` | 33 |
| `yandexDiskRuntime` | 125 |
| `yandexUploadRuntime` | 58 |
| Новый `yandexEventsRuntime` | 46 |
| `changeImpact`, `testCategories` | 22 + 6 |
| `logStorage`, `logWriterRuntime`, `portableShellAndStatus` | 4 + 34 + 5 |
| `packageHardeningRuntime` | 17 |
| `testIpkPermissions` | 25 |
| **Всего** | **375 в 11 файлах** |

Проверки завершились успешно, без пропусков и отмен на Linux. 25 IPK-сценариев
выполняются на обеих редакциях, но в таблице считаются один раз. Первый профильный
запуск содержал 45 новых сценариев; затем добавлен отдельный отказ flock, и весь
новый файл из 46 сценариев проверен повторно. Это не 375 новых ошибок: новых тестов
46, исправленных групп три, остальные проверки — реальные прямые зависимости.
Полный набор проекта не запускался.

На исходной r318 выполнено восемь избранных проверок: шесть не проходят, два
контрольных проходят. В этой выборке ранняя ошибка скрывает поздние пути push.
На промежуточном варианте четыре избранных проверки не проходят: неверный источник
в обоих caller и ложный `source_changed` при росте default-журнала в PUT/HEAD.
Все преобразования исходника и SHA-256 отражены в трассах. Неудачные baseline —
ожидаемые доказательства дефекта, не незавершённый финальный прогон.

Исполняются настоящий shell и обе общие библиотеки. Копирование, архивирование,
права, содержимое файлов и Linux flock — реальные. HTTP и UCI — модели, реквизиты
синтетические; исходники и системные каталоги перенаправлены в уникальные `.build`.
Fault-тест обязан подтвердить вызов подставленной команды. Проверка ожидания lock
использует управляемый барьер, а не только паузу фиксированной длины. Во время PUT
независимый дескриптор получает тот же lock и дописывает событие — это подтверждает,
что блокировка не оставлена у сети.

Windows не проверялся. Для неконкурентных Windows-fixtures lock обозначен как
модель; настоящие Linux-конкурентные тесты там явно пропускаются. Пропуск не является
успешным испытанием flock. Два старых preflight-теста больше не исправляют production
в памяти: ранняя ошибка теперь устранена в поставляемом коде.

## Влияние и сопутствующие изменения

Изменён PKG_RELEASE 318 → 319; runtime-версия и ресурсы берутся из существующего
Makefile-механизма. Логика установки и миграции не менялась. Новая тестовая зависимость
добавлена в `categories.mjs`, `changeImpactRules.mjs` и проверки карты. Общий путь
журнала теперь имеет ещё одного прямого потребителя; при будущей правке библиотеки
должен запускаться и `yandexEventsRuntime`.

Три прежних Yandex-fixture получили копии настоящих библиотек с переадресованным
RAM-путём. В минимальный PATH теста без gzip добавлены flock/sleep. Это изменение
стенда вслед за реальной зависимостью, не ослабление production. Не изменены Android,
правила доступа, workflow и исполняющие runner-скрипты.

`quality:plan` отмечает общий риск из-за версии пакета/карты и рекомендует широкий
набор. По прямому решению владельца проверены все перечисленные непосредственные
потребители, не несвязанные Android/firewall/AI тесты. Advisory-предупреждение о
размере legacy Yandex-файла сохранено: около 997 учитываемых строк при пороге 900;
старый транспортный тест — около 568 при пороге 500. Декомпозиция всего backend
ради порога расширила бы риск этого исправления. Неизвестных исходников не оставлено.

Синтаксис изменённого shell проверен через sh и BusyBox ash; семь изменённых
JavaScript-файлов — через node --check. Документационный checker проверил 285
Markdown-файлов. Оба распакованных IPK прошли собственный runtime-hardening;
исправленный backend и обе библиотеки побайтно совпадают с исходниками и имеют 0755.
Первый вспомогательный probe архива искал имя без допустимого префикса `./`; после
исправления только probe проверка пройдена, формат пакетов не менялся.

ESLint требует отсутствующую локальную зависимость; отдельный журнал фиксирует
фактический результат offline-попытки. `node --check` не заменяет ESLint. Новая
SDK-сборка, Android build или GitHub Actions не запускались. Тестовый IPK — не
официальная SDK-сборка и не проверенная установка на устройство.

## Повторение проверок

Из корня репозитория на Linux нужны Node.js, Python 3, POSIX sh, стандартные
файловые утилиты, tar и flock. Нельзя запускать production-helper с root-правами
на рабочей машине вместо перенаправленного fixture: он рассчитан на OpenWrt.

```sh
node scripts/run-test-category.mjs --file yandexEventsRuntime.test.mjs --file yandexDiskRuntime.test.mjs --file yandexBackupRuntime.test.mjs --file yandexUploadRuntime.test.mjs
node scripts/run-test-category.mjs --file logStorage.test.mjs --file logWriterRuntime.test.mjs --file portableShellAndStatus.test.mjs --file packageHardeningRuntime.test.mjs --file testCategories.test.mjs --file changeImpact.test.mjs
python scripts/build-test-ipk.py --variant all --out-dir .build/r319-packages
SHEEPFOLD_TEST_IPK="$PWD/.build/r319-packages/luci-app-sheepfold-family-internet-control_0.1.0-319_all.ipk" node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
SHEEPFOLD_TEST_IPK="$PWD/.build/r319-packages/luci-app-sheepfold-ai-support_0.1.0-319_all.ipk" node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
node scripts/checkDocumentation.mjs --all
git diff --check
```

Ожидается exit 0, no failures/skips на Linux, валидный JSON, исходные байты в PUT,
сохранность исходников при отказе и отсутствие собственного staging после окончания.

Для сохранения доказательств установите `SHEEPFOLD_YANDEX_EVENTS_EVIDENCE_DIR` на
отдельный каталог. Fixture удаляет свои рабочие данные после теста; trace и stdout
сохраняются только при этой явной опции. Для сравнения `SHEEPFOLD_YANDEX_TEST_SOURCE`
задаёт каталог со старым helper; `SHEEPFOLD_YANDEX_EVENTS_OPEN_PUSH=1` применяет
**только к старому исходнику** объявление local. Его нельзя использовать для
заявления, что неизменённый старый entry работал. Никаких реальных аккаунтов в
переменные модели не передавать.

## Оставшиеся ограничения и следующий аудит

Полный XML/quota/prune, list/download/restore и статус фоновой синхронизации
остаются самостоятельными непроверенными путями. HEAD-контракт размера из r318
не изменён; его совместимость с настоящим Яндекс Диском ещё не подтверждена.
Нет checksum, общей транзакции настроек или нескольких cloud-процессов. Уже
выполненный PUT не откатывается. Авторизационный probe archive может предшествовать
снимку, но MKCOL/PUT и удаление ожидающих архивов — только после него.

Размер журнала, время локального копирования под lock и расход RAM пока не
ограничены новым кодом. Аварийный SIGKILL может оставить закрытые временные файлы;
автоматическая очистка неизвестных старых каталогов не добавлена. Изменение пути
после финальной сверки и гонки с root-writer не устранены полностью. При отказе
обязательного журнала весь archive-проход останавливается, а не отправляет backup
частично с фиктивным успехом.

Рекомендуемая следующая узкая область — безопасный разбор XML/расчёт квоты перед
облачной очисткой либо достоверный sync-status. Не включать restore только ради
исправления очередного раннего объявления: распаковка и применение требуют
самостоятельных проверок страховочной копии и безопасности.
