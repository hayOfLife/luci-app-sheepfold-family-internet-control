# Sheepfold r318: проверяемая отправка архива Яндекс Диска

Дата: **12 сентября 2026 года**. База: **`6228e37` (r317)**, потомок принятого
`bdb3a92`. Пакет: `0.1.0-318`, ветка `main`. Изменения локальные, в GitHub не
отправлены. Это интеграционный снимок, не подтверждённый стабильный релиз.

## Результат и область

Исправлены B116–B118 в `sheepfold-yandex-disk`: запуск verify/uploader, проверка
результата PUT и отдельного размера по HEAD, закрытый снимок отправляемых байтов
и отказ при замеченном изменении источника либо настроек внутри одного transfer.
[Подробный реестр](bug-register.ru.md) содержит **118 карточек** с причинами,
альтернативами, сценариями, результатами и ограничениями.

Не изменены Google Drive, Android, правила доступа, workflow или runners.
«Без ограничений» выше чёрного списка устройств для обычного интернета; независимые
запреты управления роутером и карантин сохранены (D01). Новых runtime-зависимостей нет.
Полный suite не запускался. Новый тест зарегистрирован в существующих категориях
и в карте непосредственного влияния Yandex-файла.

## Что было подтверждено до исправления

**B116 — обычный вызов не выполняется.** На неизменённой r317
`upload_and_verify` заканчивается exit 127, `code: not found`. Самостоятельная
`verify` аналогично пытается запустить `local_bytes`. Ошибочные строки являются
командами оболочки, не объявлениями. Исправлены именно выполняемые функции и
обработка аргументов, а не `set -e` или проверки caller.

**B117 — независимый reader теряет размер.** Прямой `remote_file_bytes` получает
правильный XML с `<d:getcontentlength>28</d:getcontentlength>` и HTTP 207, но выдаёт
пустую строку при exit 0. Жадность regex и допустимое пустое совпадение скрывают число.
Прямой PUT также не отвергал redirect как неуспех helper и мог использовать частично
прочитанный пароль после неуспешного UCI. Все реквизиты в тесте синтетические.

**B118 — после устранения ранних ошибок теряется новая локальная редакция.** Для
позднего сценария создан отдельный промежуточный исходник: только два объявления
и reader размера исправлены, прежний алгоритм отправки сохранён. Во время PUT/HEAD
источник заменяется другими байтами **той же длины — 28 байт**. Обработчик возвращает
`ok:true`; полный архивный caller удаляет изменённый исходник. После исправления
тот же сценарий даёт `source_changed`, файл остаётся. В промежуточном сценарии
архивная команда возвращает `ok:true,pushed:2`; наличие файла проверяется отдельно.

Промежуточный исходник **не назван неизменённой r317**. Оригинал останавливается
раньше. Доказательства включают оба исходника, их SHA-256, полный stdout/stderr,
точку мутации, переданные HTTP-байты и состояние очереди после команды.

## Как устроено исправление

### Результат загрузки и размер

Функции изолированы subshell, не перезаписывают переменные caller. PUT использует
один закодированный HTTPS URL, проверенный пароль, отключённые curlrc/URL-glob,
не следует redirect и не повторяется автоматически. Код curl и HTTP проверяются
отдельно; допустимы 200/201/204. Частичный stdout не попадает в JSON как HTTP-число.

Размер **одного известного объекта** проверяется отдельным HEAD, без неполного
разбора XML. Принимается только завершённый последний HTTP/1.x-блок со статусом
200, единственным корректным Content-Length, без неоднозначного framing, range
или преобразования содержимого. Локальный wc проверяется до нормализации.
Числа сравниваются как нормализованные десятичные строки, без 32-bit переполнения.
Пустой файл допустим при подтверждённом нуле.

Семантика сверена с первичным источником: [RFC 9110, §8.6](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.6)
и [HEAD, §9.3.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.2).
Content-Length для HEAD необязателен. Если Яндекс его не выдаёт, результатом будет
отказ с сохранением исходника, а не возврат к непроверенному XML. Это осознанная
граница совместимости, требующая проверки на реальном сервисе.

### Снимок и сохранность исходника

Каждый uploader владеет уникальным закрытым transfer-каталогом. До PUT проверяются
cp, cmp, chmod и wc. Отправляется снимок, затем выполняется HEAD, и перед успехом
исходник побайтно сравнивается с ним. Неуспешный mktemp не даёт права очищать путь
из его частичного stdout. При обработанных отказах очищается только свой каталог.

Секция UCI cloud сверяется до/после охваченных запросов и перед успехом; замеченная
смена настроек не даёт смешать новый аккаунт с подтверждением прежней передачи.
Настройки других процессов не откатываются. Эта сверка не является блокировкой всех
writers и не покрывает всю архивную команду.

### План влияния и оставшиеся предупреждения

`quality:plan` и impact-советник выполнены. Их консервативная рекомендация полного
набора вызвана сопутствующим изменением общих документов/карты, не новым сквозным
API или изменением runner. По принятому правилу владельца выбраны все прямые
Yandex/storage/writer/packaging-тесты и изменённая карта (329), не firewall/Android.
Неизвестных карте исходников не оставлено. Manual router/SDK-проверки не выполнены.

Структурный анализ предупреждает о размере legacy Yandex-файла (955 учитываемых
строк при пороге 900) и прежнего транспортного теста (570 при 500). Это не скрывается
как «всё quality зелёное». Отдельная декомпозиция разумна позднее, но перенос всей
подсистемы ради порога расширил бы риск этой исправляющей итерации.

### Что уточнялось в стендах

Начальный новый запуск был остановлен внешним лимитом и не засчитан успешным.
Стенд сначала оборачивал Python даже исправные файловые утилиты; теперь подставляется
только та утилита, чей отказ нужен конкретному сценарию. Trace её вызова обязателен;
обычные файловые операции остаются настоящими. Это ускорение стенда, не production.

Первый профильный прогон остановился на двух старых транспортных тестах. Их модель
отдавала 207 на PUT и не умела HEAD. Добавлены отдельные ответы PUT/HEAD; ожидание
правильного URL и границы caller не ослаблено. Прежний тест PROPFIND-размера заменён
на новые HEAD/reader-сценарии, поскольку это другой HTTP-контракт. Финальный профильный
runner завершился успешно после изменения моделей.

### Уровень доказательства

UCI и HTTP в Node-тестах представлены моделями; production helper не подменяется.
Реальны cp/cmp/wc/tar, права и файлы в уникальных `.build`-каталогах. Local HTTPS
использует настоящий curl и Python TLS-server, сертификат проверяется; `-k` не
применяется. Использован только 127.0.0.1, никаких настоящих облачных реквизитов.

ESLint не выполнен: `npm exec --offline -- eslint ...` завершился ENOTCACHED.
Node syntax-check не заменяет ESLint. Новый SDK/Android CI не запускался: Android не
менялся, тестовый IPK не объявлен канонической SDK-сборкой или установкой.

## Повторение

Рабочий каталог — корень репозитория. Нужны Node.js с `node:test`, Python 3,
POSIX sh/awk/sed/coreutils/tar, для дополнительного стенда — curl и openssl.
На Windows использован существующий `shellTestPath`, но этот проход выполнялся
на Linux; Windows-совместимость не заявляется по одному чтению кода.

```sh
node scripts/run-test-category.mjs --file yandexUploadRuntime.test.mjs --file yandexDiskRuntime.test.mjs --file yandexBackupRuntime.test.mjs --file logStorage.test.mjs --file logWriterRuntime.test.mjs --file portableShellAndStatus.test.mjs --file packageHardeningRuntime.test.mjs --file testCategories.test.mjs --file changeImpact.test.mjs
python scripts/build-test-ipk.py --variant all --out-dir .build/r318-packages
SHEEPFOLD_TEST_IPK="$PWD/.build/r318-packages/luci-app-sheepfold-family-internet-control_0.1.0-318_all.ipk" node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
SHEEPFOLD_TEST_IPK="$PWD/.build/r318-packages/luci-app-sheepfold-ai-support_0.1.0-318_all.ipk" node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
```

Ожидается exit 0. Не запускать полный wildcard `node --test tests/*.test.mjs`
для этой узкой задачи. Отдельный файл можно запускать напрямую во время разработки.
Для сохранения trace задать `SHEEPFOLD_YANDEX_UPLOAD_EVIDENCE_DIR`; fixtures штатно
удаляются. Для сравнения `SHEEPFOLD_YANDEX_TEST_SOURCE` указывает на каталог ровно с
исследуемым `sheepfold-yandex-disk`. Не выдавать staged-source за оригинал.

В архиве доказательств находится `evidence/httpsProbe.py`. После распаковки checks
в `.build/r318-checks` из корня репозитория:

```sh
python .build/r318-checks/evidence/httpsProbe.py --source package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-yandex-disk --output .build/r318-https-result.json
```

Ожидается `checks:10, passed:10`, exit 0. Скрипт создаёт временный сертификат,
loopback server и синтетические файлы; после себя удаляет временный каталог.
Не подставлять реальный endpoint или реквизиты в этот стенд. Проверка не устанавливает
пакет и не изменяет `/etc/config`/`/tmp/sheepfold` реальной системы.

## Что не закрыто

Сверка размера — не checksum. Remote writer может изменить объект без изменения
длины. HEAD может отсутствовать на реальном сервисе. Ответ уже выполненного PUT
не откатывается; отказ последующей проверки не доказывает отсутствия облачных
изменений. Между cmp и rm caller остаётся окно для другого локального writer.

Сверка UCI ограничена одним uploader: смена до его входа, ABA и окно после последней
проверки остаются. Нет общей блокировки всех отправителей, предела RAM-снимков,
потокового лимита заголовков или гарантии уборки после SIGKILL/отключения питания.

Старые collection XML/quota/prune, сохранение sync-status, обработка ошибки rm,
выбранный путь журнала и его блокировка, `push-events` entry, list/download и безопасный
restore требуют следующих проверок (R15). **Восстановление конфигурации не включено**.
Полная готовность backend Яндекс Диска не заявлена. Физический роутер, flash,
живой аккаунт Яндекс и нативный UCI не проверялись.
