# Sheepfold r305: проверяемый OAuth и привязанный к реквизитам кэш токена

Дата: 10 сентября 2026 года. База: `4936914` (r304), потомок принятой `bdb3a92`.
Версия обоих роутерных пакетов: `0.1.0-305`. Изменения локальные в `main`, push
не выполнялся. Итоговый commit/tree и контрольные суммы находятся во внешнем
`delivery-verification.json`; будущий hash не записывается в создающий его коммит.

## Итог и область

Исправлены **B85–B87**: OAuth refresh-обмен, соответствие кэша действующим реквизитам
и закрытая проверяемая публикация файла токена. В [реестре](bug-register.ru.md)
**87 карточек**; это не 87 независимых уязвимостей и не число тестов.

Изменён один production-скрипт `sheepfold-google-drive` и номер пакета. Существующий
`tests/googleDriveUploadRuntime.test.mjs` расширен без создания новой общей fixture
или изменения карты категорий. Ближайшие upload-сценарии r304 сохранены. Общая функция
проверенного разбора JSON используется также reader метаданных Drive, поэтому все
30 прежних сценариев загрузки входят в выборку, а не только новый обмен токена.

Android, правила доступа, workflow, runner и quality engine не менялись. D01,
отдельные запреты управления и карантин сохранены. Новые зависимости не добавлены:
используются предусмотренные jshn/curl/SHA-256 или OpenSSL. Установочные проверки и
разделение Standard/AI Support не ослаблены.

## B85. Корректный JSON не принимался, ошибки обмена могли выдаваться за токен

Оригинальный `access_token` ищет compact JSON регуляркой. При HTTP 200 и корректном
ответе с пробелами после двоеточия команда `test` завершается неуспешно. Это обычный
сценарий, не искусственный отказ. Compact JSON остаётся положительным контролем.

Отдельно воспроизведены приём похожего на токен частичного JSON, игнорирование
HTTP 400/500 и неуспешного exit curl, неподтверждённые тип/срок токена. Неправильный
срок мог заменяться на 3000 секунд. `-d` передавал непрозрачные реквизиты без
URL-кодирования: синтетические `+`, `&`, `%` менялись при разборе формы.

Теперь данные передаются через `--data-urlencode name@file`. По отдельности
проверяются exit HTTP-клиента, HTTP 200, чтение и размер тела, JSON, поля и типы.
`access_token` должен быть безопасной строкой Bearer, `token_type` — Bearer,
`expires_in` — положительным целым в предусмотренном диапазоне. Ошибка сервера
не превращается в токен. Короткий действующий срок не расширяется до стандартного.

**Почему:** регулярка с дополнительными пробелами не становится JSON-парсером;
одного `curl --fail` недостаточно для проверки успешного тела. Штатное кодирование
curl надёжнее ручной замены отдельных символов. Аргументы процесса содержат пути
к закрытым файлам, не значения client_secret/refresh_token.

При внешней сверке jshn выявлены две существенные особенности: `json_load` использует
`eval` командной подстановки и может скрывать неуспешный exit `jshn`; проверка
отсутствующего поля обращается к unset-переменным и несовместима с безусловным
`set -u`. В ограниченном JSON-subshell nounset отключён, все обязательные поля
проверяются явно. Вывод `jshn -r` исполняется только после успешного завершения
доверенного парсера. Никакой пользовательский текст напрямую не исполняется.

**Граница:** модель jshn отражает проверенную семантику, но нативная libubox не
запускалась. JSON-дубли подчиняются парсеру. Размер OAuth-ответа проверяется после
загрузки: потоковая квота RAM не реализована. Поиск папок и другие старые regex
остаются отдельными задачами R14.

## B86. Токен прежних реквизитов использовался после смены аккаунта

При изменении client_id, client_secret либо refresh_token старый access_token
продолжал возвращаться из кэша без обращения к endpoint. В отдельном сценарии
проверен настоящий `archive-push`: HTTP-модель записывает заголовок Authorization
при отправке архива и обнаруживает прежний токен. В r305 этот сценарий использует
новый токен, полученный с изменёнными реквизитами.

**Это не фактическая отправка данных другому аккаунту:** сеть полностью заменена
моделью, реквизиты синтетические. В реальной системе несовпадение папок/прав могло
также привести к отказу. Подтверждён именно неправильный выбор токена.

Кэш теперь связан с тройкой реквизитов через проверенный SHA-256 полей, разделённых
длинами. Он содержит cache_key/issued_at/expires_at, но не refresh token. UCI
читается с проверкой show/get и повторным сравнением. При совпадении ключа и срока
кэш переиспользуется; legacy/просроченный/несовместимый кэш требует нового обмена.
Ошибка чтения существующего файла останавливает операцию, а не выдаётся за отсутствие.

Время проверяется до HTTP и после. Истечение отсчитывается от начала запроса;
60 секунд — запас для кэша, не продление срока. Смена реквизитов во время запроса
обнаруживается перед возвратом. Ошибка нового обмена не включает fallback на
токен прежнего контекста. Отказ SHA/date с правдоподобным частичным stdout не принимается.

**Почему:** очистка кэша только в одном UI не охватывает прямой UCI/других writers.
Постоянный отказ от кэша создаёт лишнюю нагрузку. Контекстный ключ сохраняет полезное
переиспользование, не требуя дублировать refresh secret в кэш-файле.

**Граница:** это не глобальная транзакция всех UCI writers и OAuth-запросов.
Между последней сверкой и использованием остаётся окно. FOLDER_CACHE не связан
с новым аккаунтом/root_folder; полная миграция папок не заявляется. digest — не
подпись против root. Монотонные часы и автоматический отзыв токена в Google не добавлены.

## B87. Непроверенная и незащищённая публикация кэша

Старый прямой writer мог сначала создать файл с более широкими правами, затем
не проверить chmod. Ссылка перенаправляла запись в другой файл, а каталог по
имени кэша приводил к ошибке, которую последующие успешные команды скрывали.
Это проверено на изолированных объектах, не системных файлах пользователя.

Теперь используются umask 077, уникальный каталог 0700 и файлы 0600. Полный
кэш готовится до замены. Проверяются запись, права и тип целевого объекта;
symlink/каталог отвергаются. `mv` публикует готовый файл на той же файловой системе.
При обработанном отказе предыдущее содержимое сохраняется, cleanup удаляет только
принадлежащий операции каталог. B86 не позволяет принять сохранённый старый кэш
за подходящий новому контексту.

**Почему:** финальный chmod не защищает предшествующий промежуток создания;
прямая запись обнуляет прежние данные до готовности новых. Предварительное удаление
старого кэша или cleanup общего каталога увеличивали бы последствия отказа.

**Граница:** нет гарантии против привилегированной подмены между проверкой типа
и rename, hardlink-атак root, SIGKILL, отказа удаления, reboot или отключения питания.
Общая блокировка отправителей/fsync не добавлены. Кэш — расходное состояние RAM,
не подтверждение сохранности облачных резервных копий.

## Проверки и воспроизведение

| Проверка | Результат |
| --- | --- |
| Профильный runner | **150 тестов в 5 файлах, все прошли**, без skipped/cancelled |
| Google Drive runtime | **70 тестов:** 30 прежних upload и 40 новых OAuth |
| Те же новые 40 на оригинальном r304 | **37 не проходят, 3 проходят** |
| logStorage / logWriterRuntime | **4 / 34**, все прошли |
| packageHardeningRuntime | **17**, все прошли |
| testIpkPermissions, Standard | **25**, все прошли, включены в 150 |
| AI Support, повтор archive checks | **25**, все прошли, не прибавлены к уникальным |
| Обе тестовые упаковки r305 | Собраны; uploader совпадает с исходниками, 0755, версия и jshn проверены |
| Hardening распакованных Standard/AI Support | Оба успешны |

Статистика на старом файле не означает 37 отдельных ошибок. В частности, сценарий
с отказом новой стадии `mv` на старой версии обнаруживает отсутствие этой стадии,
не доказывает, что старый скрипт вызвал искусственно сломанный `mv`. Семантика
обычного отказа, положительные контроли и проверки новых защитных стадий разделены.

Первая промежуточная попытка wrapper для UCI пыталась найти host-утилиту, которой
в среде нет. Исправлен fixture: он сохраняет и вызывает свой UCI-двойник. Это не
ошибка продукта. Старый тест отсутствующего jshn перенесён на прежнюю границу:
модель удаляет библиотеку после получения метаданных. Иначе новая проверка OAuth
останавливает запрос раньше и тест не достигает заявленного отказа. Отдельно
проверено отсутствие jshn до начала авторизации. Assertions не отключены.

### Команды

Рабочий каталог — корень репозитория. Для Linux runtime нужны Node.js, Python 3,
POSIX sh и файловые утилиты. Нет сети и настоящих реквизитов. Ожидается exit 0:

```sh
python3 scripts/build-test-ipk.py --variant all --out-dir .build/ipk-output
SHEEPFOLD_TEST_IPK="$PWD/.build/ipk-output/luci-app-sheepfold-family-internet-control_0.1.0-305_all.ipk" \
node scripts/run-test-category.mjs \
  --file googleDriveUploadRuntime.test.mjs \
  --file logStorage.test.mjs \
  --file logWriterRuntime.test.mjs \
  --file packageHardeningRuntime.test.mjs \
  --file testIpkPermissions.test.mjs
SHEEPFOLD_TEST_IPK="$PWD/.build/ipk-output/luci-app-sheepfold-ai-support_0.1.0-305_all.ipk" \
node --test tests/testIpkPermissions.test.mjs
node --test --test-name-pattern 'Google Drive OAuth' tests/googleDriveUploadRuntime.test.mjs
node scripts/checkDocumentation.mjs --git 4936914
sh -n package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-google-drive
busybox ash -n package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-google-drive
node --check tests/googleDriveUploadRuntime.test.mjs
git diff --check
```

Для исходного воспроизведения положить оригинальный `sheepfold-google-drive`
из `4936914` в отдельный каталог и передать его в `SHEEPFOLD_GDRIVE_TEST_SOURCE`.
При этом новые 40 тестов должны завершиться с exit 1 и указанными 37/3. Не запускать
production-скрипт непосредственно под root вместо fixture: он меняет UCI/RAM.
Все временные данные теста находятся в `.build/gdrive-fixtures` и удаляются после
сценария; аварийное прерывание может оставить тестовые файлы. Сеть не используется.

Полный suite не запускался. Выбраны пять прямых файлов, названных quality plan для
изменённого загрузчика и его теста. Версионная строка пакета не стала поводом запускать
весь продукт. Карта зависимостей/engine/runner не менялись. Quality сообщает о длине
production-файла **1025 строк** при ориентире 900: предупреждение сохранено, не
отключено. Большая декомпозиция остальных cloud-команд не включена в этот узкий проход.

ESLint не выполнен: `npm exec --offline -- eslint ...` возвращает ENOTCACHED.
Node syntax-check его не заменяет. BusyBox использован для проверки синтаксиса,
не для доказательства доставки либо всех искусственных отказов. Native jshn/UCI,
Google OAuth/Drive, физический роутер/Android, официальные SDK и новая CI-сборка
не запускались. r305 — локальный интеграционный снимок, не стабильный релиз.

## Внешняя сверка семантики

10.09.2026 использованы только первичные источники, не личные аккаунты:

- [Google OAuth web-server protocol, refresh token](https://developers.google.com/identity/protocols/oauth2/web-server):
  refresh POST, application/x-www-form-urlencoded, успешный JSON с access_token,
  expires_in и token_type; client_secret помечен optional. Новые дополнительные
  механизмы OAuth из текущей документации не добавлялись без задачи.
- [curl manual](https://curl.se/docs/manpage.html): `-d` передаёт данные как есть,
  `--data-urlencode name@filename` кодирует содержимое файла.
- [OpenWrt libubox jshn.sh](https://lxr.openwrt.org/source/libubox/sh/jshn.sh):
  `json_load`, `json_get_type` и обращение к переменным полей. Из этого следует
  явная проверка exit и локальное отключение nounset, не доказательство исполнения
  native libubox в данной среде.

Остальные причины и состояния взяты из проверяемых исходников и fixture traces.
Подробные карточки — [B85–B87 и R14](bug-register.ru.md). История r304 не переписана
как будто OAuth-проверки уже входили в прежний прогон.
