# Sheepfold r299: сохранность и согласованность очереди просьб

Дата: **09.09.2026**. База: **`7f77e56` (r298)**; она содержит принятую владельцем
`bdb3a92` и её доработки тестирования/CI. Пакет: **0.1.0-299**, ветка `main`.
Точный итоговый commit и SHA-256 артефактов фиксируются в `delivery-verification.json`
архива проверок. Никаких push, удаления веток GitHub или установки на роутер нет.

## Результат и область изменения

Исправлены три группы B65–B67. [Реестр](bug-register.ru.md) содержит **67 карточек**:
исторические причины не переписаны, новые карточки подробно объясняют сценарий,
причину, решение, альтернативы и ограничения.

| Карточка | Наблюдение на r298 | Реализация r299 |
|---|---|---|
| B65 | Отказ reader удаляет действующую просьбу; раздельные поля и неверное время принимаются неоднозначно | Вся известная запись проверяется одним reader, часы нормализуются; ошибка даёт 503 и сохраняет проблемный файл |
| B66 | Два одновременных create дают два `duplicate:false` и два события | create/list/TTL используют один queue-lock, публикация и поиск дубля согласованы |
| B67 | List первым создаёт 0755 при umask 022, chmod ошибки подавляются, failed mv оставляет tmp | Оба пути требуют 0700; private mktemp, checked write/0600/publish, cleanup только своего tmp |

Основной изменённый файл —
`package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-access-request`.
В `root/www/cgi-bin/sheepfold-api` изменена **только одна строка message** для
существующего `access_request_unavailable`: причиной может быть ID либо очередь.
HTTP-обработчики, auth, rate-limit, source guards, формы и поля успеха не переписаны.
В Makefile повышен только `PKG_RELEASE`; новые зависимости не добавлены.
`sheepfold-lock-common` и `+flock` уже входят в обе редакции, их код не менялся.

Добавлен `tests/childRequestQueueRuntime.test.mjs`; существующий fixture копирует
также lock-common. Native Windows использует только явно указанную последовательную
модель flock; настоящая конкуренция/права/symlink проверяются отдельными Linux-тестами.
Карта categories и direct consumers обновлена, но runner, npm scripts, workflow,
Android, frontend, firewall и приоритеты не менялись. D01 остаётся действующим:
«Без ограничений» выше чёрного списка устройств для обычного интернета; отдельные
запреты управления и карантин сохранены.

## Как воспроизведено

Для B65 подменяется только файловый reader при обращении к `.request`, а не API
целиком. Wrapper пишет trace и возвращает ошибку. На r298 GET даёт 200/пустой список
и удаляет запись. На исправлении CGI даёт 503 и файл побайтно сохранён. Дополнительный
сценарий снимает отказ и получает ту же просьбу. В позднем отказе после частичной
сборки списка CGI отбрасывает весь неуспешный результат. Неправдоподобные часы и
неоднозначные записи проверяются до решения об удалении именно этой записи.

Для B66 первый create удерживается прямо перед публикацией. Второй явно достигает
либо прежней публикации, либо новой попытки lock; тест освобождает первый только
после подтверждения этого события. На r298 оба отвечают `duplicate:false`.
На r299 один публикует, второй возвращает его ID с `duplicate:true`; log один.
Другой тест удерживает тот же lock внешним процессом flock и подтверждает, что list
не удаляет истёкшую запись до освобождения; inode lock-файла остаётся прежним.
Это не статистическая попытка угадать гонку коротким sleep.

Для B67 проверяются реальные mode в Linux и injected отказы chmod/mv/mktemp.
Искусственный mktemp с чужим путём в stdout и exit 7 не позволяет cleanup удалить
этот путь. Неуспешное опубликование остаётся ошибкой, но собственный незавершённый
файл не накапливается при нормальной работе cleanup. Чужие временные файлы сохранены.

## Команды и результаты проверок

Рабочий каталог — корень клона. Нужны Node.js 22, Python 3 для IPK и Linux с
системным POSIX sh, awk/sed и файловыми утилитами; для native-сценариев — flock.
Стенды изолированы в `.build/test-fixtures`, используют синтетические UCI, DHCP/ARP,
часы и авторизацию. Не запускать production helper от root вместо теста: его
абсолютные пути предназначены для OpenWrt.

```sh
node --test tests/childRequestQueueRuntime.test.mjs
node scripts/run-test-category.mjs --file childRequestQueueRuntime.test.mjs --file childAccessRequestRuntime.test.mjs --file childAccessRequest.test.mjs --file lockCommon.test.mjs --file apiRateLimitRuntime.test.mjs --file homeNetworkAccess.test.mjs --file packageHardeningRuntime.test.mjs --file changeImpact.test.mjs --file testCategories.test.mjs
```

Фактически **148 тестов в 9 файлах: pass 148, fail/skip/cancel 0**. Новых сценариев
**29**. Те же новые тесты на неизменённом checkout r298 через
`SHEEPFOLD_REQUEST_TEST_SOURCE` дают **25 fail / 4 pass**; на исправленном коде
**29 pass**. Часть тестов защищает новые условия и контрольное старое поведение;
25 fail — не 25 независимых найденных дефектов. Полный suite не запускался.

`quality:plan` прочитан и сохранён. Советник по путям общего CGI/Makefile рекомендует
широкие категории, Android и полный прогон. Проверка diff ограничила влияние:
CGI меняет только текст одной существующей ошибки; форма/защищённые маршруты/Android
API не изменены. По решению владельца выполнены прямые тесты и непосредственные
соседи. Для lock-common добавлен прямой контрактный/поведенческий сосед, для fixture
— оба потребителя. Изменение карты тестов является добавлением зависимости, не
переработкой механизма отбора или изоляции. Автосборки/runner принятых коммитов сохранены.

```sh
python scripts/build-test-ipk.py --variant all
node scripts/run-test-category.mjs --file testIpkPermissions.test.mjs
node scripts/checkDocumentation.mjs --git 7f77e56
node scripts/runQualityChecks.mjs --git 7f77e56 --plan
busybox ash -n package/luci-app-sheepfold-family-internet-control/root/usr/libexec/sheepfold/sheepfold-access-request
busybox ash -n package/luci-app-sheepfold-family-internet-control/root/www/cgi-bin/sheepfold-api

```

Пакеты собираются в `.build/ipk-output`. Это **тестовые IPK**, не официальный SDK
и не установленный пакет. Фактические дополнительные результаты и контрольные
суммы фиксируются в приложенных журналах/машинном протоколе. Повтор тех же тестов
на втором варианте или восстановленном bundle не увеличивает число уникальных
сценариев. Предварительные и базовые отказы сохранены отдельно от final pass.

## HTTP и политика ошибок

Успех POST по-прежнему содержит `app`, `ok`, `requestId`, `duplicate`; настоящий
пустой GET — `requests: []`. Queue-reader, clock, directory/lock отказы возвращают
503 с существующими `access_request_unavailable` / `access_requests_unavailable`.
Неуспешная публикация остаётся 500 `request_failed`. Неизвестное устройство,
администраторское устройство и отсутствие opt-in сохраняют прежние коды.

Отказ не выдаёт интернет и не отзывает родительскую привязку. Автоматический повтор
изменяющего запроса не добавлен. Запись в очередь не равнозначна доставке уведомления.

## Компромиссы и открытые границы

Сохранение повреждённой записи означает временную недоступность всей очереди до
её диагностики, а не автоматическое удаление семейных данных. Не добавлена кнопка
самолечения либо rm всей очереди. Неизвестные поля схемы отклоняются, поэтому будущая
миграция формата должна быть явной. Уборка подтверждённых истёкших записей может
частично завершиться до следующей ошибки; это не атомарный rollback всех удалений.

Остаются R11: ограничение общего размера RAM и записи, обнаружение всех ошибок
перечисления каталога, уборка после SIGKILL, поддержка/миграция старых дублей,
монотонный TTL, изменение opt-in/ID вместе с UCI. Старые процессы и root-writers,
не использующие lock, не согласованы. Временные файлы при отказе самого rm могут
остаться закрытыми в RAM. Во время обновления нужно учитывать старые CGI-процессы,
а нагрузку/трёхсекундное ожидание измерять на роутере.

Штатная однодневная граница сохранена: ровно 86400 секунд ещё допустимы; запись
старше удаляется. Правило удаления дат из будущего тоже сохранено. Перевод часов
назад может поэтому удалить прежнюю просьбу — полноценный монотонный срок не заявлен.

Исторические SDK/Android-проверки принятой базы не отменены, но не присваиваются r299.
Новый CI/SDK, Android, настоящий UCI, физический роутер, uhttpd под нагрузкой и доставка
уведомлений не запускались. Успешное выполнение Linux-модели не заменяет эти уровни.
Это локальный интеграционный снимок, не подтверждённый стабильный релиз.

## Внешние технические источники

В этом проходе проверены [Linux man-pages flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html)
и [официальная справка BusyBox](https://busybox.net/downloads/BusyBox.html).
Первый источник объясняет advisory-границу, наследование открытого дескриптора и
необходимость общего inode. Второй напоминает, что набор applet зависит от сборки.
Они не служат доказательством запуска Sheepfold на конкретной прошивке; основные
доказательства дефектов — исходники, deterministic tests и журналы этого прохода.
