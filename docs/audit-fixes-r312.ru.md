# Аудит r312: подготовка резервных копий до отправки и владение временными файлами

Дата: **11 сентября 2026 года**. База: **`aafb71c` (r311)**, потомок принятого
`bdb3a92`. Ветка результата — `main`; публикация в GitHub не выполнялась.
Пакет: **0.1.0-312**. Реестр: **103 карточки**, новые **B102–B103**.

## Область

Изменены `sheepfold-google-drive` (только создание config-backup и подготовка
`archive-push`), release в Makefile, его существующий runtime-тест и профильные
документы. Общие test runners, CI, Android, политика доступа, UCI defaults и
протокол привязки не изменены. `restore-config` не исправлялся и не включался.

## B102: нельзя подтвердить полный проход после отказа tar

R311 подавляла результат `create_config_backup` через `|| true`. Когда tar записывал
частичный файл и возвращал ошибку, backup пропускался без увеличения errors.
Тест с **неизменённым** скриптом r311 получил
`{"ok":true,"pushed":1,"errors":0}`. Подставленная команда оставила trace вызова;
локальный уже отправленный журнал был удалён. Это технический отказ в синтетическом
fixture, не наблюдение повреждённой памяти пользовательского роутера.

Теперь сначала готовятся копия постоянного config и имеющийся снимок events.log.
Проверяются копирование, режимы, соответствие исходнику, результат tar, единственный
member и байты после извлечения в stdout. Исходный config перечитывается сравнением
после создания. Неправдоподобная или неуспешно полученная дата не используется.

До успеха подготовки нет облачных изменений и удаления отправляемых RAM-архивов.
Ошибка возвращается как `backup_prepare_failed` / `events_snapshot_failed`, с
`ok:false`, `pushed:0`, `errors:1`, ненулевым exit. Отказ записи диагностического статуса
не должен мешать основному ответу об ошибке.

**Компромисс:** сломанная config-копия останавливает весь данный архивный проход,
сохраняя локальные журналы. Отдельный `push-events` не изменён. Поздние ошибки HTTP
по-прежнему могут следовать за уже выполненными uploads/deletes: общей транзакции нет.

Почему проверяется содержимое: успешного exit или одинакового размера недостаточно
для доказательства локальной копии. Это ограниченная проверка своего архива, не
распаковка произвольного пользовательского архива в файловую систему и не применение
настроек. Gzip и резервный plain tar сохранены. Содержимое конфигурации не интерпретируется
как UCI; это снимок сохранённого файла, не commit/export чужих pending-правок.

## B103: имя с точностью до секунды не означает владение файлом

R311 создавала config/events в общем `.gdrive-backup-staging`. При совпадении секундного
имени запись заменяла прежнюю копию; последующий rm удалял её путь. В тесте заранее
подготовлена старая синтетическая копия и закреплена дата. После успешной команды
r311 чтение старого файла давало ENOENT; r312 сохраняет исходные байты.

Та же проверка охватывает events-копию и перенаправление через старый staging-symlink.
Проверка реального tar подтверждает режим вновь созданного файла до upload-chmod.
Старые 0644 не названы доказанной общедоступной утечкой: RAM-root обычного пути уже
имел 0700. Новый процесс использует umask 077, режимы 0700/0600 и уникальный каталог
через существующую `drive_workdir`.

Trap получает путь только после успешного создания. Штатное завершение и обработанные
отказы чистят собственные временные данные, не старые одноимённые файлы. Секундные
remote-имена сохраняются для совместимости; их совпадение у параллельных отправителей
остаётся открытым. Общая блокировка HTTP, политика remote-версий и автоповторы не добавлены.

## Изменение тестового fixture

Ранее fixture не создавал `/etc/config/sheepfold`; успешные архивные тесты не проходили
этап config-backup. Теперь файл синтетический, но tar/cp/cmp настоящие. В модели Drive
размер config-копии определяется из фактически принятых байтов; явные overrides
неуспешных HTTP/metadata сохранены. Это не доказательство работы настоящего Drive.

Выбранные исходные проверки запускаются с той же новой моделью, но оригинальным
скриптом через `SHEEPFOLD_GDRIVE_TEST_SOURCE`. Три успешных контрольных сценария исходной
версии не переименованы в ошибки. Восьми исходных проверок достаточно для воспроизведения
двух заявленных групп; все 29 на старой версии не запускались в окончательном проходе.

### Уточнение двух прежних тестов после добавления config

Соседний запуск нашёл два несоответствия именно тестового fixture. При отказе
копирования конкретного журнала программа могла правомерно отправить независимый
config-backup; прежний assertion запрещал вообще любой upload. Теперь trace содержит
имя объекта: проверяется отсутствие отправки повреждённого source, его сохранность
и допустимость только отдельно подготовленного config.

Второй тест задавал размер 26 байт сразу всем metadata-ответам. Это подходит исходному
синтетическому журналу, но не новому реальному gzip. Override привязан к имени
`synthetic.tar`; config получает фактический размер. Добавлен отдельный отрицательный
контроль: явно неправильные metadata config по-прежнему отклоняются. Производственный
код ради этих ожиданий не ослаблялся. Исходные два отказа, прерванный повтор и шесть
окончательных профильных проверок сохранены в доказательствах.

## Проверки и воспроизведение

Рабочий каталог — корень checkout. Требуются Node.js, Python 3, sh, обычные файловые
утилиты, tar/gzip; для отдельного теста — установленный BusyBox. Все данные синтетические
и находятся в `.build`, fixture удаляет их после завершения. Сам uploader напрямую на
рабочем роутере от root для повторения тестов не запускать.

```sh
node --test --test-name-pattern='Google Drive local archive snapshots|Google Drive archive format controls' tests/googleDriveUploadRuntime.test.mjs
node --test --test-name-pattern='Google Drive independent upload evidence|Google Drive upload preparation|Google Drive checks preparation before remote mutation|Google Drive status observation safety' tests/googleDriveUploadRuntime.test.mjs
node --test tests/logStorage.test.mjs tests/packageHardeningRuntime.test.mjs
node --test tests/logWriterRuntime.test.mjs
python3 scripts/build-test-ipk.py --variant all
```

Новый набор: **29 pass, 0 fail/skip**, exit 0. Исходная r311, восемь избранных
контролей: **3 pass, 5 fail**, намеренно ненулевой exit. Это не пять независимых
уязвимостей. Соседние результаты и окончательный протокол поставки приведены ниже.

Проверка двух вариантов:

```sh
SHEEPFOLD_TEST_IPK=.build/ipk-output/luci-app-sheepfold-family-internet-control_0.1.0-312_all.ipk node --test tests/testIpkPermissions.test.mjs
SHEEPFOLD_TEST_IPK=.build/ipk-output/luci-app-sheepfold-ai-support_0.1.0-312_all.ipk node --test tests/testIpkPermissions.test.mjs
```

Из каждого заново собранного IPK дополнительно извлечён rootfs в отдельный `.build`
каталог, выполнен `sheepfold-runtime-hardening <root>`, сверены байты uploader
с исходником и его режим 0755. Каждый вариант прошёл 25 архивных проверок.
Это не SDK-сборка и не opkg/apk-установка на роутер.

Советник `inspectChangeImpact` отнёс изменение release к critical и предложил полный
прогон. Полный набор сознательно не выполнен: номер release не изменяет протокол,
политику, зависимости или схему UCI. Выбраны прямые тесты uploader, dispatcher,
writer scheduler, hardening и оба IPK; карта зависимостей и runners не менялись.

## Существенные ограничения

HTTP, UCI и jshn — тестовые модели. Настоящие OAuth/Google Drive, нативный UCI/libubox,
flash, роутер и физический телефон не проверялись. Нативный установленный BusyBox tar
проверяет только формат создаваемого архива, не все applet/target-конфигурации OpenWrt.
ESLint недоступен в локальном npm-кэше; синтаксис Node не заменяет линтер.

Снимки увеличивают расход RAM. Параллельные внешние изменения, ABA, подмена root-процессом,
SIGKILL, отказ cleanup, fsync и power loss не покрыты. При ошибке upload новый временный
config-backup очищается, исходный постоянный файл остаётся. Это не долговечная очередь.

Формат remote-имён, общий предел хранения, полная пагинация, самостоятельное восстановление
и чтение нестандартного log_cache_path остальными экспортёрами остаются R13/R14. Изменения
не открывают дополнительные права доступа и не меняют принятый приоритет «Без ограничений».

поставляемом протоколе проверки архива.
