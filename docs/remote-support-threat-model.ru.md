# Модель угроз временной удалённой техподдержки

<!-- §rsup001 -->

Статус: проектный документ. Рабочего удалённого канала в Sheepfold пока нет; неактивная LuCI-заглушка не устанавливает транспорт, не связывается с сервером и не меняет сеть роутера.

Документ защищает будущую реализацию от превращения временной помощи в постоянный скрытый вход. Он дополняет [общий план](remote-support-access-plan.ru.md), [протокол](remote-support-protocol.ru.md) и ADR-0022.

## Действующая граница HTTPS/typed

[ADR-0031](architecture/decisions/0031-typed-https-remote-support.ru.md) заменяет FRP/SSH/bastion
исходящим HTTPS с Ed25519-signed сообщениями. Серверная реализация есть в private source;
устанавливаемый OpenWrt-клиент по решению владельца 23.10.2026 отложен. Новый Node-стенд
не добавляет этот клиент и не включает интерфейс.

- Оператор аутентифицируется mTLS и TOTP; код заявки сам по себе не даёт доступа
- Роутер принимает только allowlisted diagnostic/prepare/apply, не shell-строки или SSH-ключи
- Каждое изменение требует точного plan hash и нового локального подтверждения
- Identity, исходный session deadline и server binding отделены от RAM lease/sequence/boot ID
- Reboot/reconnect не продлевает доступ; старые полномочия загрузки не восстанавливаются
- Локальный отзыв и истечение срока запрещают новые действия независимо от сервера
- Подпись не заменяет TLS, проверку scope, времени, replay, возможностей или согласия
- Нет маршрутизации LAN, WAN LuCI, reverse SSH, FRP или fallback на прежний transport
- Typed diagnostic results видит control-сервер; это не HPKE report plane, поэтому нужны
  минимизация, безопасные recipes и отдельный gate реальных данных

```text
Владелец -> локальное разрешение / exact plan approval / отзыв
Будущий router manager -> исходящий HTTPS + Ed25519 -> control service
Оператор -> mTLS + TOTP -> allowlisted очередь операций
Роутер -> проверка scope/lease/replay/consent -> ограниченный результат
```

Следующие разделы являются исторической моделью угроз первоначального FRP/SSH-проекта.
Общие риски кода, replay, часов, root-секретов и Podkop остаются полезны; требования
установить `frpc`, bastion или SSH forwarding заменены ADR-0031 и не подлежат реализации.

## Защищаемый результат

Владелец локально создаёт одно разрешение для одной заявки. Техподдержка, уже вошедшая в закрытую служебную систему с MFA, один раз принимает это разрешение и получает временный SSH-доступ только к указанному роутеру. Истечение срока или локальный отзыв закрывают доступ независимо от состояния браузера, телефона, `frpc` и внешнего сервера.

Функция не должна:

- открывать LuCI, Dropbear/SSH или FRP reverse-порт всему WAN;
- маршрутизировать домашнюю LAN через relay;
- использовать root-пароль владельца, LuCI cookie или Android Bearer;
- позволять серверу самостоятельно начать или продлить доступ;
- менять конфигурацию Podkop, AdGuard Home или IPv6 ради собственного запуска;
- считать номер порта, имя proxy или 12-значный код шифрованием;
- продолжать работу после неясной ошибки проверки подписи, срока или личности.

## Границы доверия

```text
локальный владелец и LuCI
        |
        | явное включение и «Дать доступ»
        v
router backend (root) ---- временный ключ ---- Dropbear 127.0.0.1:22
        |
        | подписанные сообщения и отдельный manager
        v
frpc (непривилегированный UID) -- mTLS --> relay/frps
                                            |
                                            | внутренний маршрут сеанса
                                            v
                                  закрытый bastion
                                            |
                                            | MFA + служебная учётная запись
                                            v
                                  рабочее место техподдержки
```

Каждая стрелка является отдельной границей. Успешная проверка одной границы не заменяет остальные. Например, действующий TLS-клиент роутера не доказывает, что владелец создал разрешение, а знание кода не доказывает, что его ввёл сотрудник техподдержки.

## Активы

| Актив | Почему важен | Где допустимо хранить |
|---|---|---|
| Долговременный приватный ключ роутера | Отличает установку Sheepfold от другого клиента | На flash, root-only, вне UCI, экспорта и журнала |
| Публичная identity-запись роутера | Связывает подписанные запросы с одной установкой | Control plane и несекретный локальный идентификатор |
| Корневой ключ доверия Sheepfold | Проверяет server key manifest и запрещает подмену control plane | Публичная часть в подписанном пакете; приватная часть офлайн |
| Онлайн-ключ подписи сервера | Подписывает короткоживущие команды и relay map | В защищённом серверном хранилище с ротацией |
| Транспортный сертификат/секрет `frpc` | Разрешает конкретному клиенту подключиться к relay | Короткоживущий файл root-only; предпочтительно в RAM |
| 12-значный код | Позволяет принять уже созданное ожидание | Открыто только в локальном LuCI; на сервере только защищённый verifier |
| `sessionId`, сроки и sequence | Не дают reconnect или replay создать новый доступ | На обеих сторонах; секретом не являются, но защищаются подписью |
| Временный SSH-ключ | Даёт фактический root-доступ | Публичная часть временно в Dropbear; приватная часть только у bastion/техподдержки |
| Relay map | Определяет единственные разрешённые endpoint | Последняя подписанная рабочая копия на роутере |
| Журнал аудита | Позволяет понять, кто и когда открыл доступ | Без кодов, токенов, ключей, shell-команд и конфигурационных секретов |
| Sheepfold-owned firewall/route | Даёт только служебному процессу выйти напрямую к relay | Отдельные именованные firewall4/netifd-артефакты |

## Противники и ошибочные состояния

- случайный сканер из интернета;
- устройство ребёнка или вредоносный клиент внутри LAN;
- человек, случайно увидевший или услышавший код;
- злоумышленник с украденной служебной учётной записью без MFA;
- скомпрометированное рабочее место техподдержки;
- недобросовестный сотрудник, имеющий доступ к общей учётной записи;
- скомпрометированный relay, bastion или control plane;
- подмена DNS, TLS-сертификата, relay map или пакета;
- повтор старой подписанной команды, кода, heartbeat или transport lease;
- ошибка времени роутера, откат часов или перезагрузка;
- ошибка Sheepfold, firewall4, netifd, Podkop, AdGuard Home или `frpc`;
- DoS против relay/control plane и массовое одновременное включение роутеров;
- физический доступ к роутеру или полный root-доступ к нему.

Физический root-доступ к работающему роутеру находится вне возможности этой функции. Однако он не должен раскрывать ключи других роутеров или позволять войти в них.

## Неподвижные инварианты

1. Только локальное действие владельца создаёт claim; server push этого не делает.
2. Код без служебной аутентификации и MFA не открывает маршрут.
3. Служебная аутентификация без действующего одноразового кода не открывает маршрут.
4. Первый успешный claim необратимо сжигает код; повтор всегда отклоняется.
5. Claim действует не более 72 часов, а доступ после claim не более 24 часов.
6. Reconnect, reboot, смена relay, повтор команды и исправление часов не продлевают сроки.
7. Владелец может локально отозвать доступ даже при недоступном control plane.
8. Сервер независимо закрывает маршрут по отзыву и deadline.
9. Временный SSH-ключ удаляется при отзыве, expiry, смене режима, uninstall и boot-cleanup.
10. Reverse SSH доступен только с закрытого bastion. WAN-скан не видит рабочий SSH/LuCI/reverse-порт.
11. Домашняя LAN и произвольный port forwarding запрещены.
12. Direct-WAN совпадает одновременно по UID процесса, подписанному IP relay и разрешённому transport-порту.
13. Remote support не отключает IPv6 и не редактирует Podkop/AdGuard Home.
14. Секреты отсутствуют в UCI, argv, журнале, обычном экспорте, диагностике и push-уведомлениях.
15. Неизвестная версия протокола, команда, подпись, ключ или критическое поле дают отказ, а не совместимый небезопасный fallback.

## Порт не является секретом

В системе различаются два типа портов:

- `transportPort` - известный исходящий TLS-порт relay, например `443`; он входит в узкое direct-WAN правило и защищён взаимной криптографической аутентификацией;
- `sessionRoutePort` - случайно выделенный внутренний порт одного принятого сеанса на loopback/private-интерфейсе relay; к нему может обратиться только bastion.

Постоянный отдельный порт для каждого роутера не используется. Он создавал бы стабильный сетевой идентификатор, расходовал диапазон портов и оставался обнаружимым сканированием. Временный `sessionRoutePort` полезен для изоляции и быстрого отзыва, но не участвует в аутентификации.

12-значный код не содержит номер порта, адрес relay, `routerId` или обратимо закодированный `sessionId`. Иначе утечка одной величины раскрывала бы другую, а структура кода уменьшала бы его случайность. Control plane связывает код, заявку, роутер и внутренний маршрут в своей защищённой записи.

## Реестр угроз и контролей

| Угроза | Обязательный контроль | Fail-closed результат | Проверка |
|---|---|---|---|
| WAN-скан находит FRP/SSH | Reverse-порты слушают только loopback/private relay; внешний firewall допускает только transport TLS | Сканер не получает SSH banner и не видит порт сеанса | Внешний скан до, во время и после claim |
| Перебор 12-значного кода | CSPRNG, verifier с server-side pepper, не более пяти ошибок на claim, лимиты по учётной записи и источнику | Claim блокируется, нужен новый код владельца | Ошибочные попытки и параллельный перебор |
| Код подсмотрен | Код требует активной заявки, MFA и служебной учётной записи | Посторонний человек не получает маршрут | Попытка claim без каждого фактора |
| Порт вычислен из кода | Код и порт генерируются независимо; порт не публичен | Знание одного не помогает найти другое | Статистический/контрактный тест генератора |
| Повтор принятого кода | Атомарный переход `open -> claimed`, один server transaction | Ровно один победитель, остальные получают `claimAlreadyUsed` | Гонка нескольких claim-запросов |
| Повтор server-команды | Подпись, `sessionId`, монотонный `sequence`, nonce и expiry | Команда не выполняется второй раз | Replay golden vectors и рестарт manager |
| Подмена DNS/relay | Подписанная relay map, закреплённый trust root, TLS hostname validation | Последняя рабочая карта остаётся; неизвестный relay не используется | Поддельная карта, DNS и сертификат |
| Компрометация одного relay | SSH остаётся end-to-end, relay не имеет ключа техподдержки; control plane может отозвать relay map | Relay не видит команды и не открывает другой роутер | Перехват трафика и отзыв relay key |
| Компрометация control plane | Server-команда всё равно не создаёт claim; локальный deadline/revoke; разделение ключей | Новый доступ без local claim невозможен | Server push к роутеру без ожидания |
| Компрометация bastion | Временный ключ, один session route, 24 часа, немедленный отзыв | Доступ ограничен одной уже принятой заявкой | Попытка открыть другой router/session |
| Украденная служебная учётная запись | MFA, rate limit, закрытая сеть bastion, аудит | Без второго фактора и кода входа нет | Вход с паролем без MFA и code |
| Недобросовестный сотрудник | Номер заявки, видимое уведомление, запись всех переходов, короткий срок | Владелец видит факт доступа и закрывает его | Проверка журнала и локального revoke |
| Ошибка времени роутера | Server deadline плюс monotonic runtime; после reboot обязательная server revalidation | Неясный срок блокирует восстановление активного доступа | Перевод часов назад/вперёд и reboot |
| Reconnect продлевает доступ | Deadline создаётся один раз и подписан; transport lease короче session deadline | Новый socket наследует прежний конец | Reconnect перед самым expiry |
| Подмена/понижение протокола | Точная версия, allowlist message types, подписанный payload, запрет unsigned fallback | `protocolUnsupported`/`signatureInvalid`, tunnel закрыт | Старый/неизвестный envelope |
| Общий FRP token утёк | Общие токены запрещены; у роутера отдельная identity и короткий transport credential | Утечка одного клиента не открывает другие | Попытка credential A от имени router B |
| Секрет попал в журнал/argv | Передача через root-only файлы/stdin, централизованное маскирование | Операция прекращается при невозможности безопасной передачи | Поиск в UCI, `ps`, log, export, crash report |
| Чужой процесс использует bypass | Совпадение UID + relay IP + transport port | Пакет чужого UID идёт обычным маршрутом | nftables test с другим UID/адресом/портом |
| LAN-клиент использует tunnel | Нет subnet routing/GatewayPorts; target только loopback SSH роутера | Доступ к LAN отсутствует | Попытка TCP/UDP к нескольким LAN-адресам |
| Firewall/netifd reload стирает правило | Sheepfold-owned include и hotplug восстанавливают узкое состояние | До восстановления manager не заявляет `active` | Reload, WAN renew и failover |
| Ошибка Podkop захватывает transport | Отдельный mark/table только для support UID/relay/port | Manager пробует прямой WAN, не меняя Podkop | Четыре режима интеграции и сломанный Podkop |
| Сервер недоступен | Bounded backoff+jitter, последний relay map, локальный revoke/expiry | Семейные правила продолжают работать; срок не растёт | Длительный outage и массовый boot |
| Обновление/удаление оставляет вход | Preflight, server revoke, локальная очистка, boot-cleanup, package ownership | Обновление откладывается либо сеанс закрывается | Upgrade/downgrade/uninstall/power loss |
| CSRF/XSS в LuCI нажимает кнопку | Root password gate, LuCI ACL, POST/CSRF contract, backend nonce и подтверждение | Запрос без локальной сессии/nonce отвергается | API-вызов без LuCI auth и CSRF |
| Вредоносный пакет/обновление | Подписанный package source, точное имя/версия/архитектура, общий package manager | Модуль не устанавливается, режим остаётся off | Повреждённая подпись и подменённый asset |
| Ложный `success` UI | Read-back структурированного backend status | UI показывает ошибку/ожидание, а не активный доступ | Timeout, 5xx и расхождение состояния |

## Разделение ключей

Экспериментальный Node transport-клиент (`§rsup001`) принимает только подписанный one-shot
grant для своего CSR/stream/router/session, отдельного transport SPKI и точного leaf deadline.
CA не передаётся по этому wire. Token и signed credential response живут только в RAM;
HMAC snapshot/replay не допускает их сохранения. Неизвестные fields/DER/extensions, поздний
ответ после local revoke, clock rollback и изменённый duplicate закрывают grant. Это проверка
протокола, не доказательство живого SSH или изоляции service UID: доверенный процесс/root
может прочитать собственную память. [Точная граница](remote-support-protocol.ru.md#экспериментальный-transport-профиль).

- Один ключ не используется одновременно для package signing, server messages, TLS и SSH.
- Приватный identity-ключ роутера создаётся локально и никогда не покидает роутер.
- Server signing key отделён от TLS private key и от ключа, защищающего claim verifier.
- Transport credential ограничен одним роутером и коротким сроком. Общий `frpc` token для всех установок запрещён.
- SSH-ключ поддержки относится к одной принятой заявке и удаляется после неё.
- Ротация online server key выполняется манифестом, подписанным офлайн-корнем. Неизвестный ключ не принимается по команде того же неподтверждённого сервера.

## Компрометация компонентов

### Control plane

Даже скомпрометированный control plane не должен уметь создать claim на роутере. Он может попытаться злоупотребить уже открытым ожиданием, поэтому код, MFA, локальное уведомление, короткие сроки и локальный отзыв остаются независимыми барьерами.

### Relay

Relay видит метаданные соединения, но не SSH-команды. Он не получает долговременный identity-ключ роутера и приватный SSH-ключ. Отдельный relay можно исключить новой подписанной картой без замены остальных router identities.

### Bastion или рабочее место

Это наиболее опасная компрометация во время активной заявки, потому что техподдержка получает root shell. Поэтому боевой выпуск требует обновлений bastion, MFA, минимального списка операторов, запрета произвольного сетевого выхода из session route и процедуры немедленного глобального отзыва.

### Сам роутер

Полный root на роутере позволяет украсть его собственную identity. Сервер должен уметь отозвать один `routerId`; украденный ключ не даёт доступ к другим установкам. Перенос identity в backup на другой роутер запрещён.

## Реакция на инцидент

1. Локальный `Закрыть доступ сейчас` немедленно удаляет ключ, останавливает proxy и firewall/route state, не ожидая сервера.
2. Control plane закрывает session route и отзывает transport credential.
3. Компрометированный relay или online key исключается подписанным emergency manifest; старые команды добавляются в denylist по key/session range.
4. Владельцу приходит понятное уведомление о закрытии и причине без секретных технических данных.
5. Аудит сохраняет безопасные переходы состояния, но не команды shell и не содержимое домашней сети.
6. Новый доступ после инцидента требует нового локального claim; старый код, порт, ключ и `sessionId` не восстанавливаются.

## Принятые остаточные риски

- В первой версии одна общая служебная учётная запись хуже персональных аккаунтов: журнал различает заявку, но не доказывает личность конкретного сотрудника. Это осознанное временное ограничение, а не желательная конечная модель.
- Во время принятой заявки техподдержка фактически получает root shell. Полностью устранить риск злоупотребления без ограниченного command gateway нельзя.
- Метаданные факта и времени соединения видны relay/control plane, даже если SSH-содержимое зашифровано.
- Физический WAN-down, отсутствие питания, повреждённая прошивка и factory reset не исправляются интернет-туннелем.
- Один relay и динамический IPv4 пригодны только для PoC, но не доказывают отказоустойчивость боевого сервиса.

## Блокирующие условия выпуска

Рабочий переключатель нельзя включать, пока одновременно не выполнены условия:

- опубликован и протестирован версионированный протокол;
- отдельный security review подтвердил server/control plane/bastion;
