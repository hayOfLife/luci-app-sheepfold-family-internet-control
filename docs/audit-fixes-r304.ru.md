# Sheepfold r304: проверяемая загрузка архивов в Google Drive

Дата: 10 сентября 2026 года. База: `fd228c8` (r303), потомок принятой `bdb3a92`.
Версия обоих роутерных пакетов: `0.1.0-304`. Работа выполнена локально в `main`,
push не выполнялся. Точный коммит, дерево и контрольные суммы поставки находятся
во внешнем `delivery-verification.json`: будущий hash не записывается в сам коммит.

## Итог и область

Исправлены три группы **B82–B84**. В [подробном реестре](bug-register.ru.md) теперь
84 карточки, а не 84 независимо подтверждённые уязвимости. Исправлен путь загрузки
в одном production-файле — `sheepfold-google-drive`; версия пакета повышена до r304.

Проверены `push-events`, загрузка уже существующего архива в `archive-push`, локальная
команда `verify` и общие функции, через которые проходят эти операции. Внешняя сеть,
действующий аккаунт и реальные секреты не использовались. Остальные самостоятельные
команды просмотра, скачивания и восстановления не включались и не объявлены исправными.
Код Android, правила доступа, workflow, engine и runner тестов не менялись. Доработана
одна запись карты зависимостей, добавлены профильные тесты и ссылки документации.
D01 («Без ограничений» выше чёрного списка для обычного интернета), запреты управления
и карантин не менялись. Standard не получает AI-only зависимости.

## B82. Имена переменных выполнялись как команды

В обычных функциях встречались строки `logs_id verify_json`, `local_bytes` и другие
списки имён без `local`. Shell пытался запустить первое имя как программу. Оригинальные
`push-events`, `verify` и `archive-push` в локальном стенде завершаются с `not found`;
это обычный сценарий с корректными синтетическими реквизитами, не искусственный отказ.

В охваченных функциях добавлены настоящие объявления, включая параметры и временные
имена общих вызовов. Их значения не перезаписывают состояние вызывающей функции.
Не отключались `set -e`, проверка ошибки и ветви отказа ради продолжения процедуры.

**Почему:** удаление одной строки оставило бы следующий аналогичный отказ, а глобальные
временные имена сохраняли бы риск взаимного влияния. Неиспользуемые в загрузке функции
`cmd_list`, `cmd_download`, `latest_backup_name`, `cmd_restore_config` и
`folder_list_json_array` оставлены без изменения. В них всё ещё есть старые проблемы;
слепо включать восстановление конфигурации исправлением одного объявления опасно.

## B83. Локальный размер выдавался за проверку облачной копии

`upload_file_to_folder` вычислял `remote_bytes` повторным `wc` локального файла.
Функция сравнивала размер исходника с ним же. Успешный статус отправки мог разрешить
удаление исходного архива, хотя независимых сведений о сохранённом объекте не было.

**Точная граница доказательства:** оригинальная r303 останавливается раньше из-за B82.
Поэтому удаление архива воспроизведено на отдельном промежуточном варианте
`declarations-only`, где исправлены только объявления/область имён, но сохранён прежний
алгоритм отправки и проверки. В тесте локальный архив удалялся без запроса метаданных.
Нельзя пересказывать это как завершившееся удаление исходной неизменённой r303.

Теперь успешное создание или обновление завершается отдельным `files.get` с
`fields=id,size`. Проверяется успешный exit `curl`, HTTP 200, полный JSON, совпадающий
ID и допустимый размер. Ошибка или несовпадение не разрешают удалять исходный архив.
JSON читается через уже предусмотренную зависимость `jshn`, не регуляркой, зависящей
от пробелов. Размер нормализуется десятично и сравнивается строкой, без переполнения
арифметики shell. Нулевой файл с нулевым подтверждённым размером допустим.

**Почему:** ответ на отправку сам по себе не заменяет независимое чтение конкретного
сохранённого объекта. Прежняя операция «локальный размер = локальный размер» не может
обнаружить неполную загрузку. Существующий формат успешного ответа сохранён.
Самостоятельная CLI `verify <path> <bytes>` остаётся локальным сравнением переданного
числа: её нельзя называть сетевой проверкой сама по себе.

**Границы:** размер — не контрольная сумма. Другая последовательность байтов той же
длины не обнаруживается. Ошибка после PUT/PATCH/POST не доказывает, что объект в облаке
не изменён. Автоматические повторы административных/облачных записей не добавлены.

## B84. Неудачная подготовка тела запроса и незащищённые временные данные

В промежуточном варианте `declarations-only` подставленный `cat` печатает `partial`
и возвращает ошибку. Вызов находится в условном контексте: итоговый успешный `printf`
скрывает отказ, неполное multipart-тело отправляется, а источник может быть удалён.
Trace теста подтверждает и вызов `cat`, и фактически переданные байты, а не только
ожидаемый код команды. Подготовленное тело имело режим 0644 в проверенной Linux-среде.

Теперь отправляется закрытый проверенный снимок исходника. До HTTP проверяются
создание уникального каталога, копирование, `cmp`, права и размер. Multipart-тело
собирается в отдельном закрытом каталоге: каждый `printf`, `cat`, `chmod` и вызов `curl`
проверяется явно. Данные имеют 0600 внутри 0700; маска создания — 077. Операция удаляет
только собственный каталог, право очистки появляется после успешного `mktemp`.
После проверки метаданных исходник ещё раз сравнивается со снимком. Обнаруженное
изменение возвращает `source_changed` и сохраняет исходный файл.

**Почему:** `set -e` недостаточно для функции, вызванной в `if`/`!`. Нельзя заменять
реальное содержимое пустым телом, игнорировать отказ чтения или удалять общий каталог
как временный мусор. Снимок отделяет данные HTTP-запроса от дописываемого живого журнала.
Неудача проверки возвращается как ошибка, не как подтверждённая безопасная копия.

**Границы:** снимки увеличивают расход RAM; суммарная квота не реализована. Между
последним `cmp` и удалением остаётся окно для другого writer. SIGKILL/отказ удаления
могут оставить закрытый temporary-каталог. Общее согласование writers, checksum,
fsync и гарантия переживания отключения питания не реализованы.

### Почему девять файлов

Проверены uploader, storage-контракт, вызывающий writer, hardening и IPK. Карта влияния
получила только новую локальную запись; проверены `changeImpact`, `testCategories`,
`qualityAssistants` и разделение вариантов `productVariants`. Общие fixtures,
исполняющие runner и engine не менялись. Эвристический advisor расширяет рекомендацию
из-за изменения карты и версии; она не является основанием гонять все несвязанные
подсистемы. В этом узком изменении использован явный список прямых потребителей.

### Модель не заменяет облако или OpenWrt

Исполняется настоящий shell uploader с перенесёнными во временный каталог путями.
`curl` заменён записывающим протокольным двойником: фиксируются URL, метод, HTTP-статус,
exit, тело отправки и режимы файлов. `jshn` моделируется минимальным Python-адаптером
для `json_load`, `json_get_var`, `json_get_type`. Это **не нативная libubox** и не
доказательство работы на целевом роутере. Начальное обновление OAuth не является
целью сценариев: используется синтетический кэш. Отсутствует конфигурационный файл
для генерации нового backup; проверяется уже существующий синтетический архив.

Для искусственных ошибок системный POSIX sh не должен обходить PATH-подстановки.
Тест проверяет trace вызова. Python-двойники запускаются с `-S`, без загрузки сторонних
site-packages. Совместимость синтаксиса BusyBox не названа прогоном native curl/jshn.
Права сверяются по битам 0777: унаследованный setgid тестового каталога сам по себе
не разрешает чтение и не должен ошибочно проваливать проверку 0700.

Предварительные незавершённые/неуспешные журналы сохранены отдельно от итоговых:
задержка Python site-startup, исходно неверная длина fixture (25 вместо 26 байт),
проверка SGID как обычных прав и недостаточно строгие ранние assertions. Исправления
стенда не выданы за дефекты роутера. Baseline и intermediate затем прогнаны повторно
с теми же окончательными assertions, что и исправленная версия.

## Повторение

Из корня проекта (Node.js, Python 3, POSIX sh и обычные файловые утилиты):

```sh
python scripts/build-test-ipk.py --variant all --out-dir .build/ipk-output
node scripts/run-test-category.mjs --file googleDriveUploadRuntime.test.mjs --file logStorage.test.mjs --file logWriterRuntime.test.mjs --file packageHardeningRuntime.test.mjs --file changeImpact.test.mjs --file testCategories.test.mjs --file testIpkPermissions.test.mjs --file qualityAssistants.test.mjs --file productVariants.test.mjs
```

Итоговый локальный запуск использовал уже собранный Standard IPK через
`SHEEPFOLD_TEST_IPK`; AI Support проверен отдельно с тем же test-файлом.
`SHEEPFOLD_GDRIVE_TEST_SOURCE` задаёт каталог извлечённого старого скрипта исключительно
в тесте, не меняет установленный роутер. Оригинал и промежуточный скрипт с SHA-256,
текущий и накопительный патчи приложены во внешнем архиве.

## Внешняя проверка протокола

Первичные документы Google проверены 10.09.2026:

- [files.get](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/get):
  получение метаданных отдельного объекта по ID;
- [ресурс File](https://developers.google.com/workspace/drive/api/reference/rest/v3/files):
  `size` документирован как строка int64; checksum является отдельным полем;
- [загрузка файлов](https://developers.google.com/workspace/drive/api/guides/manage-uploads):
  разделение создания multipart и обновления media.

Это источник семантики API, а не результат реального Google Drive-вызова. Источники
OpenWrt jshn в текущую среду получить не удалось; нативная совместимость требует
отдельного подтверждения. Новая зависимость не добавлена: jshn уже в Makefile.

не выполнены настоящие HTTP/OAuth/TLS, native UCI/libubox, установка на роутер,
нагрузка, потеря питания, новые Android и канонические SDK-сборки.
