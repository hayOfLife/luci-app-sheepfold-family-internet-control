# ADR-0031: Типизированная техподдержка через исходящий HTTPS

- Статус: Принято
- Дата: 2026-10-23
- Теги: `§rsup001`, `§rsuppeer`
- Заменяет: FRP/SSH/bastion-часть ADR-0022; условия явного разрешения, 72/24 часа и независимого отзыва сохраняются
- Связанные документы: [текущий протокол](../../remote-support-protocol.ru.md), [граница проектов](../../remote-support-server-integration.ru.md), [модель угроз](../../remote-support-threat-model.ru.md)

## Контекст

Серверный ADR-0016 уже выбрал подписанные HTTPS-команды вместо reverse SSH. Публичный проект
сохранил прежний проект FRP и Node.js эксперимент другого профиля. Из-за этого документация
давала несовместимые указания, а старый reference нельзя было подключить к нынешнему серверу.
Наличие серверных исходников также ошибочно описывалось как наличие клиента OpenWrt.

## Рассмотренные варианты

1. Вернуть сервер к FRP/SSH. Отклонено: универсальный доступ шире необходимых типовых операций,
   требует отдельного транспорта, ключей, bastion и контроля уже открытых SSH-соединений
2. Считать старую схему совместимой, добавляя необязательные поля или отключая проверки.
   Отклонено: разные profile/capabilities, поля и жизненные циклы нельзя скрыть терпимым parser
3. Зафиксировать выбранный HTTPS/typed профиль в обоих проектах, сохранив прежний эксперимент
   как историю и проверив новую связь на компьютере. Выбрано

## Решение

Текущий source-профиль называется `sheepfold-support-control-1`. Домашний роутер в будущей
реализации сам обращается к HTTPS endpoint; сообщения дополнительно подписываются Ed25519.
Оператор подтверждает свою служебную identity через mTLS и TOTP. Коды заявок не заменяют эту
аутентификацию и не содержат адресов или портов.

Разрешены только известные diagnostic/prepare/apply операции. `runShell`, FRP, reverse SSH,
публичный LuCI и маршрутизация домашней LAN не являются запасным способом подключения.
Изменение требует точного plan hash и отдельного локального подтверждения. Report plane и
семейный relay не используются для обхода этого ограничения.

После reboot сохраняются только private identity и минимальная привязка сеанса к серверу и
исходному сроку. Новые enrollment, boot ID и lease обязательны; reconnect срок не продлевает.
Счётчики текущего обмена и подтверждение изменения не переносятся из старой загрузки.

Канонический текущий контракт: `typedPayload.mjs`, `typed-*-message-v1.schema.json` и ручной
`runControlPeer.mjs` в `tools/remoteSupport/`. Старые `ControlClient`, transport CSR/grant,
`experimental-*.schema.json` и session simulator остаются отдельными историческими моделями.
Автоматического переключения с текущего профиля на старый нет.

По актуальному указанию владельца устанавливаемый OpenWrt-клиент пока отложен. Node.js
reference не включается в пакет, LuCI-заглушка не активируется, сервер не развёртывается.

## Последствия

- Два проекта имеют один действующий архитектурный ориентир без потери старых исследований
- Исторический major/envelope и golden bytes не переписываются: текущий профиль отделён явно
- Совпадение checkout не означает опубликованный release: vendor pin обновляется только после
  review и фиксации канонического public commit, не ради успешного теста
- Локальный стенд не измеряет RAM/flash роутера и не доказывает локальное approval настоящей правки
- Поломка физического WAN по-прежнему требует локальной помощи

## Проверка

`remoteSupportTypedProtocol.test.mjs` защищает точные поля, profile, allowlist команд и сроки.
`remoteSupportControlHttp.test.mjs` отвергает подмену профиля без fallback. Ручной peer-стенд
проверяет обе подписи, HTTPS/mTLS/TOTP, synthetic результаты, resume, restart и revoke.
Команды, ожидаемый результат и ограничения находятся в
[runbook](../../../tools/remoteSupport/README.ru.md).

## Когда пересматривать

- Требуется новый diagnostic/repair за пределами текущего allowlist
- Начинается реализация отложенного OpenWrt manager или production provisioning
- Изменяются ключи доверия, сроки, reboot/replay либо правила локального подтверждения
